# LinKHU 스펙 문서

LinKHU는 경희대학교 주요 웹서비스 바로가기를 제공하는 브라우저 확장 프로그램이다.

이 폴더는 "무엇을 왜 이렇게 만들었는가"를 기록한다. "어떻게 일하는가"(이슈·브랜치·커밋·PR·검증 절차)는 [`AGENTS.md`](../AGENTS.md)가 원본이며, 여기서 반복하지 않는다. 운영 절차 문서(릴리스, 스토어 배포, 아이콘 가이드 등)는 [`docs/`](../docs)에 있고, 이 폴더는 링크로만 연결한다.

## 문서 상태

| 항목 | 값 |
| --- | --- |
| 상태 | Baseline v1 |
| 기준일 | 2026-07-30 |
| 제품명 | LinKHU |
| 저장소 | https://github.com/kangkyunghyun/LinKHU |
| 기준 버전 | `src/manifest.json` v2.4.0 |

이 기준선은 위 시점의 코드를 읽고 대조해 작성했다.

LinKHU는 **스펙을 먼저 확정하고 구현이 스펙을 따르는** 방식으로 일한다. 따라서 이 문서들에는 두 종류의 내용이 섞여 있다.

- **사실 기록** — 이미 구현된 것을 코드에서 확인해 적은 내용. 별도 표시가 없으면 사실 기록이다.
- **확정 스펙** — 아직 구현되지 않았지만 구현이 따라야 할 확정된 요구사항. 해당 절 서두에 `상태: 확정 스펙, 미구현`으로 표시한다.

아직 확정되지 않은 아이디어와 검토 중인 계획은 어느 쪽에도 넣지 않는다. 현재 확정 스펙 상태인 절은 [3-2-5 다크 테마 스펙](3-2-DESIGN-UI-RULES.md)이다.

## 키워드

요구사항 문장은 다음 키워드로 강도를 구분한다.

- **MUST** — 반드시 지킨다. 어기면 리뷰에서 반려 대상이다.
- **SHOULD** — 권장한다. 어길 때는 PR 본문에 이유를 남긴다.
- **MAY** — 선택이다. 해도 되고 안 해도 된다.

## 읽는 순서

```text
1     BACKGROUND                     제품 정의, 문제와 가치, 범위, 기술 스택, 용어
2-1   USER-STORIES                   학생 사용자가 무엇을 하려고 하는가
2-2   OPERATOR-REQUIREMENTS          메인테이너가 무엇을 유지해야 하는가
3-1   DESIGN-SOFTWARE-ARCHITECTURE   3개 화면과 데이터 흐름, 저장소 사용
3-2   DESIGN-UI-RULES                공식 색상표, 디자인 토큰 규칙, 다크 테마 스펙
3-3   DESIGN-DECISIONS               주요 결정과 그렇게 하지 않은 이유
4     DATA                           MASTER_SITE_LIST 스키마와 검증 파이프라인
5     TESTING                        자동 테스트 범위, 수동 검증 매트릭스, 오류 처리
7     DEPLOYMENT                     릴리스와 스토어 배포 요약
```

6번 관측 레이어는 만들지 않는다. LinKHU는 텔레메트리, 분석 SDK, 원격 로그 수집을 두지 않으므로 관측할 수단 자체가 없다. 근거는 [3-3 결정 기록](3-3-DESIGN-DECISIONS.md)을 참고한다.

## 변경 원칙

1. **스펙이 먼저다.** 구현 PR은 관련 스펙 문서를 먼저 갱신하거나, 스펙과 구현을 **같은 PR에서 함께** 바꾼다 (MUST). 스펙 없이 구현부터 하고 문서를 나중에 맞추지 않는다.
2. 코드나 규칙을 바꾸면 그 영향을 받는 스펙 문서를 **같은 PR에서** 갱신한다 (MUST). 문서 갱신을 후속 PR로 미루지 않는다.
3. 스펙에는 두 종류의 내용이 있다. **사실 기록**(구현된 것)과 **확정 스펙**(구현이 따라야 할 것)이다. 둘을 섞어 쓰되, 아직 구현되지 않은 절은 서두에 상태를 밝힌다 (MUST). 읽는 사람이 "이미 있는 것"과 "만들어야 할 것"을 구분할 수 있어야 한다.
4. 사실 기록에는 코드에서 확인할 수 없는 내용을 적지 않는다 (MUST). 확정 스펙에는 검증 가능한 기준을 적는다 (MUST) — "적절한 대비"가 아니라 "4.5:1 이상"처럼 측정 가능해야 한다.
5. 같은 내용을 두 곳에 쓰지 않는다 (MUST). `AGENTS.md`나 `docs/`에 이미 있는 내용은 링크로 대체한다.
6. 설계 방향을 바꾸는 판단(무엇을 채택했고 무엇을 거부했는지)은 [3-3-DESIGN-DECISIONS.md](3-3-DESIGN-DECISIONS.md)에 배경·대안·영향과 함께 남긴다 (MUST). 같은 논쟁을 PR마다 반복하지 않기 위한 기록이다.
7. 기준선을 크게 바꾸는 개정은 위 문서 상태 표의 상태와 기준일을 함께 올린다 (SHOULD).
