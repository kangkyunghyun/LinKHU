# 3-3. 설계 결정 기록

이 문서는 LinKHU가 "왜 이렇게 되어 있는가"를 남긴다. 코드를 읽으면 무엇을 했는지는 알 수 있지만, 무엇을 **하지 않기로 했는지**는 알 수 없다. 그 부분이 여기 있다.

기록의 목적은 같은 논쟁을 반복하지 않는 것이다. 결정을 뒤집는 것은 가능하지만, 뒤집을 때는 여기 적힌 배경이 더 이상 성립하지 않음을 보여야 한다.

## 3-3-1 빌드리스 정적 구성

**배경**

LinKHU는 화면 3개, 스크립트 6개 규모의 확장 프로그램이다. 상태 관리라 할 만한 것은 `chrome.storage.local`의 키 세 개뿐이고, 서버가 없다. 주 기여자는 소수이고 기여자는 학생인 경우가 많다.

**대안**

1. Vite + TypeScript + 번들러 — 타입 안전성, 모듈 시스템, 트리 셰이킹
2. 프레임워크(React 등) 도입 — 컴포넌트 재사용
3. 빌드리스 정적 파일 — 지금 구성

**결정**

3번을 택했다. `src/`의 파일이 그대로 확장 프로그램이 된다. 스크립트는 전역 객체를 노출하고 HTML의 `<script>` 순서로 결합한다.

**영향**

- `src/`를 그대로 브라우저에 로드해 개발한다. 빌드 감시나 소스맵이 필요 없다.
- 패키징이 단순하다. `src/` 하위를 전부 모아 ZIP으로 묶으면 끝이라, 새 파일을 추가해도 빌드 설정을 고칠 필요가 없다.
- 런타임·개발 의존성이 모두 없다. `npm install`할 것이 없고 공급망 위험이 사실상 없다. 의존성 취약점 알림에 대응하는 운영 비용도 없다.
- 이 원칙은 개발 도구까지 적용된다. 테스트는 프레임워크 대신 Node 내장 러너와 가벼운 브라우저 API 모킹을 쓰고, ZIP 패키징도 압축 라이브러리 없이 스크립트에서 직접 만든다. 랜딩은 웹폰트를 불러오지 않고 시스템 글꼴을 쓴다.
- 같은 이유로 ESLint 도입은 보류 상태다. 도입하면 개발 의존성이 처음으로 생긴다. 금지는 아니며, 도입 이득이 이 원칙을 깰 만큼 큰지 판단해야 하는 사안으로 남겨둔다 (MAY).
- 대가로 타입 검사가 없다. 이 부담은 규모가 작아 감당 가능한 수준으로 본다. 대신 검증을 스크립트와 테스트로 옮겼다 ([4-DATA](4-DATA.md), [5-TESTING](5-TESTING.md)).
- 대가로 파일 공유가 안 되는 경계가 생긴다. 확장과 랜딩이 검색 규칙을 각자 구현하고 테스트로 일치를 강제하는 구조([3-1](3-1-DESIGN-SOFTWARE-ARCHITECTURE.md))는 이 결정의 직접적 결과다.
- 이 결정을 뒤집으려면 "빌드 도입으로 줄어드는 비용이 도입·유지 비용보다 크다"를 보여야 한다. 화면이나 상태가 크게 늘어나는 시점이 재검토 지점이다.

## 3-3-2 Manifest V3 단일 소스 크로스브라우저

**배경**

Chrome, Firefox, Whale 세 스토어에 배포한다. Chrome과 Whale은 Chromium 기반이라 사실상 같지만, Firefox는 확장 API 구현과 심사 요구사항이 다르다.

**대안**

1. 브라우저별로 매니페스트와 소스를 분기 — 각 플랫폼에 최적화
2. 단일 MV3 매니페스트 + Firefox 전용 필드 — 지금 구성
3. Firefox 지원 포기 — 유지 비용 최소

**결정**

2번을 택했다. 매니페스트 하나를 유지하고, Firefox에만 필요한 설정은 `browser_specific_settings.gecko`에 담는다. Firefox가 무시하지 못하는 값(`strict_min_version` 140.0, `data_collection_permissions.required: ["none"]`)을 여기에 선언한다.

**영향**

- 패키지가 하나다. 같은 ZIP을 세 스토어에 제출한다. 브라우저별 빌드 분기가 없다.
- 대가로 가장 제약이 강한 브라우저에 맞춰야 한다. Firefox가 지원하지 않는 API는 Chrome 전용이라도 쓰지 않는다.
- 매니페스트를 바꾸면 세 브라우저 호환성을 모두 확인해야 한다 ([2-2](2-2-OPERATOR-REQUIREMENTS.md)).
- `data_collection_permissions`를 `none`으로 선언했으므로, 사용자 데이터를 수집하는 기능을 추가하면 이 선언과 Firefox 심사 답변을 함께 바꿔야 한다.

## 3-3-3 최소 권한

**배경**

확장 프로그램의 권한 요청은 설치 시 사용자에게 그대로 노출된다. 교내 서비스 바로가기라는 성격상, 넓은 권한을 요구하면 "이 확장이 내 학사 정보를 보는 것 아닌가"라는 의심을 살 수 있다.

**대안**

1. `tabs` 권한을 요청해 탭 상태를 자유롭게 다룬다
2. `<all_urls>` 호스트 권한으로 교내 사이트와 상호작용한다 (자동 로그인, 콘텐츠 삽입 등)
3. 최소 권한 — 지금 구성

**결정**

3번을 택했다. 요청 권한은 `storage` 하나이고, 호스트 권한은 GitHub 릴리스 조회 API **단 하나의 URL**로 좁혔다.

```text
permissions:       ["storage"]
host_permissions:  ["https://api.github.com/repos/kangkyunghyun/LinKHU/releases/latest"]
```

`chrome.tabs.create`와 `chrome.tabs.update`는 `tabs` 권한 없이도 동작하므로 요청하지 않는다.

**영향**

- 설치 시 노출되는 권한 경고가 최소화된다. 신뢰 확보에 직접 기여한다.
- 심사 대응이 단순하다. 권한 사용 근거를 설명하기 쉽다.
- 대가로 할 수 없는 일이 있다. 자동 로그인, 교내 사이트 콘텐츠 읽기·주입, 열린 탭 목록 기반 기능은 이 결정 아래에서 불가능하다. 이는 [1-BACKGROUND](1-BACKGROUND.md)의 "하지 않는 것"과 일치한다.
- 권한을 새로 추가하는 변경은 기능 판단이 아니라 **제품 정체성 판단**으로 다룬다 (MUST). 세 스토어 재심사와 기존 사용자 권한 재승인을 유발한다.
- 텔레메트리를 두지 않는 것도 이 결정의 연장이다. 사용 데이터 수집은 권한과 신뢰 양쪽에서 비용이 크고, 이 규모의 제품에서 얻을 이득이 그보다 작다고 봤다. 관측 레이어 문서를 만들지 않는 근거다.

## 3-3-4 GitHub Pages 랜딩

**배경**

스토어 페이지만으로는 117개 지원 서비스를 보여주기 어렵고, 설치 전에 제품을 확인할 경로가 필요하다.

**대안**

1. 별도 호스팅 + 도메인 구매
2. 스토어 설명만 사용
3. GitHub Pages로 `docs/` 서빙 — 지금 구성

**결정**

3번을 택했다. `docs/` 폴더를 GitHub Pages로 배포하고, `docs/**` 변경이 `main`에 들어오면 자동 배포한다.

**영향**

- 비용이 0이고 저장소와 함께 버전 관리된다.
- 대가로 **`docs/` 폴더만 서빙된다**. 랜딩이 `src/`의 파일을 참조할 수 없다. 이 제약이 두 곳에서 구조를 결정한다.
  - 검색 로직: 랜딩이 `docs/landing.js`에 규칙을 따로 구현하고, 확장 구현과의 일치를 테스트로 강제한다.
  - 색상 토큰: 랜딩이 `docs/landing.css`에 토큰 값을 복제하고, 동기 유지를 주석과 규칙으로 관리한다 ([3-2](3-2-DESIGN-UI-RULES.md)).
- 서비스 목록도 같은 이유로 `docs/assets/services.json`에 생성해 둔다. 이 생성물이 최신인지는 `npm run build`가 검사한다.
- 랜딩이 정적 페이지이므로 서버 로직이 필요한 기능은 넣을 수 없다. 문의 폼이 Google Forms를 쓰는 이유이기도 하다.

## 3-3-5 PR #98 반려 — 랜딩 디자인 언어의 확장 이식 거부

**배경**

외부 기여자가 [이슈 #97](https://github.com/kangkyunghyun/LinKHU/issues/97)에 대응하는 [PR #98](https://github.com/kangkyunghyun/LinKHU/pull/98)을 제출했다. 시스템·라이트·다크 3단계 테마 선택을 추가하는 PR이었고, 구현 품질과 검증은 충실했다. PR 본문에 30개 테스트 통과, 실제 브라우저에서의 테마 전환·저장·재실행 확인, 여러 폭에서의 반응형 확인, 명도 대비 측정, `prefers-reduced-motion` 대응까지 기록되어 있었다.

문제는 품질이 아니라 **방향**이었다. 이슈 #97과 PR #98은 다크 테마의 시각 언어를 "랜딩 페이지 다크 구역의 따뜻한 배경과 밝은 핑크 강조색"에서 가져오도록 설계되어 있었다. 즉 랜딩의 디자인 언어를 확장 프로그램 UI로 이식하는 방향이었다.

랜딩은 넓은 화면에서 스크롤하며 읽는 홍보 페이지이고, 확장 팝업은 320px 폭에서 즉시 목표를 달성해야 하는 도구다. 두 표면은 목적이 다르므로 시각 언어도 달라야 한다. 이 판단 기준이 당시 문서로 존재하지 않았다.

**대안**

1. 그대로 병합 — 다크 테마를 빨리 확보하고 시각 방향은 나중에 조정
2. 병합 후 후속 PR로 색만 교체 — 기여를 살리면서 방향 수정
3. 반려하고 기존 UI를 유지하는 방향으로 재구현 — 채택

**결정**

3번을 택했다. PR #98을 반려하고, 다크 테마는 추후 기존 확장 UI를 유지하는 방식으로 다시 구현하기로 했다. 반려 시 기여자에게 사유("기존 디자인과 방향성이 다름")와 향후 계획(다크 모드는 추후 반영)을 남겼다. 이슈 #97은 열린 상태로 유지된다.

1번과 2번을 택하지 않은 이유는, 테마 전환 구조가 색 값과 강하게 얽혀 있어 "나중에 색만 바꾸기"가 실제로는 재구현에 가깝기 때문이다. 방향이 다른 구현을 먼저 병합하면 그 위에 쌓인 결정을 되돌리는 비용이 커진다.

**영향**

- **판단 기준이 문서화되었다.** [3-2 확장 우선 원칙](3-2-DESIGN-UI-RULES.md)이 이 결정에서 나왔다. 앞으로 같은 성격의 PR은 코드 리뷰 전에 이 원칙으로 먼저 판단한다.
- **다크 테마의 요구사항이 스펙으로 확정되었다.** [3-2-5](3-2-DESIGN-UI-RULES.md)가 3단계 테마 모드, 저장 키와 폴백, 선택 UI 위치, 토큰 값 스왑 방식, 다크 팔레트와 대비 기준을 확정한다. 구현 PR은 그 스펙을 근거로 심사한다.
- 외부 기여자의 작업이 병합되지 않았다. 방향 기준을 문서로 먼저 제공하지 않은 상태에서 기여를 받은 것이 원인이다. 기능 성격의 이슈에는 **디자인 방향과 제약을 이슈 단계에서 명시해야 한다** (SHOULD).
- 이 결정은 "다크 테마를 하지 않는다"가 아니다. 시각 언어를 확장 UI 기준으로 정한 뒤에 한다는 뜻이다.

**참고: 판단이 한 번 뒤집혔다**

초기 리뷰 시점의 판단은 "감사 표시 후 병합하고 메인테이너가 후속 정리"였다. 이후 방향 문제가 색 값 교체로 해결되지 않는다는 점이 분명해지면서 반려로 결론이 바뀌었다. **방향이 어긋난 기여는 "일단 병합하고 나중에 고친다"가 성립하지 않는 경우가 있다**는 것이 이 사례의 교훈이다. 병합 여부를 판단할 때 "나중에 고치는 비용"을 실제로 추정한다 (SHOULD).

리뷰 과정에서 나온 코드 관점의 관찰도 함께 남긴다. 제출된 구현에는 저장 경쟁 상태를 막기 위한 다중 상태 관리가 있었으나, `chrome.storage.local.set`은 호출 순서대로 처리되므로 실제로 필요한 것은 저장 실패 시 되돌리기뿐이었다. 구독자가 하나뿐인 이벤트 구조도 콜백 하나로 충분했다. **일어나지 않는 문제를 막는 코드는 리뷰에서 걷어낸다** (SHOULD).

## 3-3-6 ES 모듈로 전환하지 않음

**배경**

`src/`의 스크립트는 모두 classic script다. 전역 객체를 노출하고 HTML의 `<script>` 순서로 결합한다([3-1](3-1-DESIGN-SOFTWARE-ARCHITECTURE.md)). 현대적인 방식은 ES 모듈(`import`/`export`)이다.

**대안**

1. `src/`를 ES 모듈로 전환하고 HTML에서 `type="module"`로 로드
2. classic script 유지 — 지금 구성

**결정**

2번을 유지한다. 새 공용 모듈(`shared.js`)을 추가할 때도 classic script로 만들고 `data.js` 다음 순서로 로드하도록 했다.

이유는 **검증 도구가 이 구조에 묶여 있기 때문**이다. `scripts/validate-data.js`와 테스트 하네스는 `src/`의 파일을 Node의 `vm`으로 평가해 전역을 꺼내 쓴다. ES 모듈로 바꾸면 이 로딩 방식이 통째로 성립하지 않아 검증 스크립트와 테스트를 함께 재작성해야 한다. 얻는 것(모듈 스코프, 명시적 의존)에 비해 치르는 비용이 크다.

**영향**

- 스크립트 로드 순서가 곧 의존 관계다. 순서를 바꾸면 깨진다. 이 제약은 [3-1](3-1-DESIGN-SOFTWARE-ARCHITECTURE.md)에 명시되어 있다.
- 전역 이름이 충돌하지 않도록 각 파일이 객체 하나만 노출한다.
- Node 테스트에서 쓰려면 `module.exports` 가드가 필요하다.
- 이 결정을 뒤집으려면 검증 스크립트와 테스트 하네스의 재작성 계획이 함께 나와야 한다 (MUST).

## 3-3-7 문의 채널로 Google Forms 선택

**배경**

사용자 의견을 받을 경로가 필요했다. GitHub 이슈만으로는 계정이 없는 학생을 놓친다.

결정을 지배한 제약은 하나다. **확장 프로그램은 소스가 공개된다.** 스토어 패키지는 누구나 열어볼 수 있고 저장소도 공개다. 따라서 **어떤 비밀 키도 확장 안에 숨길 수 없다.**

**대안**

1. 자체 백엔드 API — 서버 운영 비용과 인증 키 보관 문제
2. 서드파티 폼 SaaS의 API 키 방식 — 키가 노출되면 폼이 오남용된다
3. Google Forms `formResponse` 직접 POST — 지금 구성

**결정**

3번을 택했다. Google Forms의 응답 제출 주소로 백그라운드 POST를 보낸다. 이 주소와 필드 id는 **공개돼도 안전한 값**이다. 노출되어도 남이 할 수 있는 일은 폼에 응답을 넣는 것뿐이고, 그건 원래 누구나 할 수 있다.

수신은 응답 시트와 이메일 알림으로 처리한다. 팝업·설정·랜딩 세 경로의 문의가 폼 하나로 모인다.

답변용 이메일은 Forms의 **내장 "이메일 수집" 기능을 쓰지 않고 선택 단답형 질문으로 받는다.** 내장 기능은 로그인을 강제해 익명 백그라운드 전송이 깨지기 때문이다. 이메일 질문 id를 비워두면 입력란 자체가 숨겨지므로, 이메일을 받지 않는 구성으로도 운영할 수 있다.

**영향**

- 서버가 없다. 운영 비용이 0이고 개인정보를 직접 보관하지 않는다.
- 확장에 비밀값을 두지 않는다는 원칙이 유지된다. 새 외부 연동을 추가할 때도 같은 기준을 적용한다 (MUST) — **비밀 키가 필요한 방식은 채택할 수 없다.**
- 대가로 전송 성공을 확인할 수 없다. CORS 제약 때문에 응답을 읽지 못하므로 "네트워크 오류 없음 = 성공"으로 간주한다. 이 한계에서 파생되는 검증 절차가 [5-TESTING](5-TESTING.md)에 있다.
- 확장과 랜딩이 같은 폼·같은 필드를 쓰는지는 테스트로 고정한다.

## 3-3-8 imgSrc 명시 경로 유지

**배경**

`MASTER_SITE_LIST`의 117개 항목이 모두 `imgSrc`를 직접 적는다. 값은 대부분 `images/{카테고리}/{id}.png` 꼴이라, 규칙에서 유도해 필드를 없앨 수 있어 보인다.

**대안**

1. `imgSrc`를 없애고 `category`와 `id`로 경로를 계산
2. 명시 경로 유지 — 지금 구성

**결정**

2번을 유지한다.

규칙이 항상 성립하지 않는다는 것이 이유다. 전용 도안이 없는 서비스가 다른 서비스의 아이콘을 공유하는 경우가 있어([4-DATA](4-DATA.md)), 규칙으로 유도하면 예외 처리가 다시 필요하다. 예외가 있는 규칙은 규칙이 아니다.

명시 경로는 검증 스크립트와도 잘 맞는다. 값이 그대로 파일 경로이므로 존재 확인, `src/` 이탈 검사, 미사용 이미지 탐지를 모두 문자열 비교로 처리할 수 있다.

**영향**

- 항목마다 한 줄이 더 길다. 대신 데이터만 보고 어떤 아이콘을 쓰는지 알 수 있다.
- 아이콘 공유가 자연스럽게 표현된다. `imgSrc`에 중복 제약을 두지 않는 근거다.
- 파일명을 `id`와 맞추는 것은 권장이지 강제가 아니다.

## 3-3-9 검색 랭킹을 확장과 랜딩에서 통일

**배경**

랜딩과 팝업이 각자 검색을 구현하면서 정렬 규칙이 달랐다. 팝업에서 검색 후 `Enter`를 누르면 첫 결과가 열리는데, 랭킹이 다르면 **같은 검색어에 다른 서비스가 열린다.**

**대안**

1. 각 화면이 자기 맥락에 맞는 랭킹을 쓴다
2. 랜딩의 이름 접두 우선 랭킹을 팝업에도 적용 — 채택
3. 공통 모듈로 추출해 한 곳에서 관리

3번은 파일 공유가 불가능해(§3-3-4) 선택지가 아니었다.

**결정**

2번을 택했다. 이름 접두 일치를 최우선으로 하는 랭킹으로 통일했다. 사용자가 이름 앞부분을 입력하는 것이 가장 흔한 검색 방식이므로, 그 경우 첫 결과가 정확해야 `Enter` 동작을 신뢰할 수 있다.

**영향**

- 두 구현이 존재하되 결과가 같아야 한다. 이 일치를 테스트가 강제한다 ([5-TESTING](5-TESTING.md)).
- 랭킹 규칙을 바꿀 때는 양쪽을 함께 바꾼다 (MUST). 한쪽만 바꾸면 테스트가 실패한다.
- 랭킹 단계는 [2-1](2-1-USER-STORIES.md)에 사용자 관점으로, [3-1](3-1-DESIGN-SOFTWARE-ARCHITECTURE.md)에 구현 관점으로 기술되어 있다.

## 3-3-10 학과 데이터 통합 정책

**배경**

경희대학교의 공식 학과 수와 LinKHU의 `학과` 카테고리 항목 수가 다르다. 2026-07-30 기준 목록에는 68개가 있다. 이 차이를 "데이터 누락"으로 오해하기 쉽다.

**대안**

1. 공식 학과 목록을 그대로 옮겨 개수를 맞춘다
2. 독립 홈페이지가 있는 곳만 항목으로 둔다 — 채택

**결정**

2번을 택했다. **하위 학과·학부가 상위 단과대와 같은 홈페이지를 쓰면 단과대 항목만 유지하고, 독립 홈페이지가 있을 때만 하위 항목을 만든다.**

LinKHU가 제공하는 것은 "학과 목록"이 아니라 "바로가기"다. 같은 주소로 가는 항목이 여러 개면 사용자에게는 선택지가 아니라 소음이다. 데이터 규칙에서도 같은 `url`의 중복을 금지한다([4-DATA](4-DATA.md)).

**영향**

- 목록 수와 공식 학과 수의 차이는 **정책의 결과이지 누락이 아니다** (MUST 인지). 개수 불일치를 근거로 항목을 추가하지 않는다.
- 학과 추가 요청이 오면 먼저 확인할 것은 "독립 홈페이지가 있는가"다. 없으면 해당 단과대 항목으로 안내한다.
- 학과가 독립 홈페이지를 새로 개설하면 항목 추가 대상이 된다.

## 3-3-11 버저닝은 semver

**배경**

확장 버전은 매니페스트에 적히고 스토어와 릴리스 노트에 노출된다. 어떤 변경에서 어느 자리를 올릴지 기준이 필요했다.

**대안**

1. 릴리스마다 패치만 올린다 — 단순하지만 변경 규모를 알 수 없다
2. semver를 따른다 — 채택

**결정**

2번을 택했다. **사용자에게 보이는 새 기능이 들어가면 마이너를 올린다.** 버그 수정과 내부 정리만 있으면 패치를 올린다.

실제 적용 사례로, 문의 기능·홈페이지 링크·검색 랭킹 개선이 함께 들어간 릴리스는 패치가 아니라 마이너(2.4.0)로 확정했다.

**영향**

- 사용자가 버전 숫자만 보고 변경 규모를 짐작할 수 있다.
- 릴리스 노트 작성과 자리 판단이 함께 이뤄진다. 노트에 새 기능이 있는데 패치라면 둘 중 하나가 잘못된 것이다 (SHOULD 확인).
- 매니페스트 버전은 `숫자.숫자.숫자` 형식이어야 하며, 릴리스 검증이 이를 확인한다.

## 3-3-12 업데이트 안내 링크 분기

**배경**

새 버전이 나왔을 때 사용자를 어디로 보낼지는 **설치 경로에 따라 다르다.** 스토어 설치본 사용자를 GitHub 릴리스로 보내면 ZIP을 받아 수동 설치하라는 뜻이 되고, 개발 빌드 사용자를 스토어로 보내면 자기 설치본과 무관한 페이지를 보게 된다.

**대안**

1. 항상 GitHub 릴리스로 안내
2. 항상 Chrome Web Store로 안내
3. 설치 경로와 브라우저를 판별해 분기 — 채택

**결정**

3번을 택했다. 두 단계로 판별한다.

1. **스토어 설치본인가** — 매니페스트에 `update_url`이 있는지로 판단한다. 이 필드는 스토어 설치 시 브라우저가 주입하며 저장소의 매니페스트에는 없다. 없으면 개발 빌드로 보고 GitHub 릴리스로 안내한다.
2. **어느 스토어인가** — 스토어 설치본이면 userAgent로 Whale / Firefox / 그 외(Chrome)를 구분해 해당 스토어로 안내한다.

**영향**

- 사용자가 자기 설치 경로에 맞는 곳으로 간다. 업데이트가 한 번의 클릭으로 끝난다.
- userAgent 판별은 취약한 방식이다. 틀려도 다른 스토어 페이지가 열릴 뿐 기능이 깨지지 않으므로 감수 가능한 수준으로 본다.
- 스토어가 늘거나 스토어 주소가 바뀌면 이 분기를 갱신해야 한다 (MUST).
- 판별 실패는 예외로 처리하고 기본값(GitHub 릴리스)으로 폴백한다.

## 3-3-13 릴리스 무결성 장치

**배경**

릴리스는 사람이 여러 단계를 순서대로 밟는 작업이다. 버전을 올리고, 노트를 쓰고, 머지하고, 태그를 민다. 어느 하나를 빠뜨리면 **잘못된 산출물이 스토어로 나간다.** 배포된 뒤에는 되돌리기 어렵다.

**대안**

1. 체크리스트 문서로 사람이 확인
2. 자동 검증으로 막는다 — 채택 (문서와 병행)

**결정**

2번을 택했다. 릴리스 경로에 세 가지 장치를 뒀다.

| 장치 | 막는 실수 |
| --- | --- |
| 태그와 매니페스트 버전 대조 | 버전을 올리지 않고 태그만 미는 것 |
| 릴리스 노트 존재 확인 | 노트 없이 릴리스가 나가는 것 |
| 재현 가능한 패키징 | 같은 커밋에서 다른 ZIP이 나오는 것 |

패키징은 파일 타임스탬프를 고정값으로 기록한다. 체크아웃 시각과 무관하게 **같은 소스에서 항상 같은 바이트의 ZIP이 나온다.** 스토어에 올린 파일이 저장소의 어느 커밋에서 나왔는지 해시로 대조할 수 있다.

**영향**

- 릴리스 실수가 배포 전에 워크플로에서 막힌다.
- 재현 가능성은 테스트로 고정되어 있다. 패키징 스크립트를 고칠 때 이 성질을 깨뜨리면 테스트가 실패한다 ([5-TESTING](5-TESTING.md)).
- 대가로 ZIP의 파일 시각이 1980년으로 보인다. 스토어 심사와 동작에 영향이 없어 감수한다.

## 3-3-14 단축키는 강제하지 않고 안내한다

**배경**

팝업을 여는 단축키를 매니페스트에 등록해 뒀지만, 사용자 환경에서 그 조합이 비어 있는 경우가 있다.

**플랫폼 제약이 결정을 강제한다.** 확장은 이미 점유된 단축키를 빼앗을 수 없다.

- 매니페스트의 단축키 설정은 **설치 시점의 제안일 뿐**이다. 운영체제, 브라우저, 다른 확장이 이미 쓰는 조합이면 등록되지 않는다.
- Chrome과 Whale은 확장이 단축키를 프로그래밍 방식으로 바꾸는 것 자체를 허용하지 않는다.
- Firefox는 변경 API가 있지만, 점유된 조합은 마찬가지로 가져올 수 없다.

**대안**

1. 다른 조합을 자동으로 시도해 하나라도 등록 — Chrome·Whale에서 불가능
2. 단축키 기능을 포기 — 등록에 성공한 사용자의 편의를 버린다
3. 등록 실패를 감지해 사용자에게 안내 — 채택

**결정**

3번을 택했다. 설정 페이지가 단축키 등록 여부를 확인하고, **비어 있을 때만** 안내 박스를 노출한다. 안내에는 Chrome·Whale·Firefox 각각의 단축키 관리 화면 경로를 담는다.

브라우저 내부 주소는 링크로 직접 이동시킬 수 없는 경우가 있어, 이동에 실패하면 주소를 클립보드에 복사하고 붙여넣도록 안내한다.

**영향**

- 단축키가 동작하지 않는 사용자가 원인과 해결 방법을 알 수 있다. 조용히 안 되는 상태가 사라진다.
- 이미 등록된 사용자에게는 안내가 보이지 않는다.
- 이 제약은 확장 코드로 해결할 수 없다. "단축키가 안 눌린다"는 제보에는 **먼저 브라우저의 단축키 설정을 확인하도록 안내한다** (SHOULD).
- 개선 여지로 남은 것은 현재 등록된 단축키를 설정 페이지에 상시 표시하는 것이다. 등록 여부와 무관하게 자기 조합을 확인할 수 있게 된다.
