# 5. 검증

LinKHU는 확장 프로그램 UI가 제품의 대부분이라, 자동 테스트로 잡을 수 있는 범위가 제한적이다. 브라우저 확장 API와 드래그 앤 드롭은 Node 테스트 환경에서 재현하기 어렵다.

그래서 검증을 두 층으로 나눈다. **순수 로직은 자동 테스트로 고정하고, 화면 동작은 수동 검증 매트릭스로 고정한다.** 어느 쪽도 상대를 대신하지 않는다.

```text
§5-1   자동 테스트        npm test가 덮는 범위
§5-2   덮지 못하는 것      자동화하지 않은 영역과 이유
§5-3   수동 검증 매트릭스   변경 유형별 확인 항목
§5-4   오류 처리          실패 시 동작 규약
```

## 5-1 자동 테스트

`npm test`는 Node 내장 테스트 러너(`node --test`)로 `tests/`를 실행한다. 2026-07-30 기준 7개 파일 23개 테스트다. 테스트 프레임워크를 따로 두지 않는다 — 의존성 없는 구성([3-3](3-3-DESIGN-DECISIONS.md))을 유지하기 위해서다.

| 파일 | 고정하는 것 |
| --- | --- |
| `shared.test.js` | 검색 정규화, 이름·id·카테고리 매칭, 점수 순위, 기본 순서 |
| `landing-search.test.js` | 랜딩 검색 정규화, 매칭, 결과 개수 제한, 기본 서비스 |
| `data-validation.test.js` | 저장소 데이터의 유효성, 중복 필드 탐지, 아이콘 공유 허용, 경로 구분자 |
| `browser-behavior.test.js` | 팝업의 중복 id 제거, 클릭·수식키·휠 클릭 동작, 버전 비교, 설정 저장 성공·실패 |
| `feedback.test.js` | 문의 설정 여부 판정, 전송 대상 필드, 이메일 선택 포함 |
| `landing-feedback.test.js` | 랜딩과 확장의 문의 전송 일치 |
| `package-extension.test.js` | 패키징 산출물의 재현 가능성 |

특히 중요한 두 테스트가 있다.

- **확장-랜딩 검색 일치** — `shared.test.js`가 `LinKHUShared.rankSites`와 랜딩의 `searchServices` 결과 순서가 같은지 확인한다. 두 구현이 갈라지는 것을 막는 유일한 장치다 ([3-1](3-1-DESIGN-SOFTWARE-ARCHITECTURE.md)).
- **확장-랜딩 문의 일치** — `landing-feedback.test.js`가 두 경로가 같은 폼·같은 필드로 전송하는지 확인한다.

검색 규칙이나 문의 전송을 바꿀 때는 **양쪽 구현을 함께 바꿔야 하며**, 위 테스트가 그것을 강제한다 (MUST).

`data-validation.test.js`는 저장소의 실제 데이터를 검사한다. 즉 `npm test`만 실행해도 데이터가 깨졌는지 알 수 있다.

패키징 테스트는 산출물의 **재현 가능성**을 고정한다. 파일 타임스탬프가 달라져도 같은 ZIP이 나와야 한다. 패키징 스크립트가 고정된 DOS 시각(1980-01-01)을 쓰는 이유다.

## 5-2 덮지 못하는 것

다음은 자동 테스트로 검증하지 않는다. 대신 §5-3의 수동 검증으로 다룬다.

| 영역 | 자동화하지 않은 이유 |
| --- | --- |
| 드래그 앤 드롭 정렬 | HTML5 드래그 이벤트와 포인터 좌표를 Node 환경에서 재현하는 비용이 크다 |
| 드래그 중 자동 스크롤 | 실제 레이아웃과 스크롤 위치가 필요하다 |
| 팝업 렌더링 결과 | `chrome.storage` 콜백과 DOM 렌더링이 결합되어 있다 |
| 테마·색상 표현 | 시각 판단은 사람이 봐야 한다 |
| 브라우저 단축키 | 브라우저가 등록하는 영역이라 확장 코드 밖이다 |
| 스토어 심사 요구사항 | 외부 시스템이다 |

이 목록이 길어지면 구조를 의심한다. 로직을 화면에서 분리해 순수 함수로 옮길 수 있는지 먼저 검토한다 (SHOULD). `shared.js`가 그렇게 분리된 예다.

## 5-3 수동 검증 매트릭스

변경 유형별 확인 항목이다. [`AGENTS.md`의 수동 검증 기준](../AGENTS.md)을 화면 단위로 구체화한 것이며, 상충하면 이 문서를 따른다.

PR 본문에는 **무엇을 어떤 기준으로 확인했는지 재현 가능하게** 적는다 (MUST). "정상 동작함"은 검증 기록이 아니다.

### 팝업

| 확인 항목 | 기대 결과 |
| --- | --- |
| 일반 클릭 | 새 탭이 활성 상태로 열리고 팝업이 닫힌다 |
| `Ctrl`/`Cmd` + 클릭 | 새 탭이 배경으로 열리고 **팝업이 유지된다** |
| 휠(가운데) 클릭 | 새 탭이 배경으로 열린다 |
| 검색 입력 | 이름·id·카테고리로 결과가 좁혀진다 |
| 검색 후 `Enter` | 첫 결과가 **현재 탭**에서 열린다 |
| 한글 조합 중 `Enter` | 조합만 확정되고 이동하지 않는다 |
| `/` 키 | 검색창으로 포커스가 이동한다 |
| 숫자 `1`~`9` | n번째 카드가 열린다 |
| 검색창에 숫자 입력 | 숫자 단축키가 발동하지 않는다 |
| 빈 결과 | 빈 상태 메시지가 보인다 |
| 아이콘 로딩 실패 | 확장 기본 아이콘으로 대체된다 |

### 설정 페이지

| 확인 항목 | 기대 결과 |
| --- | --- |
| 오른쪽으로 드래그 | 내 바로가기에 담기고 왼쪽 목록에서 사라진다 |
| 왼쪽으로 드래그 | 원래 카테고리 자리로 돌아가고 이름순으로 정렬된다 |
| 내 바로가기 안에서 드래그 | 순서가 바뀐다 |
| 긴 목록에서 위/아래 가장자리로 드래그 | 스크롤 영역이 자동으로 스크롤된다 |
| 저장 버튼 | 성공 알림이 뜬다 |
| 저장 후 새로고침 | 순서가 유지된다 |
| 저장 후 팝업 열기 | 같은 순서로 표시된다 |
| 검색 | 결과 없는 카테고리 그룹이 숨겨진다 |
| 단축키 미설정 상태 | 안내 박스가 보인다 |
| 단축키 설정 후 | 안내 박스가 사라진다 |

### 데이터 변경

| 확인 항목 | 기대 결과 |
| --- | --- |
| `npm run validate:data` | 오류 0건, 결과를 PR 본문에 기재 |
| `npm run build` | 랜딩 산출물 최신 확인 통과 |
| 팝업·설정 표시 | 추가·수정한 항목이 정상 표시된다 |
| 랜딩 검색 | 추가한 항목이 검색된다 |

### 패키징·매니페스트 변경

| 확인 항목 | 기대 결과 |
| --- | --- |
| `npm run build` | `dist/`에 ZIP이 생성되고 파일 목록이 예상과 일치한다 |
| 새 파일 추가 시 | ZIP에 포함되었는지 확인한다 (`src/` 하위는 자동 수집된다) |
| 매니페스트 변경 시 | Chrome·Firefox·Whale 호환성과 권한 범위를 확인한다 |

### UI·색상 변경

| 확인 항목 | 기대 결과 |
| --- | --- |
| 토큰 참조 | 브랜드 색이 하드코딩되지 않고 토큰을 참조한다 |
| 토큰 정의 일치 | 참조하는 토큰이 모두 정의되어 있다 (미정의 변수 0개) |
| 확장-랜딩 값 동기 | 공유 토큰 3종의 값이 두 파일에서 같다 |
| 명도 대비 | 일반 텍스트 4.5:1 이상, 측정값을 PR 본문에 기재 |
| 레이아웃 | 색만 바뀌고 배치·크기가 그대로다 |

색상 규칙의 원본은 [3-2](3-2-DESIGN-UI-RULES.md)다.

## 5-4 오류 처리

실패 상황에서의 동작 규약이다. 공통 원칙은 하나다. **부분 실패가 전체 사용을 막지 않는다** (MUST).

### 데이터 검증 실패

- `validate:data`는 오류와 경고를 나눠 출력하고, 오류가 있을 때만 종료 코드를 0이 아닌 값으로 둔다.
- 오류 메시지는 **어떤 서비스의 어떤 필드가 왜 잘못되었는지** 식별자와 함께 보여야 한다 (MUST). 식별자가 없으면 117개 중 어디를 고쳐야 할지 알 수 없다.
- 랜딩 산출물이 낡았을 때는 해결 명령(`npm run generate:landing-data`)을 메시지에 포함한다 (MUST).

### 저장소 실패

| 상황 | 동작 |
| --- | --- |
| `userOrder`가 없음 | `공통` 카테고리 기본 순서로 폴백 (MUST) |
| `userOrder`에 없는 id 포함 | 렌더링에서 제외, 화면은 정상 (MUST) |
| `userOrder`에 중복 id | 한 번만 렌더링 (MUST) |
| 저장 실패 | `chrome.runtime.lastError` 확인 후 사용자에게 실패 알림 (MUST) |

저장 실패를 조용히 넘기지 않는다. 사용자는 저장되었다고 믿고 페이지를 떠난다.

### 네트워크 실패

| 상황 | 동작 |
| --- | --- |
| 최신 버전 조회 실패 | 캐시된 값 사용, 없으면 업데이트 안내를 표시하지 않음 (MUST) |
| GitHub API 오류 응답 | 콘솔에 기록하고 캐시 값으로 폴백 (MUST) |
| 문의 전송 실패 | 사용자에게 실패 문구 표시, 입력 내용은 지우지 않음 (MUST) |
| 문의 채널 미설정 | 준비 중 안내 문구 표시 (MUST) |

버전 조회는 12시간 캐싱한다. 캐시가 없는 상태에서 조회가 실패해도 팝업의 다른 기능은 모두 동작해야 한다.

문의 전송은 `mode: "no-cors"`라 응답 본문을 읽을 수 없다. **네트워크 오류가 없으면 성공으로 간주한다.** 이 한계는 구조상 불가피하며, 성공 문구를 정할 때 전제로 삼는다 ([3-1](3-1-DESIGN-SOFTWARE-ARCHITECTURE.md)).

### 자산 로딩 실패

- 서비스 아이콘 로딩 실패 시 확장 기본 아이콘(`icons/icon48.png`)으로 대체한다 (MUST). 깨진 이미지 아이콘이 보이지 않아야 한다.
