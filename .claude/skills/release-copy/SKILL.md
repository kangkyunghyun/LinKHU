# 릴리스 문구 쓰기

**릴리스 노트를 사용자 언어로 다시 쓰는 일이다. 옮겨 붙이는 일이 아니다.**

원본 두 개를 제자리에서 갱신한다. 매번 새로 짓지 않는다.

| 문서 | 쓰는 곳 | 독자 | 릴리스마다 하는 일 |
|---|---|---|---|
| [`docs/copy/1-1-STORE-LISTING.md`](../../../docs/copy/1-1-STORE-LISTING.md) | Chrome / Firefox / Whale 설명란 | 설치를 고민하는 사람 | **변경 목록을 두지 않는다.** 계속 알릴 기능만 `[주요 기능]`·`[편의 기능]`에 한 줄로 더하고, 서비스 개수를 맞춘다 |
| [`docs/copy/1-2-COMMUNITY-POST.md`](../../../docs/copy/1-2-COMMUNITY-POST.md) | 에브리타임 등 커뮤니티 게시글 | LinKHU를 모르는 사람 | **변경 목록을 두지 않는다.** 계속 알릴 기능만 기능 목록에 한 줄로 더하고, 사용 지표를 다시 센다 |

두 글은 같은 릴리스를 다루지만 독자가 다르다. 스토어 글은 이미 페이지에 들어온 사람에게 목록으로 알리고, 커뮤니티 글은 아무 맥락 없는 사람에게 이게 뭔지부터 설명한다. 한쪽을 복사해 다른 쪽에 넣지 않는다.

**버전별 변경 목록은 어느 글에도 두지 않는다** (MUST). 커뮤니티 글을 읽는 사람은 이전 버전을 모른다. `(v2.8.0 업데이트)`가 소개보다 먼저 오면 지난 버전을 아는 사람용 글로 읽혀 그냥 넘긴다. 스토어 글은 예전에 맨 아래 `[vX.Y.Z 업데이트]` 절을 두었지만, 릴리스마다 세 대시보드에 손으로 붙여 넣어야 해서 빠뜨리기 쉬워 뺐다(이슈 [#283](https://github.com/kangkyunghyun/LinKHU/issues/283)). 버전별 변경은 Firefox 버전 노트와 Whale 버전 설명에 릴리스 노트로 들어간다.

**커뮤니티 글은 게시글 문법으로 쓴다** (MUST). 제품명 제목, `[주요 기능]` 같은 대괄호 섹션 제목, 리뷰·스타 요청은 스토어 문법이라 게시판에서는 광고로 읽혀 넘겨진다(이슈 [#196](https://github.com/kangkyunghyun/LinKHU/issues/196)). 첫 문장은 독자가 겪는 불편이고, 첫 문단 안에서 이게 무엇인지 드러나야 한다. 기능은 소개 문장 아래 `-` 목록에 한 줄씩 두어 훑어보기 쉽게 한다(이슈 [#253](https://github.com/kangkyunghyun/LinKHU/issues/253)). 목록 밖 문장은 `~습니다.`체로 통일한다.

변경 이력이 필요한 사람은 **홈페이지의 업데이트 섹션**으로 간다(이슈 [#190](https://github.com/kangkyunghyun/LinKHU/issues/190)). 릴리스를 내면 자동으로 따라오므로 두 글이 그 일을 떠맡을 이유가 없어졌다.

## 순서

### 1. 무엇이 바뀌었는지 읽는다

```bash
VERSION=$(node -p "require('./src/manifest.json').version")
cat "docs/releases/v$VERSION.md"
```

버전은 `src/manifest.json`이 원본이다. 문구에 적는 번호는 여기서 가져온다.

### 2. 사용자 노출 변경만 고른다

**`### Internal` 섹션은 통째로 버린다.** 사용자가 화면에서 겪지 않는 변경이다.

`Features`와 `Fixes`에서도 화면에 드러나는 것만 남긴다. **3~5개.** 더 늘리면 아무것도 안 읽힌다. 릴리스 노트가 10줄이어도 사용자 눈에 보이는 사건은 보통 서너 개다.

기준은 하나다 — **사용자가 그 항목을 읽고 "그래서 내가 뭘 할 수 있는데"에 답할 수 있는가.**

| 릴리스 노트 원문 | 문구 |
|---|---|
| 색상을 디자인 토큰으로 일원화하고 주색을 역할별로 분리 | 버린다. 화면에서 겪는 일이 아니다 |
| 다크 테마 아이콘 생성 스크립트 추가 | 버린다. 결과는 "다크에서 또렷하게 보인다"로 이미 다른 줄에 있다 |
| 시스템·라이트·다크 3단계 테마 추가 | 남긴다. 사용자가 누를 버튼이 생겼다 |

### 3. 계속 알릴 기능을 기능 목록에 넣는다

**계속 알릴 기능은 두 글의 기능 목록에 바로 넣는다.** 두 글 모두 변경 목록이 없으므로 기능 목록의 한 줄이 그 기능을 알릴 **유일한** 자리다. 이 단계를 건너뛰면 기능이 아무 데도 안 남는다 — 예를 들어 문의하기가 생겼는데 스토어 설명에 한 줄도 없는 채로 남는다.

고친 것(Fixes)은 기능 목록에 넣지 않는다. 버전 노트와 홈페이지 업데이트 섹션이 맡는다.

**두 문서 모두에서 확인한다.** 다만 검색창 이동, Enter로 첫 결과 열기 같은 세부 조작은 넣지 않는다. 처음 보는 사람에게는 어느 사이트가 열리는지가 앞이고, 순서 변경·단축키는 한 줄이면 된다. 두 문서에서 하는 일이 이렇게 갈린다.

| | 스토어 글 | 커뮤니티 글 |
|---|---|---|
| 기능 목록에 넣기 | `[주요 기능]`·`[편의 기능]`에 넣는다 | **대괄호 제목 없는 기능 목록에 한 줄로 더한다** |

숫자가 박힌 문장(`[지원 사이트]`의 서비스 개수 등)도 이때 함께 본다. 두 문서에 모두 있다.

커뮤니티 글에는 출시 시점과 사용자 수도 있다. 처음 보는 독자가 "누가 쓰나", "금방 버려지지 않나"를 묻기 전에 답하는 문장이라 **릴리스마다 다시 센다** (MUST). 세는 법은 [`docs/copy/1-2-COMMUNITY-POST.md`](../../../docs/copy/1-2-COMMUNITY-POST.md) 1-2-2의 표가 원본이다. 공개 페이지에서 누구나 확인할 수 있는 값만 쓴다. 따지는 사람이 직접 열어 봐도 맞아야 한다.

### 4. 사용자 문장으로 고쳐 쓴다

- **내부 용어를 쓰지 않는다.** 디자인 토큰, 생성 스크립트, 워크플로우, 리팩터링, 스펙, 검증 — 전부 사용자 어휘가 아니다.
- **동작으로 쓴다.** "테마 토글 컴포넌트 추가"가 아니라 "헤더의 버튼으로 시스템/라이트/다크를 바꿀 수 있습니다".
- **고친 것은 증상으로 쓴다.** "이랬던 문제가 없어졌습니다"가 "안정성을 개선했습니다"보다 짧고 정확하다.
- **없는 기능을 만들지 않는다.** 릴리스 노트에 없는 항목은 쓰지 않는다. 여기서 지어낸 문장이 스토어 심사와 사용자 기대에 그대로 남는다.
- **버전 번호를 손으로 세지 않는다.** 1단계의 `$VERSION`을 쓴다.

### 5. 두 문서를 갱신한다

- `docs/copy/1-1-STORE-LISTING.md` — **버전별 변경 목록을 넣지 않는다** (MUST). 3단계에서 고른 기능과 서비스 개수만 고친다. 바뀐 게 없으면 문서도 대시보드도 건드리지 않는다. 바뀌었으면 [스펙 §7-6](../../../docs/spec/7-6-STORE.md)에 따라 세 대시보드 설명에 붙여 넣는다.
- `docs/copy/1-2-COMMUNITY-POST.md` — **버전별 변경 목록을 넣지 않는다** (MUST). 3단계에서 고른 "계속 알릴 기능"만 기능 목록에 한 줄로 더하고, 대괄호 섹션 제목을 새로 만들지 않는다. 그럴 것이 없어도 **사용 지표는 다시 센다.** 제목과 맺음말은 그대로 둔다.
  설치 안내는 브라우저별 스토어 링크 세 개와 홈페이지 링크(`https://kangkyunghyun.github.io/LinKHU/?utm_source=everytime`)를 함께 둔다.
  PC에서 읽는 사람은 홈페이지를 거치지 않고 바로 설치해야 한다(이슈 [#253](https://github.com/kangkyunghyun/LinKHU/issues/253)).
  커뮤니티 유입의 상당수는 확장을 설치할 수 없는 모바일 인앱 브라우저라, 홈페이지 링크는 그 방문자에게 PC 설치 경로를 안내하는 몫으로 남긴다.

### 6. 검증한다

**두 글 모두 버전을 말하지 않는다.** 버전 표기가 있으면 그것이 실수다.

```bash
# 게시되는 글에 버전 표기가 새어 들어갔는가 (0줄이어야 한다)
sed -n '/^```text$/,/^```$/p' docs/copy/1-1-STORE-LISTING.md docs/copy/1-2-COMMUNITY-POST.md | grep -nE "v[0-9]+\.[0-9]+\.[0-9]+"

# 게시되는 글에 내부 용어가 새어 나갔는가 (0줄이어야 한다). 갱신 절차의 설명은 검사하지 않는다
sed -n '/^```text$/,/^```$/p' docs/copy/1-1-STORE-LISTING.md docs/copy/1-2-COMMUNITY-POST.md | grep -nE "토큰|리팩터|워크플로우|스크립트|스펙|커밋|검증 추가"

# 커뮤니티 글에 스토어 문법이 들어갔는가 (0줄이어야 한다)
sed -n '/^본문:/,/^```$/p' docs/copy/1-2-COMMUNITY-POST.md | grep -nE "^\["
```

버전 검사는 버전이 있으면 실패하는 쪽으로 둔다. 새 버전이 있는지 세는 검사는 0이 정상이 되면 "빠뜨린 것"과 구분되지 않는다.

내부 용어 검사는 두 문서에 그대로 적용된다. 검사 대상은 게시되는 `text` 블록뿐이다. 갱신 절차는 메인테이너가 읽는 설명이라 스펙 링크가 들어간다.

사용자 수는 명령으로 맞출 수 없다. Chrome, Whale, Firefox 스토어 페이지를 열어 세 값을 더한다.

그리고 **릴리스 노트와 나란히 놓고 읽는다.** 지어낸 항목이 있는지는 명령으로 안 잡힌다.

## 하지 말 것

- **`### Internal`을 요약해서 넣지 않는다.** 요약해도 사용자에게는 여전히 남의 일이다.
- **모든 항목을 넣지 않는다.** 목록이 길수록 새 기능이 묻힌다.
- **문서를 새로 쓰지 않는다.** 두 원본은 릴리스마다 제자리에서 고친다. 매번 새로 지으면 말투와 링크가 판마다 갈라진다.
- **두 글 모두 변경 목록을 넣지 않는다.** 커뮤니티 글은 읽는 사람이 이전 버전을 모르고, 스토어 글은 릴리스마다 손으로 붙여 넣다 빠뜨린다. 변경 이력은 홈페이지의 업데이트 섹션이 맡는다. 이유는 위 표 아래에 있다.
- **커뮤니티 글에서 홈페이지 링크를 빼지 않는다.** 스토어 링크만 두면 휴대폰 독자가 설치 경로를 잃는다. 이유는 5단계에 있다.
- **커뮤니티 글에 스토어 글의 기능 목록을 그대로 옮기지 않는다.** 대괄호 섹션 제목과 세부 조작 설명이 들어가는 순간 광고글이 된다. 이유는 위 표 아래에 있다.
- **스토어 대시보드에 붙여넣는 것까지 대신하지 않는다.** 문서를 갱신하는 데서 끝내고, 붙여넣기는 [스펙 §7-6](../../../docs/spec/7-6-STORE.md)을 따라 사람이 한다.
