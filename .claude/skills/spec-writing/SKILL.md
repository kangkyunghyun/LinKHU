# 스펙 문장 규칙

스펙은 사람이 설계하고 리뷰한 뒤 에이전트에게 그대로 건네는 지시문이다. 자연어로 쓴 엔지니어링 지식이므로 사람과 에이전트 모두에게 읽기 편해야 하고, 읽고 나면 구현이 어떻게 될지 쉽게 상상되어야 한다. 성공 기준은 그것 하나다.

층위 번호, 문서별 책임, 코드와 스펙의 대응, 주제별 원본은 [`docs/spec/README.md`](../../../docs/spec/README.md)가 정한다. 이 스킬은 그 위에서 **한 문서 안의 내용과 문장**만 다룬다.

## 넣는 것

- **지금 동작하는 코드의 설명.** 무엇을 왜 정했는지와 그 결과값. 결과값은 "적당한 여백"이 아니라 `20px`처럼 확인할 수 있는 값이다.
- **결정의 이유.** 규칙만 있으면 읽는 사람이 의도를 모른다. 왜 그 값이고 왜 그 순서인지 한 줄이면 된다. 한 줄로 답할 수 없으면 아직 정한 것이 아니다.
- **예시 값.** 필드명만 나열하지 않는다. 계약 문서의 요청과 응답, 데이터 스키마는 실제 값을 채운 예시를 함께 둔다. 예시가 없으면 에이전트가 추측한다.
- **필수와 선택의 구분.** 채워야 하는 값과 비어도 되는 값을 표에서 가른다.
- **없으면 없다고 쓴다.** 관측 수단이 없으면 "없다", 설정 페이지에 폴백이 없으면 "없다"라고 적는다. 빈 자리를 채우려고 지어내지 않는다.
- **"안 한다"는 못 박을 때만.** 에이전트가 자꾸 제안하는 방향(ES 모듈 전환, 탭 권한 추가, 번들러 도입)은 "하지 않는다"로 명시한다. 그 밖의 규칙은 "하지 마라"가 아니라 "이럴 때는 이렇게 한다"로 쓴다.
- **화면은 스크린샷으로.** 치수와 배치를 글로 적고, 실제 모습은 4-7의 이미지를 싣는다.

## 넣지 않는 것

- **지나간 것.** "이전 스펙은", "정정", "폐기한다", "선행 작업", "옮기는 과정에서"처럼 지금에 이르기까지의 이력. 대안을 놓고 고른 것이면 `DECISIONS.md`에 한 줄 덧붙이고 스펙에는 결과만 남긴다. 나머지는 커밋이 갖는다.
- **미정과 계획.** "검토 중", "후속 과제", "열려 있는 개선 항목", "나중에". 결정되면 그때 들어온다. 결정 안 된 것을 적어 두면 사람도 에이전트도 무엇을 따라야 할지 모른다.
- **일기.** 무엇을 고민했고 무엇이 잘 안 됐는지. 이슈 번호와 PR 회고도 스펙에 남기지 않는다.
- **다른 층이 이미 정한 것.** 계약의 필드를 구현 문서에서 반복하지 않고, 카테고리 목록을 레이아웃 문서에서 반복하지 않는다. 번호로 가리킨다.
- **손으로 센 숫자.** 서비스 수, 테스트 개수처럼 데이터나 코드에서 계산되는 값은 그 값을 정하는 문서 한 곳(서비스 수는 3-2)에만 적는다. 다른 문서는 "3-2가 정한다"로 가리킨다. 운영 기준은 개수가 아니라 상한과 하한으로 적는다. "91개 통과"가 아니라 "실패 0"이다.
- **코드 옮겨 적기.** CSS 속성, 함수 시그니처, 프롬프트 전문. 무엇을 언제 어떤 수준으로 쓰는지를 적고, 코드는 파일명으로 가리킨다.
- **프런트매터와 메타 표.** 작성자, 버전, 수정일은 커밋이 갖는다.
- **억지로 채운 절.** 형식을 맞추려고 해당 없는 절을 만들지 않는다. 길면 리뷰하기 힘들고, 리뷰하기 힘든 스펙은 아무도 읽지 않는다.

## 문장

- '한다'체로 쓰고 주체, 조건, 동작을 분명히 한다. "적절히 처리한다"처럼 해석을 독자에게 넘기지 않는다.
- `MUST`, `SHOULD`를 붙이지 않는다. "~한다"는 지키는 것이고 "~해도 된다"는 재량이다.
- em dash(—)와 원문자(①)를 쓰지 않는다. 가운뎃점(·)은 `학사·포털` 같은 고유 식별자에만 남기고 산문에서는 쉼표나 와/과로 쓴다.
- 구획선(`---`)을 쓰지 않는다. 제목과 문단 간격으로 나눈다.
- 다른 문서는 `3-2`, `4-2-2`처럼 번호로 가리킨다. 번호가 이미 주소이므로 본문끼리 링크하지 않는다. 링크는 README와 DECISIONS만 건다.
- 표는 항목을 대조할 때, 체크리스트는 누락이나 완료를 확인할 때 쓴다. 규칙에 이유가 붙으면 `규칙 | 왜` 두 열로 둔다. 영역 배치는 선으로 그린 상자가 아니라 표로 적는다.
- 순서가 있는 흐름은 mermaid로 그린다. 그림 속 용어는 1-6 공통 용어와 같아야 한다.
- 불필요한 접속사와 번역체를 줄인다. 첫째, 둘째로 기계적으로 나열하지 않고, 이미 말한 결론을 절 끝에서 다시 요약하지 않는다.
- 코드, 식별자, 외부 파일명, 직접 인용은 원문을 유지한다. 표현 규칙을 적용하려고 실제 식별자를 바꾸지 않는다.

## 피할 표현

| 피할 표현 | 대신 |
| --- | --- |
| 정본, 단일 진실 공급원, SSOT | 기준, 원본, 단일 소스, "~가 정한다" |
| 박다("값을 박는다") | 넣다, 정하다, 고정하다, 하드코딩하다 |
| 간극 | 차이, 어긋남 |
| 표류 | 어긋남, 불일치 |
| 발화하다(이벤트) | 보내다, 호출하다, 발생시키다 |
| 승격하다 | 옮기다, 토큰으로 올리다 |
| 담보하다 | 보장하다, 책임지다 |
| 동봉하다 | 함께 싣다, 포함하다 |
| "~가 소유한다"(문서·층의 역할) | "~가 정한다", "~가 관리한다" |
| 직교, 직교 분리 | 역할이 겹치지 않게, 서로 독립 |
| 마찰("진입 마찰") | 번거로움, 진입 장벽 |
| 표면화하다 | 드러나다 |
| 수렴하다("502로 수렴") | "결국 ~로 끝난다" |
| 테스트가 "~를 고정한다" | 검증한다, 깨지면 잡히게 한다 |
| 축("세 가지 축") | 관점, 기준, 갈래 |
| 배선하다 | 연결하다, 이어 붙이다 |
| 여정 | 과정, 경험 |
| 견고한 | 안정적인, 오류에 강한 |
| 원활한, 매끄러운 | 자연스러운, 끊김 없는 |
| 활용하다의 반복 | 쓰다, 사용하다 |
| 영역("~의 영역에서") | 분야, 쪽, "~에서" (화면의 구역을 뜻할 때는 그대로 둔다) |
| 강조하다, 부각하다 | "~이 중요하다", "~에서 ~이 드러난다" |
| 전략적으로 | 구체적으로 무엇을 할지 쓰기 |
| 정렬하다("목표와 정렬") | 맞추다, 일치시키다 |
| "~를 통해"의 반복 | "~로", "~해서" |
| "~에 있어서" | "~에서" |
| 이러한, 이처럼의 반복 | 생략하거나 구체 명사로 |
| 결론적으로, 종합하면 | 결정을 바로 쓰기 |
| "단순한 X가 아니라 Y다" | Y를 바로 설명하기 |
| "~로서 기능하다", "~를 나타내다" | "~이다" |
| 가지고 있다 | 있다 |
| "~되어진다" | "~된다" |
| 근본적으로, 놀랍게도, 확실히 | 삭제하거나 근거 제시 |
| 품질("품질 기준") | 무엇의 어떤 값인지 쓰기 (대비, 응답 시간, 통과 개수) |

## PR 전 점검

스펙을 고친 PR을 올리기 전에 아래를 돌리고 결과를 PR 본문에 적는다.

```bash
# 이력·미정 문구
grep -n '이전 스펙\|정정\|폐기한다\|선행 작업\|열려 있는 개선\|후속 과제\|검토 중\|나중에' docs/spec/*.md
# 피할 표현
grep -n '정본\|SSOT\|단일 진실\|박아\|박는\|간극\|발화\|승격\|담보\|동봉\|직교\|표류' docs/spec/*.md
# 손으로 센 숫자 (3-2 밖의 서비스 수)
grep -n '16[0-9]개\|1[0-9][0-9]쌍' docs/spec/*.md | grep -v '^docs/spec/3-'
# 공백 오류
git diff --check
```

그리고 사람이 본다.

- 위 층부터 읽는다. 아래를 고치려다 위를 고쳐야 한다면 위가 틀린 것이다.
- 코드를 열어 스펙의 값과 대조한다. 숫자, 파일명, 토큰 이름, 명령 순서.
- 같은 사실이 두 곳에 있으면 원본 한 곳만 남기고 나머지는 번호로 가리킨다.
- 다른 설계를 놓고 고른 것이 있으면 `DECISIONS.md` 맨 아래에 날짜순으로 한 줄 덧붙인다.
- 문서를 직접 읽는다. 에이전트에게 요약시켜 머지하지 않는다.
