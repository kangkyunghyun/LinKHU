# 결정 기록

LinKHU가 "왜 이렇게 되어 있는가"를 남긴다. 코드를 읽으면 무엇을 했는지는 알 수 있지만, 무엇을 **하지 않기로 했는지**는 알 수 없다. 그 부분이 여기 있다. 기록의 목적은 같은 논쟁을 반복하지 않는 것이다.

이 파일은 **스펙이 아니라 로그다.** 번호가 붙은 스펙 문서(`1`~`7`)는 현재 동작을 설명하며 코드와 함께 갱신되지만, 여기는 결정 시점의 기록이라 뒤에 덧붙이기만 한다. 스펙과 어긋나면 스펙이 현재다.

## 쓰는 규칙

1. **쓴 뒤 고치지 않는다**. 결정이 바뀌면 새 번호로 항목을 추가하고, 옛 항목의 `상태`만 `N-M으로 대체됨`으로 바꾼다. 본문은 그대로 둔다. 당시 배경이 남아 있어야 "왜 그때는 그랬는지"를 나중에 읽을 수 있다.
2. 설계 방향을 바꾸는 판단(무엇을 채택했고 무엇을 거부했는지)은 구현 PR과 같은 PR에서 남긴다.
3. 각 항목은 **날짜·상태·배경·대안·채택·영향**으로 적는다. 대안에는 거부한 것도 이유와 함께 적는다.
4. 번호는 주제 계층이다. 1 구성과 기술, 2 데이터와 제품, 3 릴리스와 플랫폼, 4 디자인, 5 랜딩과 기여, 6 문서와 작업 방식. 같은 계층의 마지막 번호 + 1을 쓴다.
5. 항목이 과하게 쌓이면 압축한다. 압축은 항목을 지우는 것이 아니라 본문을 줄이는 것이며, 번호와 결정 자체는 남긴다.
6. 스펙 문서에서 이 파일을 가리킬 때는 앵커를 쓴다 — `DECISIONS.md#d-3-4`.

## 1-1 빌드리스 정적 구성

**2026-07-30 · 채택**

**배경** — LinKHU는 화면 3개, 스크립트 6개 규모의 확장 프로그램이다. 상태 관리라 할 만한 것은 `chrome.storage.local`의 키 몇 개뿐이고, 서버가 없다. 주 기여자는 소수이고 기여자는 학생인 경우가 많다.

**대안** — 1) Vite + TypeScript + 번들러 2) 프레임워크(React 등) 도입 3) 빌드리스 정적 파일.

**채택** — 3번. `src/`의 파일이 그대로 확장 프로그램이 된다. 스크립트는 전역 객체를 노출하고 HTML의 `<script>` 순서로 결합한다.

**영향**
- `src/`를 그대로 브라우저에 로드해 개발한다. 빌드 감시나 소스맵이 필요 없다. 패키징도 `src/` 하위를 ZIP으로 묶으면 끝이라 새 파일을 추가해도 빌드 설정을 고칠 필요가 없다.
- 런타임·개발 의존성이 모두 없다. `npm install`할 것이 없고 공급망 위험이 사실상 없다.
- 이 원칙은 개발 도구까지 적용된다. 테스트는 Node 내장 러너와 가벼운 브라우저 API 모킹을 쓰고, ZIP 패키징도 압축 라이브러리 없이 만든다. 랜딩은 웹폰트를 불러오지 않는다.
- 같은 이유로 ESLint 도입은 보류 상태다. 금지는 아니며, 도입 이득이 이 원칙을 깰 만큼 큰지 판단해야 하는 사안으로 남겨둔다.
- 대가로 타입 검사가 없다. 대신 검증을 스크립트와 테스트로 옮겼다 ([6-2](6-2-DATA.md), [7-2](7-2-TEST-CASES.md)).
- 대가로 파일 공유가 안 되는 경계가 생긴다. 확장과 랜딩이 검색 규칙을 각자 구현하고 테스트로 일치를 강제하는 구조가 이 결정의 직접적 결과다.
- 뒤집으려면 "빌드 도입으로 줄어드는 비용이 도입·유지 비용보다 크다"를 보여야 한다. 화면이나 상태가 크게 늘어나는 시점이 재검토 지점이다.

## 1-2 Manifest V3 단일 소스 크로스브라우저

**2026-07-30 · 채택**

**배경** — Chrome, Firefox, Whale 세 스토어에 배포한다. Chrome과 Whale은 Chromium 기반이라 사실상 같지만, Firefox는 확장 API 구현과 심사 요구사항이 다르다.

**대안** — 1) 브라우저별로 매니페스트와 소스를 분기 2) 단일 MV3 매니페스트 + Firefox 전용 필드 3) Firefox 지원 포기.

**채택** — 2번. 매니페스트 하나를 유지하고, Firefox에만 필요한 설정은 `browser_specific_settings.gecko`에 담는다. Firefox가 무시하지 못하는 값(`strict_min_version` 140.0, `data_collection_permissions.required: ["none"]`)을 여기에 선언한다.

**영향**
- 패키지가 하나다. 같은 ZIP을 세 스토어에 제출한다.
- 대가로 가장 제약이 강한 브라우저에 맞춰야 한다. Firefox가 지원하지 않는 API는 Chrome 전용이라도 쓰지 않는다.
- 매니페스트를 바꾸면 세 브라우저 호환성을 모두 확인해야 한다 ([2-2](2-2-OPERATOR-REQUIREMENTS.md)).
- `data_collection_permissions`를 `none`으로 선언했으므로, 사용자 데이터를 수집하는 기능을 추가하면 이 선언과 Firefox 심사 답변을 함께 바꿔야 한다.

## 1-3 최소 권한

**2026-07-30 · 채택**

**배경** — 확장 프로그램의 권한 요청은 설치 시 사용자에게 그대로 노출된다. 교내 서비스 바로가기라는 성격상, 넓은 권한을 요구하면 "이 확장이 내 학사 정보를 보는 것 아닌가"라는 의심을 살 수 있다.

**대안** — 1) `tabs` 권한 요청 2) `<all_urls>` 호스트 권한으로 교내 사이트와 상호작용(자동 로그인, 콘텐츠 삽입) 3) 최소 권한.

**채택** — 3번. 요청 권한은 `storage` 하나이고, 호스트 권한은 GitHub 릴리스 조회 API **단 하나의 URL**로 좁혔다.

```text
permissions:       ["storage"]
host_permissions:  ["https://api.github.com/repos/kangkyunghyun/LinKHU/releases/latest"]
```

`chrome.tabs.create`와 `chrome.tabs.update`는 `tabs` 권한 없이도 동작하므로 요청하지 않는다.

**영향**
- 설치 시 노출되는 권한 경고가 최소화된다. 심사 대응도 단순하다.
- 대가로 자동 로그인, 교내 사이트 콘텐츠 읽기·주입, 열린 탭 목록 기반 기능은 불가능하다. [1-BACKGROUND](1-BACKGROUND.md)의 "하지 않는 것"과 일치한다.
- 권한을 새로 추가하는 변경은 기능 판단이 아니라 **제품 정체성 판단**으로 다룬다. 세 스토어 재심사와 기존 사용자 권한 재승인을 유발한다.
- 텔레메트리를 두지 않는 것도 이 결정의 연장이다. **관측 레이어 문서를 만들지 않는 근거다.**

<a id="d-1-4"></a>
## 1-4 ES 모듈로 전환하지 않음

**2026-07-30 · 채택**

**배경** — `src/`의 스크립트는 모두 classic script다. 전역 객체를 노출하고 HTML의 `<script>` 순서로 결합한다. 현대적인 방식은 ES 모듈이다.

**대안** — 1) ES 모듈로 전환하고 `type="module"`로 로드 2) classic script 유지.

**채택** — 2번. 이유는 **검증 도구가 이 구조에 묶여 있기 때문**이다. `scripts/validate-data.js`와 테스트 하네스는 `src/`의 파일을 Node의 `vm`으로 평가해 전역을 꺼내 쓴다. ES 모듈로 바꾸면 이 로딩 방식이 통째로 성립하지 않아 검증 스크립트와 테스트를 함께 재작성해야 한다.

**영향**
- 스크립트 로드 순서가 곧 의존 관계다. 순서를 바꾸면 깨진다 ([4-3](4-3-SOFTWARE-ARCHITECTURE.md)).
- 전역 이름이 충돌하지 않도록 각 파일이 객체 하나만 노출한다. Node 테스트에서 쓰려면 `module.exports` 가드가 필요하다.
- 뒤집으려면 검증 스크립트와 테스트 하네스의 재작성 계획이 함께 나와야 한다.

## 1-5 문의 채널로 Google Forms 선택

**2026-07-30 · 채택**

**배경** — 사용자 의견을 받을 경로가 필요했다. GitHub 이슈만으로는 계정이 없는 학생을 놓친다. 결정을 지배한 제약은 하나다. **확장 프로그램은 소스가 공개된다.** 따라서 **어떤 비밀 키도 확장 안에 숨길 수 없다.**

**대안** — 1) 자체 백엔드 API — 서버 운영 비용과 인증 키 보관 문제 2) 서드파티 폼 SaaS의 API 키 방식 — 키가 노출되면 폼이 오남용된다 3) Google Forms `formResponse` 직접 POST.

**채택** — 3번. 이 주소와 필드 id는 **공개돼도 안전한 값**이다. 노출되어도 남이 할 수 있는 일은 폼에 응답을 넣는 것뿐이고, 그건 원래 누구나 할 수 있다. 답변용 이메일은 Forms의 내장 "이메일 수집"을 쓰지 않고 선택 단답형 질문으로 받는다 — 내장 기능은 로그인을 강제해 익명 백그라운드 전송이 깨지기 때문이다.

**영향**
- 서버가 없다. 운영 비용이 0이고 개인정보를 직접 보관하지 않는다.
- 확장에 비밀값을 두지 않는다는 원칙이 유지된다. 새 외부 연동에도 같은 기준을 적용한다 — **비밀 키가 필요한 방식은 채택할 수 없다.**
- 대가로 전송 성공을 확인할 수 없다. CORS 제약 때문에 "네트워크 오류 없음 = 성공"으로 간주한다 ([5](5-CONTRACT.md)).
- 확장과 랜딩이 같은 폼·같은 필드를 쓰는지는 테스트로 고정한다.

## 2-1 imgSrc 명시 경로 유지

**2026-07-30 · 채택**

**배경** — `MASTER_SITE_LIST`의 항목이 모두 `imgSrc`를 직접 적는다. 값은 대부분 `images/{카테고리}/{id}.png` 꼴이라, 규칙에서 유도해 필드를 없앨 수 있어 보인다.

**대안** — 1) `imgSrc`를 없애고 `category`와 `id`로 경로를 계산 2) 명시 경로 유지.

**채택** — 2번. 규칙이 항상 성립하지 않는다. 전용 도안이 없는 서비스가 다른 서비스의 아이콘을 공유하는 경우가 있어, 규칙으로 유도하면 예외 처리가 다시 필요하다. **예외가 있는 규칙은 규칙이 아니다.** 명시 경로는 검증 스크립트와도 잘 맞는다 — 값이 그대로 파일 경로이므로 존재 확인, `src/` 이탈 검사, 미사용 이미지 탐지를 모두 문자열 비교로 처리할 수 있다.

**영향**
- 항목마다 한 줄이 더 길다. 대신 데이터만 보고 어떤 아이콘을 쓰는지 알 수 있다.
- 아이콘 공유가 자연스럽게 표현된다. `imgSrc`에 중복 제약을 두지 않는 근거다.
- 파일명을 `id`와 맞추는 것은 권장이지 강제가 아니다.

<a id="d-2-2"></a>
## 2-2 검색 랭킹을 확장과 랜딩에서 통일

**2026-07-30 · 채택**

**배경** — 랜딩과 팝업이 각자 검색을 구현하면서 정렬 규칙이 달랐다. 팝업에서 검색 후 `Enter`를 누르면 첫 결과가 열리는데, 랭킹이 다르면 **같은 검색어에 다른 서비스가 열린다.**

**대안** — 1) 각 화면이 자기 맥락에 맞는 랭킹을 쓴다 2) 랜딩의 이름 접두 우선 랭킹을 팝업에도 적용 3) 공통 모듈로 추출. 3번은 파일 공유가 불가능해([5-1](#d-5-1)) 선택지가 아니었다.

**채택** — 2번. 이름 접두 일치를 최우선으로 하는 랭킹으로 통일했다. 사용자가 이름 앞부분을 입력하는 것이 가장 흔한 검색 방식이므로, 그 경우 첫 결과가 정확해야 `Enter` 동작을 신뢰할 수 있다.

**영향**
- 두 구현이 존재하되 결과가 같아야 한다. 이 일치를 테스트가 강제한다 ([7-2](7-2-TEST-CASES.md)).
- 랭킹 규칙을 바꿀 때는 양쪽을 함께 바꾼다. 한쪽만 바꾸면 테스트가 실패한다.

<a id="d-2-3"></a>
## 2-3 학과 데이터 통합 정책

**2026-07-30 · 채택**

**배경** — 경희대학교의 공식 학과 수와 LinKHU의 `학과` 카테고리 항목 수가 다르다. 이 차이를 "데이터 누락"으로 오해하기 쉽다.

**대안** — 1) 공식 학과 목록을 그대로 옮겨 개수를 맞춘다 2) 독립 홈페이지가 있는 곳만 항목으로 둔다.

**채택** — 2번. **하위 학과·학부가 상위 단과대와 같은 홈페이지를 쓰면 단과대 항목만 유지하고, 독립 홈페이지가 있을 때만 하위 항목을 만든다.** LinKHU가 제공하는 것은 "학과 목록"이 아니라 "바로가기"다. 같은 주소로 가는 항목이 여러 개면 사용자에게는 선택지가 아니라 소음이다.

**영향**
- 목록 수와 공식 학과 수의 차이는 **정책의 결과이지 누락이 아니다**. 개수 불일치를 근거로 항목을 추가하지 않는다.
- 학과 추가 요청이 오면 먼저 확인할 것은 "독립 홈페이지가 있는가"다. 없으면 해당 단과대 항목으로 안내한다.

<a id="d-2-4"></a>
## 2-4 버저닝은 semver

**2026-07-30 · 채택**

**배경** — 확장 버전은 매니페스트에 적히고 스토어와 릴리스 노트에 노출된다. 어떤 변경에서 어느 자리를 올릴지 기준이 필요했다.

**대안** — 1) 릴리스마다 패치만 올린다 2) semver를 따른다.

**채택** — 2번. **사용자에게 보이는 새 기능이 들어가면 마이너를 올린다.** 버그 수정과 내부 정리만 있으면 패치를 올린다.

**영향**
- 사용자가 버전 숫자만 보고 변경 규모를 짐작할 수 있다.
- 노트에 새 기능이 있는데 패치라면 둘 중 하나가 잘못된 것이다.
- 매니페스트 버전은 `숫자.숫자.숫자` 형식이어야 하며, 릴리스 검증이 이를 확인한다.

<a id="d-3-1"></a>
## 3-1 업데이트 안내 링크 분기

**2026-07-30 · 채택**

**배경** — 새 버전이 나왔을 때 사용자를 어디로 보낼지는 **설치 경로에 따라 다르다.** 스토어 설치본 사용자를 GitHub 릴리스로 보내면 ZIP을 받아 수동 설치하라는 뜻이 되고, 개발 빌드 사용자를 스토어로 보내면 자기 설치본과 무관한 페이지를 보게 된다.

**대안** — 1) 항상 GitHub 릴리스로 안내 2) 항상 Chrome Web Store로 안내 3) 설치 경로와 브라우저를 판별해 분기.

**채택** — 3번. 두 단계로 판별한다. ① **스토어 설치본인가** — 매니페스트에 `update_url`이 있는지로 판단한다. 이 필드는 스토어 설치 시 브라우저가 주입하며 저장소의 매니페스트에는 없다. ② **어느 스토어인가** — userAgent로 Whale / Firefox / 그 외(Chrome)를 구분한다.

**영향**
- 사용자가 자기 설치 경로에 맞는 곳으로 간다.
- userAgent 판별은 취약하다. 틀려도 다른 스토어 페이지가 열릴 뿐 기능이 깨지지 않으므로 감수 가능한 수준으로 본다.
- 스토어가 늘거나 주소가 바뀌면 이 분기를 갱신해야 한다. 판별 실패는 기본값(GitHub 릴리스)으로 폴백한다.

<a id="d-3-2"></a>
## 3-2 릴리스 무결성 장치

**2026-07-30 · 채택**

**배경** — 릴리스는 사람이 여러 단계를 순서대로 밟는 작업이다. 어느 하나를 빠뜨리면 **잘못된 산출물이 스토어로 나간다.** 배포된 뒤에는 되돌리기 어렵다.

**대안** — 1) 체크리스트 문서로 사람이 확인 2) 자동 검증으로 막는다 (문서와 병행).

**채택** — 2번. 릴리스 경로에 세 가지 장치를 뒀다.

| 장치 | 막는 실수 |
| --- | --- |
| 태그와 매니페스트 버전 대조 | 버전을 올리지 않고 태그만 미는 것 |
| 릴리스 노트 존재 확인 | 노트 없이 릴리스가 나가는 것 |
| 재현 가능한 패키징 | 같은 커밋에서 다른 ZIP이 나오는 것 |

패키징은 파일 타임스탬프를 고정값으로 기록한다. **같은 소스에서 항상 같은 바이트의 ZIP이 나온다.**

**영향**
- 릴리스 실수가 배포 전에 워크플로에서 막힌다.
- 재현 가능성은 테스트로 고정되어 있다 ([7-2](7-2-TEST-CASES.md)).
- 대가로 ZIP의 파일 시각이 1980년으로 보인다. 심사와 동작에 영향이 없어 감수한다.

<a id="d-3-3"></a>
## 3-3 단축키는 강제하지 않고 안내한다

**2026-07-30 · 채택**

**배경** — 팝업을 여는 단축키를 매니페스트에 등록해 뒀지만, 사용자 환경에서 그 조합이 비어 있는 경우가 있다. **플랫폼 제약이 결정을 강제한다.** 매니페스트의 단축키는 설치 시점의 제안일 뿐이고, 확장은 이미 점유된 조합을 빼앗을 수 없다. Chrome과 Whale은 확장이 단축키를 프로그래밍 방식으로 바꾸는 것 자체를 허용하지 않는다.

**대안** — 1) 다른 조합을 자동으로 시도 — Chrome·Whale에서 불가능 2) 단축키 기능을 포기 3) 등록 실패를 감지해 사용자에게 안내.

**채택** — 3번. 설정 페이지가 등록 여부를 확인하고 **비어 있을 때만** 안내를 노출한다. 브라우저 내부 주소는 링크로 직접 이동시킬 수 없는 경우가 있어, 이동에 실패하면 주소를 클립보드에 복사하도록 안내한다.

**영향**
- 단축키가 동작하지 않는 사용자가 원인과 해결 방법을 알 수 있다.
- 이 제약은 확장 코드로 해결할 수 없다. "단축키가 안 눌린다"는 제보에는 **먼저 브라우저의 단축키 설정을 확인하도록 안내한다**.

<a id="d-3-4"></a>
## 3-4 단축키 안내를 팝업까지 올리고 주소를 규칙으로 안내한다

**2026-09-13 · 채택 · 이슈 [#209](https://github.com/kangkyunghyun/LinKHU/issues/209)**

**배경** — Aside에서 제안 단축키가 비밀번호 자동입력과 충돌해 등록되지 않았다는 문의가 있었다. 설정 페이지의 접힌 안내와 Chrome·Whale·Firefox만 나열한 문구로는 사용자가 자신의 브라우저에서 지정하는 방법을 찾기 어려웠다. [3-3](#d-3-3)의 "강제하지 않고 감지해 안내한다"는 그대로 유효하고, 이 결정은 그 원칙 안에서 안내의 노출 지점과 문구 방식을 넓힌다.

**대안** — 1) 브라우저별 단축키 제공 — 브라우저별 `suggested_key`를 따로 지정할 수 없다 2) 기본 조합 변경 — 충돌은 브라우저마다 다르고 기존 사용자의 설정을 흔든다 3) 설정에만 접힌 안내 유지 — 팝업에서 문제를 발견한 사용자에게 닿지 않는다 4) 팝업에 한 줄 안내를 추가하고 설정에서 주소 규칙을 펼쳐 보여준다.

**채택** — 4번. 팝업은 `chrome.commands.getAll`로 등록 여부를 먼저 확인하고, 미등록이며 `shortcutNoticeDismissed`가 `true`가 아닐 때만 헤더 아래 안내를 표시한다. 닫기는 `shortcutNoticeDismissed=true`를 즉시 저장하고 화면에서 숨긴다. 저장 실패 시 배너를 복구하고 상태 줄로 실패를 알린다. 설정 안내는 접지 않고 미등록일 때만 표시하며, Chromium 기반 브라우저의 내부 주소와 `/extensions/shortcuts` 규칙을 설명하고 Chrome·Whale·Aside를 예로 든다. Firefox는 `about:addons` 경로를 별도로 제시한다.

**영향**
- 미등록 사용자는 팝업에서 설정 안내에 바로 도달한다. 등록된 사용자는 추가 배너를 보지 않는다.
- 저장 키가 하나 늘어나며 저장 실패를 알리고 화면을 되돌리는 계약을 따른다 ([4-4](4-4-STATE.md)).
- 닫기 선택은 지속된다. 기본 제안키와 권한은 바꾸지 않는다.

<a id="d-3-5"></a>
## 3-5 Whale Store는 수동 배포를 유지한다

**2026-09-22 · 채택**

**배경** — Chrome과 Firefox는 공개 API로 자동 배포하는데 Whale만 수동이다. 사람이 빠뜨리면 그대로 누락되므로 자동화 여지를 조사했다. Whale 개발자센터는 확장앱 구현 API와 배포 **절차**를 제공하지만, ZIP 업로드와 리뷰 요청을 자동화하는 **공개 API 문서를 제공하지 않는다.** Help Center의 등록 안내도 로그인 → 개발자 등록 → 패키지 업로드 → 필수 정보 입력 → 제출이라는 수동 순서를 설명한다. GitHub Actions에서 안전하게 쓸 수 있는 공식 인증 방식, API endpoint, CLI가 확인되지 않았다.

**대안** — 1) 비공식 브라우저 자동 조작 2) 세션 쿠키 재사용 3) 개발자 페이지 내부 요청 역공학 4) 수동 배포 유지.

**채택** — 4번. 앞의 셋은 **기본 운영 경로로 채택하지 않는다**. 로그인 세션과 UI 변경에 취약하고, 계정 보안과 약관 리스크를 만든다. 배포를 자동화해 얻는 편의보다 계정이 잠기거나 약관을 어길 위험이 크다.

**영향**
- Whale만 사람이 직접 올린다. 다른 두 스토어와 달리 **빠뜨리면 그대로 누락되므로** 배포 후 확인에서 별도로 본다 (§7-6-7).
- Whale만 Release에 첨부된 ZIP을 직접 내려받아 쓴다. 자동 배포 둘은 태그 시점 소스로 다시 빌드한다 (§7-6-2).
- **다음 중 하나가 확인되면 자동화를 다시 검토한다** — Whale 개발자센터나 Help Center에 공식 배포 API 문서가 공개되거나, 개발자 페이지가 API key·OAuth·service account 같은 자동화용 인증 수단을 제공하거나, Naver Whale 팀이 공식 CLI 또는 GitHub Actions 연동 방법을 문서화하는 경우다.

<a id="d-4-1"></a>
## 4-1 주색을 텍스트용과 채움용으로 분리

**2026-07-30 · 채택**

**배경** — 브랜드 색 토큰 하나(`--color-primary`)가 어두운 배경 위 텍스트와 버튼·패널의 채움 배경을 겸하고 있었다. 라이트에서는 문제가 없지만 **다크에서 두 역할의 요구가 정면으로 충돌한다.** 텍스트로 쓰려면 밝아야 하고, 채움으로 쓰려면 그 위 글자가 읽혀야 한다. 밝기를 올린 `#e08589`는 채도를 41%까지 잃어 **경희 레드가 아니라 분홍으로 보였다.**

**대안** — 1) 채도를 유지한 밝은 빨강 하나로 통일 — 채움 위 텍스트가 4.5:1을 넘기 어렵다 2) 채움 위 글자색만 테마별로 뒤집기 — 채도 문제는 그대로 3) 텍스트용과 채움용 토큰을 분리.

**채택** — 3번. **역할이 두 개면 토큰도 두 개다.**

| 토큰 | 역할 | 라이트 | 다크 |
| --- | --- | --- | --- |
| `--color-primary` | 텍스트·강조 | `#a40f16` | `#ff4d52` |
| `--color-primary-fill` | 채움 배경 | `#a40f16` | `#c4121b` |

**영향**
- **채도와 대비를 동시에 얻는다.** `--color-on-primary`가 두 테마 모두 흰색으로 단순해졌고, 랜딩의 브랜드 패널 예외가 사라졌다.
- 대가로 토큰이 하나 늘고 **쓰는 쪽이 역할을 판단해야 한다.** 배경으로 칠하면 `-fill`, 글자·테두리면 `--color-primary`다 ([4-2](4-2-UI-SYSTEM.md)).
- **어떤 색이 텍스트와 배경 양쪽에 쓰이기 시작하면 분리를 먼저 검토한다**.
- 곁가지로 다크 표면에서 색조를 뺐다. 주색이 이미 강한 빨강이라 표면까지 붉으면 대비가 아니라 얼룩으로 보인다. 표면·텍스트·테두리를 순수 중성으로 바꾸고 **색은 주색 계열만 담당하게** 했다.

## 4-2 서비스 아이콘을 테마별 두 벌로 나눔

**2026-07-30 · 채택 · 이슈 [#116](https://github.com/kangkyunghyun/LinKHU/issues/116)**

**배경** — 서비스 아이콘은 흰 배경에 검정 선화로 그려진 PNG였다. 다크 테마를 넣자 **어두운 카드 위에 흰 사각형이 떠 보였다.** 핵심 제약은 아이콘이 **래스터 자산**이라는 점이다. UI 아이콘은 SVG라 `currentColor`로 토큰을 상속받지만, 서비스 아이콘은 픽셀이므로 CSS 토큰이 닿지 않는다.

**대안** — 한 벌로 해결하려던 세 시도가 모두 실패했다.

| 시도 | 왜 실패했나 |
| --- | --- |
| 흰 타일 | 어두운 화면에서 **눈부시다.** 불투명도를 낮춰도 밝은 판이라는 성질은 그대로 |
| CSS 반전 | 빨강이 **분홍으로 바뀐다.** 반전은 밝기를 제어할 수단이 없다 |
| 공용 중간톤 | 두 테마의 요구가 반대다. 라이트 대비가 17:1에서 4.54:1로 떨어졌다 |

**채택** — **자산을 두 벌로 나눈다.** 라이트는 배경만 제거해 쓰고, 다크는 생성기가 `#a1a1aa`·`#d94a52` 두 색으로 다시 칠한다. 색을 옮길 때 **밝기를 곱하지 않고 알파로 옮긴다** — 목표색보다 밝은 픽셀이 원리적으로 생기지 않는다.

**영향**
- **자산이 2배가 된다.** PNG 총량이 작고 사람이 두 벌을 손으로 관리하지 않으므로 감당 가능한 대가로 봤다.
- **생성기가 스펙의 일부가 된다.** 다크 벌은 라이트 원본에서 재현되는 산출물이며 `npm run generate:dark-icons`로 등록했다.
- **짝이 깨질 수 있다.** `validate:dark-icons`를 `build`에 넣어 CI가 막는다.
- **랜딩은 확장과 다른 방법을 쓴다.** 확장은 저장된 테마 모드가 있어 JS가 경로를 바꾸지만, 랜딩은 `prefers-color-scheme`만 따르므로 `<picture>` + `<source media>`에 맡긴다.
- 라이트 벌의 "원본 도안 색 그대로"는 [4-3](#d-4-3)에서 폐기되었다. **두 벌로 나눈다는 이 결정 자체는 유효하다.**

## 4-3 아이콘 팔레트를 세 가지로 고정하고 전량 정합

**2026-07-30 · 채택 · 이슈 [#126](https://github.com/kangkyunghyun/LinKHU/issues/126)**

**배경** — 팝업 격자에서 **학과 아이콘이 유독 탁해 보인다**는 지적이 있었다. 카테고리별 구성을 재 보니 학과는 회색이 3분의 1이고 빨강은 다른 카테고리의 3분의 2였다. **회색의 정체는 색이 아니라 불투명도였다** — 원본의 반투명 픽셀이 흰 배경에 합성되면서 밝은 회색이 되었다.

**대안** — 채움 면 처리로 셋을 검토했다. 채움→빨강은 붉은색 비중이 과해지고, 채움→검정은 아이콘이 무거워져 빨강이 묻힌다.

**채택** — **라이트 벌의 팔레트를 브랜드 레드 `#a40f16`, 검정 `#1a1a1a`, 투명 세 가지로 고정하고 전량을 정합했다.** 채움은 비운다 — 선화 중심이 되어 24px에서도 형태가 유지되고 팔레트가 가장 단순해진다. "원본 유지"보다 **격자 안에서의 시각적 일관성**을 우선했다. 사용자는 아이콘 하나를 따로 보지 않고 격자로 함께 본다.

**영향**
- 회색 채움이 0픽셀이 되었고 카테고리 간 편차가 줄었다(붉은색 6.1pt→3.3pt, 회색 13.9pt→6.6pt).
- **도안은 보존된다.** 잉크 잔존 비율 최저 84.8%, 50% 미만 0개.
- **경계 안티에일리어싱은 건드리지 않았다.** "회색 채움 금지"는 **면**에 대한 규칙이다.
- 대가로 원본 도안의 색 의도가 사라졌다. 그래서 새로 그리는 아이콘은 SVG 원본을 남기도록 했다.
- 다크 벌은 영향이 없다. 생성기가 어차피 두 색으로 다시 칠한다.

## 5-2 PR #98 반려 — 랜딩 디자인 언어의 확장 이식 거부

**2026-07-30 · 채택**

**배경** — 외부 기여자가 3단계 테마 선택을 추가하는 [PR #98](https://github.com/kangkyunghyun/LinKHU/pull/98)을 제출했다. 구현 품질과 검증은 충실했다. 문제는 품질이 아니라 **방향**이었다 — 다크 테마의 시각 언어를 랜딩의 "따뜻한 배경과 밝은 핑크 강조색"에서 가져오도록 설계되어 있었다. 랜딩은 넓은 화면에서 스크롤하며 읽는 홍보 페이지이고, 확장 팝업은 320px 폭에서 즉시 목표를 달성해야 하는 도구다. 이 판단 기준이 당시 문서로 존재하지 않았다.

**대안** — 1) 그대로 병합 후 나중에 조정 2) 병합 후 후속 PR로 색만 교체 3) 반려하고 기존 UI를 유지하는 방향으로 재구현. 1·2번은 테마 전환 구조가 색 값과 강하게 얽혀 있어 "나중에 색만 바꾸기"가 실제로는 재구현에 가깝기 때문에 택하지 않았다.

**채택** — 3번. 반려 시 기여자에게 사유와 향후 계획을 남겼다.

**영향**
- **판단 기준이 문서화되었다.** [4-2 확장 우선 원칙](4-2-UI-SYSTEM.md)이 이 결정에서 나왔다.
- **다크 테마의 요구사항이 스펙으로 확정되었다.** 구현 PR은 그 스펙을 근거로 심사한다.
- 기능 성격의 이슈에는 **디자인 방향과 제약을 이슈 단계에서 명시해야 한다**.

- **경쟁 상태에 대한 당시 리뷰 판단은 틀렸다.** "`chrome.storage.local.set`은 순서대로 처리되므로 되돌리기만 필요하다"고 기록했으나, 쓰기 순서가 지켜져도 **콜백 도착 순서는 보장되지 않는다.** 늦게 도착한 실패 콜백이 성공한 최신 저장을 되돌리고, 늦게 도착한 읽기 결과가 사용자의 명시적 선택을 덮는다. 두 결함 모두 재현 테스트로 확인한 뒤 요청 번호 하나와 가드 두 줄로 고쳤다. 교훈은 "방어가 불필요했다"가 아니라 **"방어의 규모가 과했다"**다. **경쟁 상태는 테스트로 재현해 실재를 확인한 뒤 판단한다**.

## 5-3 랜딩 릴리스 노트를 런타임에 GitHub API로 받음

**2026-09-01 · 채택 · 이슈 [#190](https://github.com/kangkyunghyun/LinKHU/issues/190)**

**배경** — 릴리스 노트가 저장소와 GitHub Releases에만 있었다. 홈페이지로 온 학생은 무엇이 언제 바뀌었는지 볼 곳이 없고, 그 역할을 커뮤니티 홍보글이 떠맡아 **처음 보는 사람에게 변경 이력부터 들이미는** 상태였다.

**대안** — 1) 빌드 시점 생성 — 산출물이 하나 늘고 릴리스마다 재생성·검증이 필요하며, 빠뜨리면 홈페이지만 옛 내용으로 남는다 2) 런타임 fetch 3) 손으로 옮겨 적기 — 검토에서 제외.

**채택** — 2번. **릴리스를 내면 홈페이지가 저절로 따라온다.** 이것이 랜딩이 외부 API를 부르는 첫 사례라 네 가지를 함께 정했다.

1. **`### Internal`을 거른다**. 저장소 기록이지 사용자에게 보일 것이 아니다. Firefox 배포에서 이미 한 번 새어 나갔다. 거르는 규칙이 Node 스크립트와 브라우저에 두 벌로 있으므로, 실제 릴리스 노트 전부에 두 구현을 돌려 결과가 같은지 테스트로 고정한다.
2. **마크다운 파서를 넣지 않는다**. [1-1](#d-1-1)의 의존성 없음이 이유다. 릴리스 노트가 쓰는 문법은 `### 제목`, `- 불릿`, `` `코드` `` 셋뿐이다. 범위 밖 문법은 **글자 그대로 보인다.**
3. **본문은 신뢰 경계 밖이다**. `innerHTML`로 붙이지 않고 `createElement`와 `textContent`로만 조립한다.
4. **실패하면 섹션을 감춘다**. **빈 상자를 남기지 않는다.** 푸터의 GitHub Releases 링크가 대체 경로가 된다.

**영향**
- **캐시는 `sessionStorage`에 탭 세션 단위로 둔다.** 확장의 12시간 TTL을 옮기지 않았다. **학내망은 NAT로 IP를 공유하므로 rate limit이 집단으로 소진될 수 있다.**
- **최근 다섯 개만 그리고, 그중 최신 하나만 펼친다.** 개수 상한은 테스트가 고정한다 — 상한이 없으면 릴리스가 쌓이면서 조용히 되돌아간다.
- 변경 이력을 홈페이지가 맡으므로 **커뮤니티 홍보글은 소개에 집중한다**(이슈 [#192](https://github.com/kangkyunghyun/LinKHU/issues/192), [#196](https://github.com/kangkyunghyun/LinKHU/issues/196)).
- **이후 외부 호출을 추가할 때도 위 네 가지를 같은 기준으로 적용한다** ([5-4](5-CONTRACT.md)).

## 6-2 스펙 세트를 ai-spec 층위로 두고 문서 계층을 spec·DECISIONS로 줄인다

**2026-09-21 · 채택 · 이슈 [#213](https://github.com/kangkyunghyun/LinKHU/issues/213)**

**배경** — 2026-09-14 멘토링에서 실서비스의 스펙 세트 구조를 확인했다. 두 가지가 현재 구조와 어긋났다.

첫째, **번호가 층위여야 한다.** 위 문서가 바뀌면 아래를 전부 바꾸고, 아래 때문에 위가 바뀌면 그건 위쪽 문제다. 이 규칙이 문서에 없었고, `3-1`(아키텍처)과 `3-2`(UI 규칙)가 서로 다른 층위인데 같은 번호를 쓰고 있었다. 둘째, **한 문서는 한 역할만 한다.** `3-2-DESIGN-UI-RULES.md`가 742줄에 색상표·토큰·우선순위·다크테마·설정목록·카드이름 6개 역할을 담고 있었다.

[6-1](#d-6-1)이 예고한 재검토 조건도 충족됐다. `requirements/`는 6개, `design/`은 1개에서 멈췄고 실제로는 이슈 본문과 PR이 그 일을 하고 있었다.

**대안** — 1) 4계층 유지 + 번호 규칙만 명문화 — 스펙 안쪽의 역할 혼재가 남는다 2) fe-spec 뼈대를 따른다 — 프론트 제품에 맞지만, 원본은 ai-spec이고 나머지는 그것을 옮긴 것이라 층위가 덜 정돈되어 있다 3) ai-spec 층위로 맞추고 문서 계층을 `spec/`과 `DECISIONS.md`로 줄인다.

**채택** — 3번. LinKHU는 AI도 자체 서버도 없으므로 ai-spec의 각 자리를 확장 프로그램의 대응물로 옮겼다 — `3-TASK-DEFINITION`은 정보 구조로, `4-1-COGNITIVE`는 화면 관점 설계(레이아웃·UI 시스템)로, `4-2-SOFTWARE`는 개발자 관점 설계(아키텍처·상태)로, `6-1-EXECUTION`은 인터랙션 구현으로, `6-2-SOFTWARE-IMPL`은 데이터 구현으로 옮겼다. AI 정렬·평가(`6-3`~`6-6`)와 관측(`7-3`)은 대응물이 없어 만들지 않았고, 관측이 없는 근거는 [1-3](#d-1-3)이다.

`requirements/`와 `design/`은 제거한다. 요구사항은 스펙의 `2-1`·`2-2`가, 설계는 `4-x`가 계속 갱신하며 맡고, 이슈별 "이번에 만들 것"은 이슈 본문과 PR에 남는다. `adr/` 21개 파일은 이 파일 하나로 모은다 — 결정 기록은 스펙이라기보다 **로그**이고, 로그는 한 곳에 쌓여야 읽힌다.

**영향**
- 작업 시작 순서가 "이슈 → 브랜치"로 돌아간다. 완료 조건은 이슈 본문에 쓴다 ([`AGENTS.md`](../../AGENTS.md)).
- 스펙 문서를 고칠 때 **위 번호를 고쳤으면 아래를 전부 훑는다**. 아래 때문에 위를 고쳐야 한다면 그건 위쪽 설계가 틀렸다는 신호다.
- 결정을 링크할 때 파일 경로가 아니라 앵커(`DECISIONS.md#d-N-M`)를 쓴다.
- 옛 ADR 본문의 `docs/` 경로는 당시 랜딩 폴더를 뜻한다. 압축하면서 오해 소지가 있는 경로는 걷어냈다.
- 대가로 이 파일이 길어진다. 길이가 읽기를 막으면 §목록에서 찾아 들어가고, 그래도 부담이면 규칙 5에 따라 본문을 압축한다.
