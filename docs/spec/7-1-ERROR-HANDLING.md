# 7-1. 오류 처리

이 문서는 데이터 검증, 저장소, 네트워크, 자산 로딩이 실패했을 때 사용자와 메인테이너가 보는 동작과 문구를 정한다.

저장 키의 성격은 상태에, 바깥 호출의 계약은 계약에, 처리 순서는 인터랙션에 있다. ([4-5-2 사용자 설정과 내부 캐시](4-5-STATE.md#4-5-2-사용자-설정과-내부-캐시), [5 계약](5-CONTRACT.md), [6-1 인터랙션](6-1-INTERACTION.md))

<br>

## 7-1-1 공통 원칙

| 원칙 | 예 |
| --- | --- |
| 부분 실패가 전체 사용을 막지 않는다. 바로가기 열기가 제품의 본체이고 나머지는 부가 기능이다 | 버전 조회가 실패해도 바로가기는 열린다 |
| 사용자가 한 일의 실패는 알리고, 사용자가 하지 않은 일의 실패는 알리지 않는다 | 저장 실패는 알리고 캐시 기록 실패는 알리지 않는다 |
| 실패 문구는 다음에 무엇을 할 수 있는지까지 말한다 | "잠시 후 다시 시도해주세요." |

<br>

## 7-1-2 데이터 검증 실패

| 상황 | 동작 |
| --- | --- |
| `npm run validate:data`에 오류가 있음 | 오류와 경고를 나눠 출력하고 종료 코드를 0이 아닌 값으로 둔다 |
| 오류 메시지 | 어떤 서비스의 어떤 필드가 왜 잘못됐는지 서비스 `id`와 함께 보인다. `id`가 없으면 목록 안의 순번(`index N`)으로 보인다 |
| 랜딩 산출물이 낡음 | 해결 명령 `npm run generate:landing-data`를 메시지에 넣어 실패한다 |
| 다크 아이콘 짝이 맞지 않음 | 어긋난 파일 경로를 보이며 실패한다 |

<br>

## 7-1-3 저장소 실패

| 상황 | 동작 | 문구 |
| --- | --- | --- |
| 저장소 응답이 늦거나 오지 않음 | 헤더, 검색창, 푸터는 그대로 보이고 카드 격자만 빈다. 화면 전체를 저장소 응답 뒤에 숨기는 로딩 화면을 두지 않는다. 두려면 시간이 지나면 화면을 여는 안전장치를 함께 둔다 | |
| `userOrder`가 없음 | 기본 목록을 이름 가나다순으로 보인다 | |
| `userOrder`에 목록에 없는 id가 있음 | 그 id를 빼고 그린다 | |
| `userOrder`에 같은 id가 두 번 있음 | 한 번만 그린다 | |
| 설정 저장 성공 | 확인을 눌러야 닫히는 알림 창 | "성공적으로 저장되었습니다." |
| 설정 저장 실패 | 확인을 눌러야 닫히는 알림 창. 화면의 순서는 그대로 둔다 | "설정을 저장하지 못했습니다. 잠시 후 다시 시도해주세요." |
| 테마 저장 실패 | 화면과 토글을 마지막으로 저장이 확인된 모드로 되돌리고 상태 줄을 보인다. 확장과 랜딩이 같다 | "테마를 저장하지 못했습니다. 이전 설정으로 되돌렸습니다." |
| 단축키 안내 닫기 저장 실패 | 안내를 다시 보이고 상태 줄을 보인다. 다음 저장이 성공하면 상태 줄을 비운다 | "단축키 안내 숨김을 저장하지 못했습니다. 다시 시도해주세요." |
| 단축키 안내를 닫았는지 읽지 못함 | 안내를 보인다 | |
| 버전 캐시 쓰기 실패 | 알리지 않는다. 다음 조회에서 다시 쓴다 | |
| 랜딩의 변경 이력 캐시를 읽거나 쓸 수 없음 | 캐시가 없는 것으로 보고 다시 받는다. 알리지 않는다 | |

<br>

## 7-1-4 네트워크 실패

| 상황 | 동작 | 문구 |
| --- | --- | --- |
| 최신 버전 조회 실패, GitHub 오류 응답 | 콘솔에 기록하고 캐시된 버전으로 비교한다. 캐시가 없으면 업데이트 안내를 보이지 않는다 | |
| 랜딩 변경 이력 조회 실패, 응답 형식 오류, 게시된 릴리스 없음 | 업데이트 구역 전체를 숨긴다. 맨 아래 GitHub 릴리스 링크가 대신한다 | |
| 랜딩 서비스 목록을 불러오지 못함 | 검색 결과 자리에 실패를 알린다 | "서비스 목록을 불러오지 못했습니다." "페이지를 새로고침한 뒤 다시 시도해주세요." |
| 분석 스크립트를 불러오지 못함 | 이벤트를 보내지 않고 랜딩은 그대로 동작한다 | |

<br>

**1. 문의 전송**

문의 전송은 응답 본문을 읽을 수 없어 네트워크 오류가 없으면 성공으로 본다. 검증은 아래 순서로 하고, 막히면 요청을 보내지 않고 폼 아래 상태 문구로 알린다.

| 순서 | 상황 | 동작 | 문구 |
| --- | --- | --- | --- |
| 1 | 문의 유형을 고르지 않음 | 보내지 않음 | "문의 유형을 골라주세요." |
| 2 | 본문이 비었음 | 보내지 않음 | "문의 내용을 입력해주세요." |
| 3 | 이메일을 썼는데 `@`가 없음 | 보내지 않음 | "이메일 주소를 확인해주세요." |
| 4 | 확장에서 폼 주소나 본문 필드가 비어 있음 | 보내지 않음 | "문의 채널이 아직 준비되지 않았습니다. 잠시 후 다시 시도해주세요." |
| 5 | 보내는 중 | 보내기 버튼과 유형 칩을 누를 수 없음 | "전송 중..." |
| 6 | 성공으로 봄 | 본문을 비우고 유형 선택을 해제함. 이메일은 남김 | "전송되었습니다. 소중한 의견 감사합니다!" |
| 6 | 네트워크 오류 | 본문, 이메일, 고른 유형을 그대로 둠 | 확장: "전송에 실패했습니다. 잠시 후 다시 시도해주세요."<br>랜딩: "전송에 실패했습니다. GitHub 이슈로 남겨주세요." |

<br>

## 7-1-5 자산 로딩 실패

| 화면 | 서비스 아이콘을 불러오지 못하면 |
| --- | --- |
| 팝업 | 확장 기본 아이콘(`icons/icon48.png`)으로 바꾼다. 깨진 이미지가 보이지 않는다 |
| 설정 | 대체 이미지가 없어 브라우저 기본 표시가 보인다 |
| 랜딩 | 아이콘 자리에 서비스 이름의 첫 글자를 보인다 |

데이터 검증이 아이콘 파일이 있는지 확인하므로, 대체가 일어나는 것은 파일이 없어서가 아니라 로딩 자체가 실패한 경우다.
