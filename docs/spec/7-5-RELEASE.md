이 문서는 버전 자리를 정하는 기준, 릴리스 준비 PR, 태그 push와 릴리스 워크플로가 검사하는 것, 릴리스 후 공지를 정한다.

배포 경로와 자동화 범위는 배포에, 스토어 제출은 스토어 제출에, 스토어와 커뮤니티 문구의 작성 기준은 [릴리스 문구 작업 가이드](../../.claude/skills/release-copy/SKILL.md)에 있다. ([7-4 배포](7-4-DEPLOYMENT.md), [7-6 스토어 제출](7-6-STORE.md))

### 7-5-1 버전 자리

릴리스 노트를 먼저 쓰고 릴리스 노트 내용으로 버전 자리를 정한다.

| 릴리스 노트에 있는 절 | 버전 |
| --- | --- |
| `### Features`가 있음 | minor |
| `### Features` 없이 `### Fixes`가 있음 | patch |
| `### Internal`만 있음 | patch |
| 저장된 데이터나 사용자 목록이 깨지는 변경 | major |

서비스 추가처럼 데이터만 늘어난 경우도 사용자가 새로 갈 수 있는 곳이 생겼으므로 Features다.

<br>

### 7-5-2 준비 PR

| 순서 | 할 일 |
| --- | --- |
| 1 | 매니페스트의 버전을 올림 |
| 2 | 버전별 릴리스 노트 `v{version}`을 아래 절 구성으로 씀 |
| 3 | 스토어 등록 문구의 업데이트 절을 새 버전으로 바꿈 |
| 4 | 계속 알릴 기능이 있으면 커뮤니티 홍보 글에 반영함 |
| 5 | 모두 `main`에 병합함. 문구는 별도 PR로 나눠도 되지만 태그 push보다 먼저 병합함 |

| 릴리스 노트 절 | 내용 | 보이는 곳 |
| --- | --- | --- |
| `### Features` | 사용자에게 보이는 새 기능과 서비스 추가 | GitHub Release, 랜딩, Firefox 버전 노트 |
| `### Fixes` | 사용자에게 보이는 수정 | GitHub Release, 랜딩, Firefox 버전 노트 |
| `### Internal` | 내부 변경 | GitHub Release에만 |

| 제약 | 내용 |
| --- | --- |
| 태그 위치 | `main`의 최신 커밋. 스토어 제출이 태그가 체크아웃된 커밋을 가리키는지 검사하고 `main`에서만 실행되기 때문 |
| 어긋났을 때 | 태그를 push한 뒤 다른 PR을 병합하면 스토어 제출이 태그가 가리키는 커밋과 체크아웃한 커밋이 다르다는 오류로 막힘. 태그를 옮기면 공개된 태그를 강제로 다시 push하게 되므로 정해진 순서로 오류를 예방함 |

<br>

### 7-5-3 태그 push

| 순서 | 할 일 |
| --- | --- |
| 1 | `main`으로 전환하고 원격과 fast-forward로 맞춤 |
| 2 | 매니페스트 버전으로 `v{version}` 태그를 만듦 |
| 3 | 태그를 원격에 push함 |

`v`로 시작하는 세 자리 버전 태그가 릴리스 워크플로를 시작한다.

| 순서 | 검사 | 실패하면 |
| --- | --- | --- |
| 1 | 태그가 매니페스트 버전과 같음 | 태그 버전과 매니페스트 버전을 함께 보임 |
| 2 | 빌드 통과 | 빌드 단계의 출력 |
| 3 | 버전별 릴리스 노트가 있음 | 찾지 못한 릴리스 노트 경로를 보임 |
| 4 | 통과하면 GitHub Release 생성. 제목은 태그 이름, 첨부는 `linkhu-v{version}.zip`, 본문은 릴리스 노트 | |

<br>

### 7-5-4 릴리스 후 공지

스토어 반영이 끝나면 학내 커뮤니티에 업데이트를 알린다.

| 규칙 | 내용 |
| --- | --- |
| 문구 | 스토어 등록 문구의 해당 버전 업데이트 절을 다시 씀 |
| 링크 | 랜딩 주소를 함께 넣음 |
| 범위 | 코드가 없는 기능은 넣지 않음 |
