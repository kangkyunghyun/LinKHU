# 7-5 릴리스

이 문서는 버전 자리를 정하는 기준, 릴리스 준비 PR, 태그 push와 릴리스 워크플로가 검사하는 것, 릴리스 후 공지를 정한다.

배포 경로와 자동화 범위는 배포에, 스토어 제출은 스토어 제출에, 스토어와 커뮤니티 문구의 작성 기준은 `.claude/skills/release-copy/SKILL.md`에 있다. ([7-4 배포](7-4-DEPLOYMENT.md), [7-6 스토어 제출](7-6-STORE.md))

<br>

### 7-5-1 버전 자리

릴리스 노트가 버전을 정한다. 변경량으로 재지 않고, 무엇이 바뀌었는지 먼저 노트로 적은 뒤 그 내용으로 자리를 정한다.

| 릴리스 노트에 있는 절 | 버전 |
| --- | --- |
| `### Features`가 있음 | minor |
| `### Features` 없이 `### Fixes`가 있음 | patch |
| `### Internal`만 있음 | patch. 사용자가 화면에서 겪는 변화가 없음 |

서비스 추가처럼 데이터만 늘어난 경우도 Features다. 코드가 한 줄도 바뀌지 않아도 사용자가 새로 갈 수 있는 곳이 생겼으므로 노트의 Features에 적고, 그러면 위 기준이 minor로 정한다.

major는 이 기준의 대상이 아니다. 저장된 데이터나 사용자 목록이 깨지는 변경일 때만 올린다.

<br>

### 7-5-2 준비 PR

| 순서 | 할 일 |
| --- | --- |
| 1 | `src/manifest.json`의 `version`을 올린다 |
| 2 | `docs/releases/v{version}.md`를 기존 형식으로 쓴다. 사용자에게 보이는 변경 중심 |
| 3 | `docs/copy/1-1-STORE-LISTING.md`의 업데이트 절을 새 버전으로 바꾼다 |
| 4 | 계속 알릴 기능이 있으면 `docs/copy/1-2-COMMUNITY-POST.md`에 녹인다 |
| 5 | 위를 모두 `main`에 머지한다 |

문구는 준비 PR에 함께 담아도 되고 별도 PR로 나눠도 되지만, 둘 다 태그 push보다 먼저 머지한다.

<br>

**1. 태그는 `main`의 최신 커밋을 가리켜야 한다**

| 제약 | 내용 |
| --- | --- |
| 릴리스 검증 스크립트 | 태그가 체크아웃된 커밋을 가리키는지 검사한다 |
| 스토어 제출 워크플로 | `main`에서만 실행된다 |

두 제약이 겹쳐 태그가 `main`의 최신 커밋일 때만 스토어 제출이 통과한다. 태그를 민 뒤에 다른 PR을 머지하면 `main`이 태그보다 앞서고, 스토어 제출이 아래 오류로 막힌다.

```text
Release tag v2.7.0 points to 6d3677a, but the checked out commit is 3f3fe84.
```

이미 어긋났다면 태그를 `main`의 최신 커밋으로 옮길 수 있지만, 공개된 태그를 강제로 다시 push하게 되고 GitHub Release가 가리키는 커밋도 바뀐다. 준비 PR 머지, 태그 push, 스토어 제출 순서를 지켜 이 상황을 막는다.

<br>

### 7-5-3 태그 push

```bash
git switch main
git pull --ff-only
VERSION=$(node -p "require('./src/manifest.json').version")
git tag "v$VERSION"
git push origin "v$VERSION"
```

`v*.*.*` 형식의 태그가 릴리스 워크플로를 시작한다. 워크플로는 아래 세 가지를 자체 단계로 검사한 뒤 릴리스를 만든다. `npm run validate:release`는 이 워크플로에서 쓰지 않는다.

| 순서 | 검사 | 막는 실수 |
| --- | --- | --- |
| 1 | 태그가 매니페스트 버전과 같은가 | 버전을 올리지 않고 태그만 미는 것 |
| 2 | `npm run build`가 통과하는가 | 깨진 데이터나 산출물이 나가는 것 |
| 3 | `docs/releases/v{version}.md`가 있는가 | 노트 없이 릴리스가 나가는 것 |

통과하면 태그 이름을 제목으로 GitHub Release를 만들고, `linkhu-v{version}.zip`을 첨부하고, `docs/releases/v{version}.md` 내용을 릴리스 노트로 쓴다.

<br>

### 7-5-4 릴리스 후 공지

스토어 반영이 끝나면 학내 커뮤니티에 업데이트를 알린다. 스토어 목록 페이지만으로는 기존 사용자가 새 버전을 알아채지 못한다.

| 규칙 | 이유 |
| --- | --- |
| 공지 문구는 [스토어 등록 정보](../copy/1-1-STORE-LISTING.md)의 해당 버전 업데이트 절을 다시 쓴다 | 같은 내용을 따로 쓰지 않는다 |
| 랜딩 페이지 링크를 함께 넣는다 | 설치 전에 확인할 곳을 준다 |
| 코드가 없는 기능을 공지에 넣지 않는다 | 구상 중인 계획은 약속이 되고, 지키지 못하면 신뢰를 잃는다 |
