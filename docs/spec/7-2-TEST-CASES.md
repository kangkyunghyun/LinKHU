# 7-2. 테스트 케이스

LinKHU는 확장 프로그램 UI가 제품의 대부분이라, 자동 테스트로 잡을 수 있는 범위가 제한적이다. 브라우저 확장 API와 드래그 앤 드롭은 Node 테스트 환경에서 재현하기 어렵다.

그래서 검증을 두 층으로 나눈다. **순수 로직은 자동 테스트로 고정하고, 화면 동작은 수동 검증 매트릭스로 고정한다.** 어느 쪽도 상대를 대신하지 않는다.

```text
§7-2-1   자동 테스트        npm test가 덮는 범위
§7-2-2   덮지 못하는 것      자동화하지 않은 영역과 이유
§7-2-3   수동 검증 매트릭스   변경 유형별 확인 항목
§7-2-4   검증 환경 준비      확장·랜딩을 로컬에서 띄우는 법
§7-2-5   특별 검증 절차      자동화가 잡지 못하는 실패를 사람이 잡는 법
```

## 7-2-1 자동 테스트

`npm test`는 Node 내장 테스트 러너(`node --test`)로 `tests/`를 실행한다. 2026-09-01 기준 11개 파일 81개 테스트다. 테스트 프레임워크를 따로 두지 않는다 — 의존성 없는 구성(DECISIONS 1-1)을 유지하기 위해서다.

| 파일 | 고정하는 것 |
| --- | --- |
| `shared.test.js` | 검색 정규화, 이름·id·카테고리 매칭, 점수 순위, 기본 순서, 카드 이름 줄바꿈 표 |
| `theme.test.js` | 테마 모드 정규화·폴백, 시스템 해석, 초기 적용 순서, 저장 실패 롤백 |
| `landing-search.test.js` | 랜딩 검색 정규화, 매칭, 결과 개수 제한, 기본 서비스 |
| `landing-mobile.test.js` | 모바일 판정, 설치 안내 노출, 링크 복사·QR 토글, GA4 보고 |
| `landing-releases.test.js` | 릴리스 노트의 `### Internal` 제거, 최소 마크다운 렌더, API 실패 폴백, 본문 마크업 무해화 |
| `data-validation.test.js` | 저장소 데이터의 유효성, 중복 필드 탐지, 아이콘 공유 허용, 경로 구분자 |
| `browser-behavior.test.js` | 팝업의 중복 id 제거, 클릭·수식키·휠 클릭 동작, 버전 비교, 설정 저장 성공·실패 |
| `feedback.test.js` | 문의 설정 여부 판정, 전송 대상 필드, 이메일 선택 포함 |
| `landing-feedback.test.js` | 랜딩과 확장의 문의 전송 일치 |
| `package-extension.test.js` | 패키징 산출물의 재현 가능성 |
| `publish-firefox.test.js` | 스토어로 보낼 릴리스 노트에서 `### Internal` 제거 |

특히 중요한 두 테스트가 있다.

- **확장-랜딩 검색 일치** — `shared.test.js`가 `LinKHUShared.rankSites`와 랜딩의 `searchServices` 결과 순서가 같은지 확인한다. 두 구현이 갈라지는 것을 막는 유일한 장치다 (§4-3).
- **확장-랜딩 문의 일치** — `landing-feedback.test.js`가 두 경로가 같은 폼·같은 필드로 전송하는지 확인한다.

검색 규칙이나 문의 전송을 바꿀 때는 **양쪽 구현을 함께 바꿔야 하며**, 위 테스트가 그것을 강제한다.

`data-validation.test.js`는 저장소의 실제 데이터를 검사한다. 즉 `npm test`만 실행해도 데이터가 깨졌는지 알 수 있다.

패키징 테스트는 산출물의 **재현 가능성**을 고정한다. 파일 타임스탬프가 달라져도 같은 ZIP이 나와야 한다. 패키징 스크립트가 고정된 DOS 시각(1980-01-01)을 쓰는 이유다.

## 7-2-2 덮지 못하는 것

다음은 자동 테스트로 검증하지 않는다. 대신 §7-2-3의 수동 검증으로 다룬다.

| 영역 | 자동화하지 않은 이유 |
| --- | --- |
| 드래그 앤 드롭 정렬 | HTML5 드래그 이벤트와 포인터 좌표를 Node 환경에서 재현하는 비용이 크다 |
| 드래그 중 자동 스크롤 | 실제 레이아웃과 스크롤 위치가 필요하다 |
| 팝업 렌더링 결과 | `chrome.storage` 콜백과 DOM 렌더링이 결합되어 있다 |
| 테마·색상 표현 | 시각 판단은 사람이 봐야 한다. 모드 해석·폴백·롤백 같은 순수 로직은 `theme.test.js`가 덮는다 |
| 브라우저 단축키 | 브라우저가 등록하는 영역이라 확장 코드 밖이다 |
| 스토어 심사 요구사항 | 외부 시스템이다 |

이 목록이 길어지면 구조를 의심한다. 로직을 화면에서 분리해 순수 함수로 옮길 수 있는지 먼저 검토한다. `shared.js`가 그렇게 분리된 예다.

## 7-2-3 수동 검증 매트릭스

변경 유형별 확인 항목이다. [`AGENTS.md`의 수동 검증 기준](../../AGENTS.md)을 화면 단위로 구체화한 것이며, 상충하면 이 문서를 따른다.

PR 본문에는 **무엇을 어떤 기준으로 확인했는지 재현 가능하게** 적는다. "정상 동작함"은 검증 기록이 아니다.

### 팝업

| 확인 항목 | 기대 결과 |
| --- | --- |
| 일반 클릭 | 새 탭이 활성 상태로 열리고 팝업이 닫힌다 |
| `Ctrl`/`Cmd` + 클릭 | 새 탭이 배경으로 열리고 **팝업이 유지된다** |
| 휠(가운데) 클릭 | 새 탭이 배경으로 열린다 |
| 검색 입력 | 이름·id·카테고리로 결과가 줄어든다 |
| 검색 후 `Enter` | 첫 결과가 **현재 탭**에서 열린다 |
| 한글 조합 중 `Enter` | 조합만 확정되고 이동하지 않는다 |
| `/` 키 | 검색창으로 포커스가 이동한다 |
| 숫자 `1`~`9` | n번째 카드가 열린다 |
| 검색창에 숫자 입력 | 숫자 단축키가 발동하지 않는다 |
| 빈 결과 | 빈 상태 메시지가 보인다 |
| 아이콘 로딩 실패 | 확장 기본 아이콘으로 대체된다 |
| 두 줄로 넘어가는 긴 이름 카드 | 글자 사이가 아니라 의미 단위로 꺾인다(§4-1-4) |
| 목록이 길어 스크롤바가 뜬 상태 | 줄바꿈 지점이 그대로 유지된다 |

색상 규칙의 원본은 §4-2다.

**색 치환에서 상습적으로 누락되는 곳이 있다.** 실제 검수에서 발견된 지점들이므로 색을 바꿀 때 먼저 확인한다.

- `prefers-color-scheme: dark` 미디어 쿼리 안의 하드코딩 배경색 — 라이트 테마만 보면 발견되지 않는다.
- 문서(`docs/**.md`)에 문장으로 적힌 색 값.
- 아이콘·이미지 에셋에 그려 넣은 색 — 코드 검색으로 잡히지 않는다.

잔여색 검사는 CSS만이 아니라 **SVG·JS·JSON·Markdown까지 포함해** `src`와 `docs` 전체를 대상으로 한다.

## 7-2-4 검증 환경 준비

### 확장 프로그램

브라우저의 확장 관리 화면에서 개발자 모드를 켜고 `src/` 폴더를 그대로 로드한다. 빌드가 없으므로 패키징하지 않고 소스 폴더를 바로 올린다(DECISIONS 1-1).

`popup.html`을 `file://`로 여는 것은 **화면 확인용으로만 쓴다.** `chrome.*` API가 없어 목록이 그려지지 않으므로, 동작 검증은 반드시 확장으로 로드해서 한다.

### 랜딩 페이지

**`file://`로 열면 동작하지 않는다**. 랜딩은 서비스 목록을 `fetch("assets/services.json")`으로 불러오는데, `file://`에서는 이 요청이 차단되어 검색이 비어 보인다. **기능이 깨진 것이 아니라 열어본 방식이 잘못된 것이다.**

랜딩을 확인할 때는 `landing/`을 로컬 HTTP 서버로 띄워 `http://`로 접근한다.

업데이트 섹션은 GitHub Releases API를 부르므로 **네트워크가 없거나 rate limit에 걸리면 섹션이 통째로 보이지 않는다** (DECISIONS 5-3). 그것이 정상 동작이며, 섹션이 안 보인다고 깨진 것이 아니다. 목록이 그려지는지 확인하려면 네트워크가 되는 환경에서 본다.

### PR 비교

다른 사람의 PR을 로컬에서 확인할 때는 원격의 PR ref를 가져와 별도 작업 트리에서 연다. 현재 작업 중인 브랜치를 건드리지 않기 위해서다.

## 7-2-5 특별 검증 절차

자동 테스트도 화면 확인도 잡지 못하는 실패 유형이 있다. 각각 전용 절차를 둔다.

### 문의 폼 — 실제 전송 1회

문의 전송은 `mode: "no-cors"`라 응답을 읽을 수 없다. 그 결과 **필드 id가 틀려도 오류 없이 조용히 실패한다.** 화면에는 "전송했습니다"가 뜨고 응답만 수집되지 않는다. 이보다 나쁜 실패 방식은 없다 — 아무도 모른 채 의견이 사라진다.

따라서 다음이 필수다.

| 언제 | 무엇을 한다 |
| --- | --- |
| 폼을 새로 연결하거나 필드 구성을 바꿨을 때 | **실제로 한 번 전송해 응답이 수집되었는지 눈으로 확인한다.** 코드 리뷰와 자동 테스트로 대체할 수 없다 |
| 위 확인을 할 때 | 확장과 랜딩 **양쪽에서** 각각 전송한다. 두 경로가 같은 폼을 쓰는지는 테스트가 보지만, 폼 자체가 살아 있는지는 보지 못한다 |
| 필드 id를 확인할 때 | 공개된 폼 페이지에서 직접 본다. **일반 공유 링크는 필드 id를 담고 있지 않다** |

**라이브 폼 점검**

**설정했다고 믿지 말고 실제 폼을 확인한다**. 공개된 `viewform` 페이지에 폼 구조가 들어 있어 entry ID와 필수 여부를 한 번에 볼 수 있다.

```bash
FORM=https://docs.google.com/forms/d/e/<폼 ID>/viewform
curl -sL "$FORM" -o /tmp/form.html

python3 - /tmp/form.html <<'PYEOF'
import re, sys, json
html = open(sys.argv[1], encoding="utf-8").read()
data = json.loads(re.search(r'FB_PUBLIC_LOAD_DATA_ = (.*?);</script>', html, re.S).group(1))
for question in data[1][1]:
    for entry in (question[4] or []):
        print(f'"{question[1]}"  entry.{entry[0]}  필수={"O" if entry[2] else "X"}')
PYEOF
```

기대 출력이다. 다르면 §5-3의 계약이 깨진 것이다.

```text
"문의 내용"        entry.1096769292  필수=O
"답변 받을 이메일"  entry.491031779   필수=X
```

폼 질문을 고친 뒤에는 이 점검을 다시 돌린다. 계약과 조용히 실패하는 경우는 §5-3에 있고, 이 채널을 택한 이유와 제약은 DECISIONS 1-5에 있다.

### 팝업 백지 위험

팝업은 저장소 콜백 안에서 화면을 그린다. **콜백이 오지 않으면 아무것도 그려지지 않는다.**

| 규칙 | 왜 |
| --- | --- |
| 화면 표시 여부를 저장소 콜백에만 의존하는 구조를 만들지 않는다 | 콜백이 도착하지 않으면 영구 백지가 된다 |
| 로딩 게이트를 두면 **시간 초과 시 화면을 여는 안전판을 함께 넣는다** | 데이터를 못 불러온 팝업은 불편하지만, 백지 팝업은 고장 난 확장으로 보인다 |

### 스크린샷 대신 계산값

랜딩 페이지는 애니메이션이 계속 돌아 스크린샷 캡처가 안정적으로 끝나지 않는다. 색상이나 테마를 검증할 때는 **스크린샷 대신 계산된 스타일 값을 읽어 비교한다**. 사람 눈에 의존하지 않으므로 판정이 더 정확하기도 하다.

라이트·다크 확인은 시스템 설정을 바꾸지 않고 브라우저의 미디어 특성 강제 기능으로 전환해 각각 측정한다.

### 테스트 실행 방식

테스트 실행 명령은 대상 파일 패턴을 명시하는 편이 안전하다. Node 버전에 따라 디렉터리 인자를 탐색 대상으로 처리하지 않아, 테스트가 **하나도 실행되지 않았는데 성공으로 보이는** 상황이 생길 수 있다. 테스트 통과를 기록할 때는 통과 개수가 예상과 맞는지 함께 확인한다.
