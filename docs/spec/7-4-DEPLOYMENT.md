# 7-4. 배포

LinKHU는 네 곳으로 나간다. 세 개 스토어와 GitHub Pages 랜딩이다. 각 경로의 트리거와 자동화 범위가 다르므로, 무엇이 자동이고 무엇이 수동인지 아는 것이 중요하다.

이 문서는 **경로와 경계**만 정한다. 각 경로를 실제로 밟는 절차는 뒤에서 이어진다.

```text
§7-4-1   배포 경로 개요   네 경로와 트리거
§7-4-2   CI 검증          PR과 main에서 도는 검증
§7-4-3   랜딩 배포        Pages 자동 배포
```

## 7-4-1 배포 경로 개요

| 경로 | 트리거 | 자동화 |
| --- | --- | --- |
| 검증 | PR, `main` push | 전자동 |
| GitHub Release | `v*.*.*` 태그 push | 전자동 (릴리스 생성 + ZIP 첨부) |
| Chrome Web Store | 수동 실행 | 워크플로 (확인 문자열 필요) |
| Firefox Add-ons | 수동 실행 | 워크플로 (확인 문자열 필요) |
| Whale Store | 수동 | 없음 |
| 랜딩 | `landing/**` 또는 Pages 워크플로 파일 변경이 `main`에 들어올 때, 또는 수동 실행 | 전자동 |

## 7-4-2 CI 검증

PR과 `main` push에서 `npm run build`가 실행된다. 즉 테스트, 데이터 검증, 랜딩 산출물 최신 확인, 패키징이 모두 돈다. 패키징 결과는 아티팩트로 업로드된다.

| 규칙 | 내용 |
| --- | --- |
| 로컬에서 검증을 잊었다 | PR에서 걸린다 |
| Node 버전 | CI는 22. 로컬 개발도 같은 계열을 쓴다 |
| CI가 실패한 PR | **병합하지 않는다** |

## 7-4-3 랜딩 배포

| 발동 조건 | 비고 |
| --- | --- |
| `landing/**`가 `main`에 들어올 때 | 가장 흔한 경로 |
| Pages 배포 워크플로 파일이 `main`에서 바뀔 때 | |
| 수동 실행(`workflow_dispatch`) | **콘텐츠 변경 없이도 재배포할 수 있다**. 배포가 실패했거나 결과가 의심스러울 때 쓴다 |

업로드되는 것은 **`landing/` 폴더**다(`upload-pages-artifact`의 `path: landing`).

| 규칙 | 내용 |
| --- | --- |
| 빌드 단계 | 없다. `landing/`의 파일이 곧 배포물이다 |
| 생성물 | `landing/assets/services.json`과 `landing/assets/images/`는 **저장소에 커밋된 상태로 배포된다**. 생성 스크립트는 배포 단계에서 돌지 않는다. 데이터를 바꾸고 생성을 잊으면 랜딩이 낡은 목록을 보여주고, 이를 막는 것이 `validate:landing-data`다 |
| 확장 버전과의 관계 | 랜딩만 바뀌는 변경은 확장 버전을 올릴 필요가 없다. 두 배포 경로는 독립적이다 |
| 반영 확인 | 머지 후 몇 분. **운영 URL에서 실제로 받아본다**. 페이지뿐 아니라 서비스 목록 데이터와 아이콘까지 정상 응답하는지 본다 — 로컬에서 잘 보이던 아이콘이 배포에서 빠지는 경우가 여기서 걸린다 |
