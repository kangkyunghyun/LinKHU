# 3. 정보 구조

이 문서는 요구사항과 설계 사이를 잇는다. [2-1](2-1-USER-STORIES.md)·[2-2](2-2-OPERATOR-REQUIREMENTS.md)가 "무엇을 할 수 있어야 하는가"를 말하고, [4-x](4-1-LAYOUT.md)가 "어떻게 만드는가"를 말한다면, 여기는 그 사이에서 **제품이 다루는 단위가 무엇이고 각 화면이 그중 무엇을 보여주는가**를 고정한다.

이 층이 흔들리면 아래가 전부 흔들린다. 카테고리를 하나 늘리는 것은 화면 조정이 아니라 **데이터 계약·설정 화면 영역·필터 칩·검증 스크립트가 동시에 움직이는 변경**이다. 그래서 여기가 설계보다 위에 있다.

```text
§3-1   다루는 단위        서비스 하나가 무엇인가
§3-2   카테고리          8개 분류와 분포
§3-3   화면별 범위        무엇을 보여주고 무엇을 감추는가
§3-4   기본 목록          아무것도 고르지 않은 사용자가 보는 것
§3-5   검색이 다루는 범위   무엇으로 찾히고 어떤 순서로 나오는가
```

## 3-1 다루는 단위

LinKHU가 다루는 단위는 **서비스 하나**다. 사용자에게는 "누르면 열리는 바로가기 하나"이고, 데이터에서는 `MASTER_SITE_LIST`의 원소 하나다.

| 필드 | 사용자에게 보이는 것 |
| --- | --- |
| `name` | 카드에 적히는 이름 |
| `imgSrc` | 카드의 아이콘 |
| `url` | 눌렀을 때 가는 곳 |
| `category` | 설정 페이지에서 묶이는 영역, 필터 칩 |
| `id` | 보이지 않음. 순서 저장과 검색에 쓰인다 |

**서비스보다 작은 단위는 없다** (MUST). 한 사이트 안의 개별 메뉴나 딥링크를 항목으로 만들지 않는다. 같은 주소로 가는 항목이 여러 개면 사용자에게는 선택지가 아니라 소음이고, 그래서 데이터 규칙이 `url` 중복을 금지한다 ([6-2-3](6-2-DATA.md)). 학과 항목을 독립 홈페이지가 있을 때만 만드는 것도 같은 이유다 ([DECISIONS 2-3](DECISIONS.md#d-2-3)).

필드별 형식과 제약은 [6-2 데이터](6-2-DATA.md)가 원본이다. 이 문서는 **그 필드가 화면에서 무슨 역할인지**까지만 말한다.

## 3-2 카테고리

카테고리는 8개이고, 단일 소스는 `src/data.js`의 `SITE_CATEGORIES`다. 배열 순서가 곧 화면 표시 순서다.

| 카테고리 | 서비스 수 |
| --- | --- |
| 학사·포털 | 13 |
| 생활·복지 | 12 |
| 장학·진로·창업 | 5 |
| 교육·역량 | 16 |
| 캠퍼스·문화 | 11 |
| 대학·행정 | 15 |
| 단과대 | 26 |
| 학과 | 69 |
| **합계** | **167** |

- **분류는 한 겹이다** (MUST). 카테고리 안에 하위 분류를 두지 않는다. 구분이 더 필요하면 카테고리를 늘린다 ([4-1-3](4-1-LAYOUT.md)).
- 서비스 하나는 카테고리 하나에만 속한다. 다중 분류를 두지 않는다 (MUST). 어느 영역에서 찾을지가 사람마다 갈리면 훑기의 이점이 사라진다.
- **카테고리 값을 늘리거나 바꾸는 것은 계약 변경이다** (MUST). [6-2-2](6-2-DATA.md)의 필드 규칙과 `scripts/validate-data.js`를 함께 고쳐야 한다.
- 위 개수는 2026-09-21 기준이다. 숫자가 여러 곳에 흩어져 생기는 문제는 [6-2-8](6-2-DATA.md)에 있다.

## 3-3 화면별 범위

세 화면이 같은 167개를 보지만, **보여주는 범위가 다르다.**

| 화면 | 기본으로 보여주는 것 | 전체 목록 | 분류 노출 |
| --- | --- | --- | --- |
| 팝업 | 내 바로가기(`userOrder`) | 검색할 때만 | 없음 |
| 설정 | 전체 167개 | 항상 | 카테고리 영역 + 필터 칩 |
| 랜딩 | 기본 서비스 3개 | 검색할 때만, 최대 5개 | 없음 |

- **팝업은 고른 것만 보여준다** (MUST). 전체 목록을 펼치는 자리가 아니다. 320px 안에서 즉시 목표를 달성하는 도구이고, 고르는 일은 설정 페이지가 맡는다.
- **팝업의 검색은 전체를 대상으로 한다** (MUST). `userOrder`가 아니라 `MASTER_SITE_LIST` 전체를 훑는다. 담아두지 않은 서비스도 찾아서 열 수 있어야 한다.
- **설정만 분류를 노출한다.** 팝업에 카테고리 머리글을 두지 않는다 — 열 개 남짓한 카드에 분류를 씌우면 밀도만 떨어진다.
- 랜딩의 기본 3개(`info21`, `ecampus`, `sugang`)와 결과 상한 5개는 **랜딩 전용 표시 규칙**이며 확장과 무관하다 ([5-1](5-CONTRACT.md)).

## 3-4 기본 목록

아무것도 고르지 않은 사용자가 팝업에서 보는 10개다. 단일 소스는 `src/shared.js`의 `DEFAULT_SITE_IDS`다.

```text
info21  ecampus  everytime  notice  library
scholarship  intern  sugang  chatkhu  ois
```

- 표시 순서는 **이름 `ko-KR` 가나다순**이다. 배열에 적힌 순서가 아니다. 설정 페이지 왼쪽 목록과 같은 기준이라 두 화면의 순서 감각이 맞는다.
- 목록에 있지만 `MASTER_SITE_LIST`에 없는 id는 **조용히 빠진다** (MUST). 서비스를 지워도 깨진 항목이 생기지 않는다.
- 이 목록은 **저장된 `userOrder`가 없을 때만** 쓰인다 (MUST). 이미 고른 사용자의 화면은 기본 목록이 바뀌어도 그대로다 ([4-4-2](4-4-STATE.md)).
- 기본 목록을 바꾸는 것은 **신규 사용자의 첫 화면을 바꾸는 일이다.** 서비스를 추가했다고 자동으로 들어가지 않는다.

## 3-5 검색이 다루는 범위

검색 대상은 **이름, id, 카테고리** 세 가지다. `url`은 대상이 아니다.

검색어와 대상 모두 소문자화(`ko-KR` 기준)하고 공백을 제거한 뒤 비교한다. "e campus"와 "ecampus"가 같게 취급된다.

| 점수 | 조건 |
| --- | --- |
| 0 | 이름이 검색어로 시작 |
| 1 | 이름에 검색어 포함 |
| 2 | id가 검색어로 시작 |
| 3 | id에 검색어 포함 |
| 4 | 카테고리에 검색어 포함 |

낮을수록 위에 온다. 동점이면 원본 배열 순서를 유지한다 (MUST) — 정렬이 안정적이지 않으면 같은 검색어에 결과 순서가 달라진다.

**이 순위는 확장과 랜딩이 같아야 한다** (MUST). 팝업에서 `Enter`가 첫 결과를 열기 때문에, 순위가 갈리면 같은 검색어에 다른 서비스가 열린다. 두 구현이 따로 존재하므로 일치를 테스트가 강제한다 ([DECISIONS 2-2](DECISIONS.md#d-2-2), [7-2](7-2-TEST-CASES.md)).
