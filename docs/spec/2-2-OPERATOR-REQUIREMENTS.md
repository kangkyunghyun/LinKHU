# 2-2. 운영자 요구사항

메인테이너가 반복해서 해야 하는 일과, **그 일이 무엇을 보장해야 하고 어떻게 확인하는지**를 정리한다. 사용자에게 보이지 않지만 제품 수명을 결정한다.

```text
§2-2-0   지켜야 할 사항       명령이 확인하는 것과 사람이 보는 것
§2-2-1   서비스 데이터 갱신   학교 사이트 변경에 대응
§2-2-2   릴리스               버전 올리고 배포 가능한 상태 만들기
§2-2-3   스토어 배포          3개 스토어 심사 대응
§2-2-4   문의 대응            사용자 의견 수집과 처리
§2-2-5   기여 관리            외부 PR 심사 기준, 포크 PR CI, 응대 방침
```

## 2-2-0 지켜야 할 사항

**사람의 기억이 아니라 명령이 확인한다.**

| 지키는 것 | 확인 | 기준 |
| --- | --- | --- |
| 데이터 무결성 | `validate:data` | 오류 0. 중복 `id`·`url` 0, 없는 아이콘 경로 0 |
| 랜딩 산출물 동기 | `validate:landing-data` | 통과. 어긋나면 생성 명령을 안내하며 실패 |
| 아이콘 라이트·다크 짝 | `validate:dark-icons` | 167쌍 전부 최신 |
| 기존 동작 회귀 | `npm test` | 91개 통과 |
| 두 벌 구현의 일치 | `npm test` | 검색 랭킹, 릴리스 노트 필터, 문의 폼 필드 |
| 릴리스 산출물 | 릴리스 워크플로 | 태그 = 매니페스트 버전, 노트 파일 존재, 같은 커밋 → 같은 바이트 ZIP |
| 위 전부 | `npm run build` | CI가 PR마다 같은 명령을 돈다 |

화면 동작, 스토어 심사, 교내 사이트의 실제 생사는 이 표에 없다. 사람이 §7-2의 수동 검증으로 본다.

## 2-2-1 서비스 데이터 갱신

교내 웹서비스는 메인테이너의 통제 밖에서 바뀐다. 주소가 바뀌거나, 서비스가 사라지거나, 학과가 신설·통폐합된다. 데이터 갱신은 LinKHU에서 가장 자주 발생하는 운영 작업이다.

| 규칙 | 왜 | 강도 |
| --- | --- | --- |
| 단일 소스는 `src/data.js`의 `MASTER_SITE_LIST` | 다른 곳에 서비스 목록을 복제하지 않는다 | MUST |
| `npm run validate:data` 결과를 PR 본문에 남긴다 | 무엇을 확인했는지 재현 가능해야 한다 | MUST |
| 한 PR에서 아이콘을 한꺼번에 많이 바꾸지 않는다 | 되돌릴 단위를 작게 유지한다 | SHOULD |

**스키마, 필드 규칙, 검증·생성 순서, 삭제 절차, URL 판단 기준은 6-2 데이터가 원본이다.** 데이터를 실제로 바꾸기 전에 그 문서를 본다. 아이콘 도안 규칙은 [아이콘 스타일 가이드](../guides/4-1-ICON-STYLE-GUIDE.md), 색상 관련 임시 규칙은 §4-2에 있다.

운영자 관점에서 기억할 것은 하나다. **데이터 변경은 데이터만 바꾸는 작업이 아니다.** 랜딩 산출물과 문서에 적힌 서비스 수가 함께 움직이며, 빠뜨리면 CI 또는 사용자 눈에서 드러난다.

## 2-2-2 릴리스

절차의 원본은 [Release Process](../guides/1-RELEASE-PROCESS.md)이고, 자동화 경계는 7-4 배포에 있다. 여기서는 운영자가 판단해야 할 것만 적는다.

| 판단할 것 | 기준 | 강도 |
| --- | --- | --- |
| 버전과 노트 | 준비 PR에서 `src/manifest.json`의 `version`을 올리고 같은 PR에 `docs/releases/v{version}.md`를 쓴다 | MUST |
| 노트에 무엇을 쓰나 | 내부 리팩터링이 아니라 **사용자에게 보이는 변경** | MUST |
| 패치인가 마이너인가 | DECISIONS 2-4의 semver 방침 | MUST |
| 태그 | 준비 PR이 머지된 뒤 같은 버전으로 push | |
| 어긋났을 때 | 태그와 매니페스트가 다르거나 노트 파일이 없으면 릴리스가 만들어지지 않아야 한다 | MUST |

검증이 **두 지점에 나뉘어 있다**는 점에 주의한다. 태그 push 시점의 릴리스 워크플로는 자체 검사로 태그·버전 일치와 릴리스 노트 존재를 확인한다. `npm run validate:release`는 여기서 쓰이지 않고, **스토어 게시 워크플로가 실행될 때** 호출되어 더 넓은 범위(버전 형식, 매니페스트 일치, 태그 존재, 릴리스 노트 존재)를 확인한다. 따라서 **태그를 밀었을 때 통과했다고 스토어 게시까지 통과한다는 보장은 없다.**

## 2-2-3 스토어 배포

LinKHU는 세 스토어에 배포되며, 각 스토어의 심사 주기와 요구사항이 다르다. 태그 push로 만들어지는 GitHub Release는 배포의 **끝이 아니라 시작**이다.

| 스토어 | 제출 방식 | 절차 문서 |
| --- | --- | --- |
| Chrome Web Store | 수동 실행(`workflow_dispatch`) 워크플로. **확인 문자열 입력을 요구한다** (MUST) | [Chrome](../guides/2-2-CHROME-WEB-STORE.md) |
| Firefox Add-ons | 같음 | [Firefox](../guides/2-3-FIREFOX-ADDONS.md) |
| Whale Store | 공개 배포 API가 확인되기 전까지 **수동 배포** | [Whale](../guides/2-4-WHALE-STORE.md) |

공통 절차는 [Store Release Checklist](../guides/2-1-STORE-RELEASE-CHECKLIST.md)를 따르고, 설명 원본은 [Store Listing](../copy/1-1-STORE-LISTING.md)에서 관리하며 버전마다 업데이트 섹션을 교체한다.

**매니페스트를 바꾼 릴리스는 세 곳의 호환성과 권한 범위를 모두 확인한다** (MUST). Firefox는 `strict_min_version`과 데이터 수집 선언이 있어 특히 영향을 받는다.

권한을 새로 추가하는 변경은 세 스토어 모두에서 재심사 사유가 되고 기존 사용자에게 권한 승인 요구가 뜬다. 권한 추가는 DECISIONS 1-3의 최소 권한 원칙에 따라 별도 판단 대상이다 (MUST).

## 2-2-4 문의 대응

사용자 의견 경로는 두 가지다.

1. **문의하기 폼** — 팝업·설정·랜딩에 있다. GitHub 계정이 없는 사용자를 위한 경로이며, Google Forms로 수집된다. 연결 설정은 [문의 채널 설정 가이드](../guides/3-FEEDBACK-SETUP.md)를 따른다.
2. **GitHub Issue** — 개발자와 기여자를 위한 경로다.

- 문의 폼이 설정되지 않은 상태에서도 화면이 깨지지 않아야 한다 (MUST). 설정 여부를 확인해 안내 문구로 처리한다.
- 확장과 랜딩의 문의 전송은 같은 폼·같은 필드를 써야 한다 (MUST). 두 경로가 갈라지면 수집 결과가 나뉜다. 이 일치는 테스트로 고정되어 있다 (7-2 테스트 케이스 참고).

## 2-2-5 기여 관리

LinKHU는 공개 저장소이며 외부 기여를 받는다.

| 규칙 | 내용 | 강도 |
| --- | --- | --- |
| 순서 | 모든 변경은 이슈 → 브랜치 → PR ([`AGENTS.md`](../../AGENTS.md)) | |
| PR 본문 | 저장소 템플릿을 쓰고 검증 결과를 재현 가능하게 적는다 | MUST |
| 방향이 다른 PR | 기능이 동작하더라도 **반려할 수 있다.** 기준은 §4-2, 사례는 DECISIONS 5-2 | MAY |
| 반려할 때 | 이유와 향후 계획을 남긴다. 기여자가 무엇이 문제였는지 알 수 있어야 한다 | SHOULD |

### 포크에서 온 PR의 CI

포크 저장소에서 올라온 PR은 **워크플로가 자동으로 실행되지 않는다.** 저장소 소유자가 실행을 승인해야 돌아가며, 승인하지 않으면 검증이 끝나지 않은 상태로 PR이 계속 열려 있게 된다.

승인은 임의의 코드를 저장소의 워크플로 환경에서 실행시키는 행위다. 따라서 **승인 전에 변경 파일 목록을 먼저 확인한다** (MUST). 다음이 포함되어 있으면 내용을 읽고 판단한 뒤에 승인한다.

| 바뀐 곳 | 왜 읽어야 하나 |
| --- | --- |
| `package.json` | 스크립트나 의존성 변경 |
| `scripts/` | 검증·패키징 스크립트 |
| `.github/` | 워크플로 정의 |

문서나 `src/`의 화면 코드만 바뀐 PR은 바로 승인해도 무방하다 (MAY).

### 응대 방침

| 상황 | 어떻게 한다 | 강도 |
| --- | --- | --- |
| 한 줄짜리 사소한 수정 | **기여자에게 왕복시키지 않는다.** 병합한 뒤 메인테이너가 이슈로 등록해 직접 정리하는 편이 서로의 시간을 아낀다 | SHOULD |
| 코드 스타일 지적 | 병합 조건이 아니라 정보성 코멘트로 남긴다 | SHOULD |
| 후속 정리를 미룰 때 | **언제까지인지 조건을 함께 적는다.** 예를 들어 다음 릴리스를 막는 조건으로 걸어둔다. 기한 없는 "나중에"는 실행되지 않는다 | MUST |
| 방어 코드가 과해 보일 때 | **그 상황이 실재하는지 테스트로 먼저 재현한다.** 재현되면 규모만 줄이고, 재현되지 않으면 근거를 남기고 걷어낸다. 추론만으로 판단했다가 틀린 사례가 DECISIONS 5-2에 있다 | MUST |
