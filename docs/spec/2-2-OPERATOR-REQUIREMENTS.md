# 2-2. 운영자 요구사항

이 문서는 메인테이너가 반복하는 운영 작업과 각 작업이 보장해야 하는 것, 확인 방법을 정한다.

방어 코드를 판단하는 테스트 규칙은 테스트 케이스에, 데이터 변경 절차와 손으로 적은 서비스 수는 데이터에, 버전 자리와 릴리스 절차는 릴리스에, 스토어 제출 절차는 스토어 제출에, 문의 폼의 조건은 계약에 있다. ([7-2-1 자동 테스트](7-2-TEST-CASES.md#7-2-1-자동-테스트), [6-2-5 변경 절차](6-2-DATA.md#6-2-5-변경-절차), [6-2-7 손으로 적은 서비스 수](6-2-DATA.md#6-2-7-손으로-적은-서비스-수), [7-5 릴리스](7-5-RELEASE.md), [7-6 스토어 제출](7-6-STORE.md), [5-3 Google Forms](5-CONTRACT.md#5-3-google-forms))

## 2-2-1 지켜야 할 사항

사람의 기억이 아니라 명령이 확인한다.

| 지키는 것 | 확인 | 기준 |
| --- | --- | --- |
| 데이터 무결성 | `npm run validate:data` | 오류 0건 |
| 랜딩 산출물 최신 | `npm run validate:landing-data` | 통과. 어긋나면 생성 명령을 안내하며 실패 |
| 아이콘 라이트와 다크 짝 | `npm run validate:dark-icons` | 모든 짝이 있고 다크 벌이 최신이며 배경이 투명 |
| 기존 동작 회귀 | `npm test` | 전부 통과 |
| 두 벌 구현의 일치 | `npm test` | 검색 순위와 문의 폼 필드가 확장과 랜딩에서 같음<br>릴리스 노트의 `### Internal` 제거 규칙이 랜딩과 Firefox 제출 스크립트에서 같음 |
| 패키지 재현성 | `npm test` | 같은 소스에서 바이트 단위로 같은 ZIP |
| 릴리스 무결성 | 릴리스 워크플로, 스토어 제출 워크플로 | 태그와 매니페스트 버전 일치, 릴리스 노트 파일 존재. 실패하면 릴리스도 스토어 제출도 만들어지지 않음 |
| 위 npm 명령 전부 | `npm run build` | CI가 PR마다 같은 명령을 실행 |

화면 동작, 스토어 심사, 교내 사이트의 실제 작동 여부는 사람이 확인한다.

## 2-2-2 서비스 데이터 갱신

교내 웹서비스는 메인테이너가 통제할 수 없는 곳에서 바뀐다. 주소가 바뀌고 서비스가 사라지며 학과가 신설되거나 통폐합된다. 데이터 갱신은 LinKHU에서 가장 잦은 운영 작업이다.

| 규칙 | 이유 |
| --- | --- |
| 서비스 목록의 원본은 `src/data.js` 하나 | 화면과 랜딩 산출물이 모두 이 목록에서 나온다 |
| `docs/supported-services.md`는 손으로 옮긴 사본이다. 데이터를 바꾸면 같은 PR에서 고친다 | 생성하거나 검사하는 스크립트가 없어 빠뜨리면 그대로 어긋난다 |
| `npm run validate:data` 결과를 PR 본문에 남김 | 무엇을 확인했는지 다시 확인할 수 있어야 한다 |
| 한 PR에서 아이콘을 한꺼번에 많이 바꾸지 않음 | 되돌릴 단위를 작게 유지한다 |

데이터를 바꾸면 랜딩 산출물과 문서에 적힌 서비스 수도 함께 바뀐다. 랜딩 산출물을 빠뜨리면 CI가 막는다. 서비스 수를 빠뜨리면 틀린 숫자가 화면과 문서에 그대로 남는다.

## 2-2-3 릴리스

| 보장할 것 | 기준 |
| --- | --- |
| 릴리스 노트 | 사용자에게 보이는 변경은 `### Features`와 `### Fixes`에, 내부 변경은 `### Internal`에 따로 적는다. `### Internal`은 랜딩과 Firefox 버전 노트에서 빠지고 GitHub Release 본문에는 그대로 실린다 |
| 배포 범위 | 태그 push는 GitHub Release까지만 만든다. 스토어 제출은 메인테이너가 따로 시작한다 |

<br>

## 2-2-4 스토어 배포

LinKHU는 Chrome Web Store, Firefox Add-ons, Whale Store 세 곳에 배포한다. 스토어마다 심사 주기가 달라 같은 버전도 공개 시점이 다르다.

| 보장할 것 | 기준 |
| --- | --- |
| 잘못된 제출 방지 | 자동 제출은 Chrome과 Firefox에만 있다. `main`에서 확인 문자열을 입력해야 시작되고, 태그가 `main`의 최신 커밋을 가리킬 때만 제출된다 |
| 매니페스트 변경 | 세 스토어의 호환성과 권한 범위를 모두 확인한다. Firefox는 `strict_min_version`과 데이터 수집 선언이 있어 영향을 가장 크게 받는다 |
| 권한 추가 | 세 스토어 모두에서 재심사 사유가 되고 기존 사용자에게 권한 승인 요구가 뜬다 |

<br>

## 2-2-5 문의 대응

| 경로 | 대상 | 위치 |
| --- | --- | --- |
| 문의하기 폼 | GitHub 계정이 없는 사용자 | 팝업, 설정, 랜딩. Google Forms로 수집 |
| GitHub Issue | 개발자와 기여자, 버그 제보와 서비스 요청을 하는 사용자 | 저장소. 랜딩 문의 창이 버그 제보 경로로 안내함 |

| 지킬 것 | 이유 |
| --- | --- |
| 확장에서 문의 폼이 설정되지 않았으면 보내기를 누를 때 준비 중 안내 문구를 보인다 | 폼 없이 보낸 문의가 사라지지 않는다 |
| 팝업, 설정, 랜딩이 같은 폼과 같은 본문, 이메일, 유형 필드를 쓴다 | 경로가 갈라지면 수집 결과가 나뉜다 |
| 문의 유형을 별도 질문으로 수집한다 | 응답 시트에서 유형으로 문의를 거를 수 있다 |
| 문의가 실제로 접수됐는지는 응답 시트로 확인한다 | 화면은 응답을 읽을 수 없어 요청을 보낸 것까지만 안다 |

## 2-2-6 기여 관리

LinKHU는 공개 저장소이며 외부 기여를 받는다.

| 규칙 | 내용 |
| --- | --- |
| 순서 | 모든 변경은 이슈, 브랜치, PR 순으로 진행 |
| PR 본문 | 저장소 템플릿을 쓰고 검증 결과를 다시 확인할 수 있게 적음 |
| 방향이 다른 PR | 기능이 동작하더라도 제품의 디자인 방향과 어긋나면 반려할 수 있음 |
| 반려할 때 | 반려 이유와 다시 낼 수 있는 조건을 남김 |

**1. 포크에서 온 PR의 CI**

저장소는 처음 기여하는 사람의 포크 PR만 승인을 기다리게 설정되어 있다. 메인테이너가 실행을 승인해야 워크플로가 돈다. 한 번이라도 병합된 적 있는 기여자의 포크 PR은 승인 없이 바로 돈다.

승인은 외부 코드를 저장소의 워크플로 환경에서 실행시키는 일이다. CI의 `npm run build`는 테스트를 거쳐 `src/`와 `landing/`의 JavaScript를 Node.js에서 실행한다. 승인 전에 변경 파일 목록을 확인하고, 아래 경로가 바뀌었으면 내용을 읽은 뒤 승인한다.

| 바뀐 곳 | 읽어야 하는 이유 |
| --- | --- |
| `package.json` | 실행되는 스크립트와 의존성이 바뀐다 |
| `scripts/` | 검증, 생성, 패키징 단계에서 실행된다 |
| `tests/`와 새로 생긴 `*.test.js` | 테스트 러너가 찾아서 실행한다 |
| `src/`, `landing/`의 JavaScript | 테스트와 데이터 검증이 불러와 실행한다 |
| `.github/` | 워크플로 정의가 바뀐다 |

Markdown 문서, 이미지, CSS, HTML만 바뀐 PR은 바로 승인해도 된다.

포크 PR의 워크플로는 읽기 권한만 갖고 저장소 비밀값을 받지 않는다. 그래서 승인은 처음 기여하는 사람에게만 요구한다. 비밀값을 쓰는 워크플로(`pull_request_target` 등)를 PR에서 돌리게 되면 모든 외부 기여자의 PR을 승인제로 바꾼다.

<br>

**2. 응대 방침**

| 상황 | 대응 |
| --- | --- |
| 한 줄짜리 사소한 수정 | 기여자에게 수정을 다시 요청하지 않는다. 병합한 뒤 메인테이너가 이슈로 등록해 직접 정리한다 |
| 코드 스타일 지적 | 병합 조건이 아니라 정보성 코멘트로 남긴다 |
| 후속 정리를 미룰 때 | 언제까지인지 조건을 함께 적는다. 예를 들어 다음 릴리스를 막는 조건으로 건다 |
| 방어 코드가 과해 보일 때 | 테스트 케이스의 자동 테스트 규칙대로 막는 상황을 먼저 재현해 보고 판단한다 |
