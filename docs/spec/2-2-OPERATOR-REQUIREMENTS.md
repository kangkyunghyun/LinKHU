# 2-2 운영자 요구사항

이 문서는 운영 주체, 운영에서 지켜야 할 기준과 확인 방법, 메인테이너가 반복하는 운영 작업과 각 작업이 보장해야 하는 것을 정한다.

방어 코드를 판단하는 테스트 규칙은 테스트 케이스에, 데이터 변경 절차와 손으로 적은 서비스 수는 데이터에, 버전 자리와 릴리스 절차는 릴리스에, 스토어 제출 절차는 스토어 제출에, 문의 폼의 조건은 계약에 있다. ([7-2-1 자동 테스트](7-2-TEST-CASES.md#7-2-1-자동-테스트), [6-2-5 변경 절차](6-2-DATA.md#6-2-5-변경-절차), [6-2-7 손으로 적은 서비스 수](6-2-DATA.md#6-2-7-손으로-적은-서비스-수), [7-5 릴리스](7-5-RELEASE.md), [7-6 스토어 제출](7-6-STORE.md), [5-4 Google Forms](5-CONTRACT.md#5-4-google-forms))

<br>

### 2-2-1 운영 주체

| 주체 | 맡는 일 |
| --- | --- |
| 메인테이너 | 운영 요구사항을 정하고 결과를 확인함<br>교내 서비스가 바뀌면 데이터를 고쳐 내보냄<br>릴리스, 스토어 제출, 문의 대응, 외부 기여 검토 |
| 기여자 | 이슈와 PR로 데이터 수정과 기능을 제안함. 병합 여부는 메인테이너가 정함 |

<br>

### 2-2-2 핵심 기준 요약

| 구분 | 지키는 것 | 확인 | 기준 |
| --- | --- | --- | --- |
| 데이터 | 데이터 무결성 | 데이터 검증 | 오류 0건 |
| 데이터 | 랜딩 산출물 최신 | 랜딩 산출물 검사 | 통과. 어긋나면 생성 방법을 안내하며 실패 |
| 데이터 | 아이콘 라이트와 다크 짝 | 다크 아이콘 짝 검증 | 모든 짝이 있고 다크 벌이 최신이며 배경이 투명 |
| 코드 | 기존 동작 회귀 | 자동 테스트 | 전부 통과 |
| 코드 | 두 벌 구현의 일치 | 자동 테스트 | 검색 순위와 문의 폼 필드가 확장과 랜딩에서 같음<br>릴리스 노트의 `### Internal` 제거 규칙이 랜딩과 Firefox 제출에서 같음 |
| 배포 | 패키지 재현성 | 자동 테스트 | 같은 소스에서 바이트 단위로 같은 ZIP |
| 배포 | 릴리스 무결성 | 릴리스 워크플로, 스토어 제출 워크플로 | 태그와 매니페스트 버전 일치, 릴리스 노트 존재. 실패하면 릴리스도 스토어 제출도 만들어지지 않음 |
| 전체 | 위 확인 전부 | 빌드 | CI가 PR마다 같은 빌드를 실행 |
| 사람 | 화면 동작, 스토어 심사, 교내 사이트의 실제 작동 | 수동 검증 | 수동 검증 항목 통과 |

<br>

### 2-2-3 서비스 데이터 갱신

교내 웹서비스는 메인테이너가 통제할 수 없는 곳에서 바뀐다. 데이터 갱신이 가장 잦은 운영 작업이다.

| 규칙 | 이유 |
| --- | --- |
| 지원 서비스 목록의 원본은 하나 | 확장 화면과 랜딩 산출물이 모두 이 목록에서 나옴 |
| 지원 서비스 목록 문서는 손으로 옮긴 사본. 데이터를 바꾸면 같은 PR에서 고침 | 생성하거나 검사하는 도구가 없음 |
| 데이터 검증 결과를 PR 본문에 남김 | 무엇을 확인했는지 다시 확인할 수 있어야 함 |
| 한 PR에서 아이콘을 한꺼번에 많이 바꾸지 않음 | 되돌릴 단위를 작게 유지함 |

| 데이터를 바꾸면 함께 바뀌는 것 | 빠뜨렸을 때 |
| --- | --- |
| 랜딩 산출물 | CI가 막음 |
| 문서와 화면에 적힌 서비스 수 | 틀린 숫자가 그대로 남음 |

<br>

### 2-2-4 릴리스

| 보장할 것 | 기준 |
| --- | --- |
| 릴리스 노트 | 사용자에게 보이는 변경은 `### Features`와 `### Fixes`에, 내부 변경은 `### Internal`에 적음<br>`### Internal`은 랜딩과 Firefox 버전 노트에서 빠지고 GitHub Release 본문에는 실림 |
| 배포 범위 | 태그 push는 GitHub Release까지만 만듦. 스토어 제출은 메인테이너가 따로 시작함 |

<br>

### 2-2-5 스토어 배포

| 보장할 것 | 기준 |
| --- | --- |
| 배포처 | Chrome Web Store, Firefox Add-ons, Whale Store |
| 잘못된 제출 방지 | 자동 제출은 Chrome과 Firefox에만 있음. `main`에서 확인 문자열을 입력해야 시작되고, 태그가 `main`의 최신 커밋을 가리킬 때만 제출됨 |
| 매니페스트 변경 | 세 스토어의 호환성과 권한 범위를 모두 확인함. Firefox는 최소 버전과 데이터 수집 선언이 있어 영향을 가장 크게 받음 |
| 권한 추가 | 세 스토어 모두에서 재심사 사유가 되고 기존 사용자에게 권한 승인 요구가 뜸 |

<br>

### 2-2-6 문의 대응

| 경로 | 대상 | 위치 |
| --- | --- | --- |
| 문의하기 폼 | GitHub 계정이 없는 사용자 | 팝업, 설정, 랜딩. Google Forms로 수집 |
| GitHub Issue | 개발자와 기여자, 버그 제보와 서비스 요청을 하는 사용자 | 저장소. 랜딩 문의 창이 버그 제보 경로로 안내함 |

| 지킬 것 | 이유 |
| --- | --- |
| 확장에서 문의 폼이 설정되지 않았으면 보내기를 누를 때 준비 중 안내 문구를 보임 | 폼 없이 보낸 문의가 사라지지 않음 |
| 팝업, 설정, 랜딩이 같은 폼과 같은 본문, 이메일, 유형 필드를 씀 | 경로가 갈라지면 수집 결과가 나뉨 |
| 문의 유형을 별도 질문으로 수집함 | 응답 시트에서 유형으로 거를 수 있음 |
| 문의 접수 여부는 응답 시트로 확인함 | 화면은 응답을 읽을 수 없어 요청을 보낸 것까지만 앎 |

### 2-2-7 기여 관리

| 규칙 | 내용 |
| --- | --- |
| 순서 | 모든 변경은 이슈, 브랜치, PR 순으로 진행 |
| PR 본문 | 저장소 템플릿을 쓰고 검증 결과를 다시 확인할 수 있게 적음 |
| 방향이 다른 PR | 기능이 동작하더라도 제품의 디자인 방향과 어긋나면 반려할 수 있음 |
| 반려할 때 | 반려 이유와 다시 낼 수 있는 조건을 남김 |

**1. 포크에서 온 PR의 CI**

| 기여자 | 워크플로 실행 |
| --- | --- |
| 처음 기여하는 사람 | 메인테이너가 실행을 승인한 뒤 |
| 한 번이라도 병합된 적 있는 사람 | 승인 없이 바로 |

승인은 외부 코드를 저장소의 워크플로 환경에서 실행시키는 일이다. CI는 테스트와 데이터 검증에서 확장과 랜딩의 JavaScript를 Node.js로 실행한다. 승인 전에 변경 파일을 보고 아래가 바뀌었으면 내용을 읽는다.

| 바뀐 곳 | 읽어야 하는 이유 |
| --- | --- |
| 패키지 설정 | 실행되는 스크립트와 의존성이 바뀜 |
| 검증, 생성, 패키징 스크립트 | 빌드 단계에서 실행됨 |
| 테스트 파일, 새로 생긴 테스트 파일 | 테스트 러너가 찾아서 실행함 |
| 확장과 랜딩의 JavaScript | 테스트와 데이터 검증이 불러와 실행함 |
| 워크플로 정의 | CI 동작이 바뀜 |
| Markdown, 이미지, CSS, HTML만 | 바로 승인해도 됨 |

| 전제 | 바뀌면 |
| --- | --- |
| 포크 PR의 워크플로는 읽기 권한만 갖고 저장소 비밀값을 받지 않음 | 비밀값을 쓰는 워크플로를 PR에서 돌리게 되면 모든 외부 기여자의 PR을 승인제로 바꿈 |

<br>

**2. 응대 방침**

| 상황 | 대응 |
| --- | --- |
| 한 줄짜리 사소한 수정 | 기여자에게 수정을 다시 요청하지 않음. 병합한 뒤 메인테이너가 이슈로 등록해 직접 정리함 |
| 코드 스타일 지적 | 병합 조건이 아니라 정보성 코멘트로 남김 |
| 후속 정리를 미룰 때 | 언제까지인지 조건을 함께 적음. 예를 들어 다음 릴리스를 막는 조건으로 걺 |
| 방어 코드가 과해 보일 때 | 막는 상황을 테스트로 먼저 재현해 보고 판단함 |
