# 2-1. 사용자 스토리

이 문서는 학생 사용자가 LinKHU로 무엇을 하려고 하는지를 스토리 단위로 고정한다. 각 스토리에는 현재 코드가 실제로 보장하는 완료 조건을 붙였다. 화면 동작을 바꾸는 PR은 여기 적힌 완료 조건을 깨지 않았는지 확인해야 한다.

여기 적힌 것은 "사용자가 기대하는 결과"이고, 그 결과를 만드는 구조는 4-3 아키텍처에, 실행 순서는 6-1 인터랙션에 있다. 검증 방법은 7-2 테스트 케이스에 있다.

```text
§2-1-1   팝업 열기            툴바와 단축키로 진입
§2-1-2   바로가기 이동         클릭, 배경 탭, 휠 클릭
§2-1-3   검색                 이름·id·카테고리로 찾기
§2-1-4   숫자 단축키           손을 마우스로 옮기지 않고 열기
§2-1-5   내 바로가기 구성       설정 페이지에서 고르고 정렬
§2-1-6   버전 확인과 문의       업데이트 안내, 의견 보내기
§2-1-7   홈페이지에서 변경 이력  릴리스마다 무엇이 바뀌었는지
```

## 2-1-1 팝업 열기

> 학생으로서, 브라우저 어디에 있든 교내 서비스 목록을 즉시 열고 싶다.

| 여는 방법 | 동작 |
| --- | --- |
| 툴바의 LinKHU 아이콘 | 누르면 팝업이 열린다 |
| 키보드 단축키 | 기본값 `Ctrl+Shift+L` (macOS `Command+Shift+L`). 매니페스트의 `_execute_action`에 **제안값으로** 등록되어 있다 |

브라우저가 단축키를 자동 등록하지 않았을 수 있으므로, 두 화면이 각각 안내를 맡는다.

| 화면 | 언제 보이나 | 무엇을 안내하나 |
| --- | --- | --- |
| 설정 | 단축키가 비어 있을 때 (MUST) | 펼쳐진 안내 박스. Chromium 기반은 내부 주소에 `/extensions/shortcuts`를 붙이는 **규칙**과 Chrome·Whale·Aside 예시, Firefox는 `about:addons` 경로 |
| 팝업 | 비어 있고 **사용자가 닫지 않았을 때** (MUST) | 헤더 아래 한 줄. `설정에서 지정`은 설정의 안내 박스를 새 탭으로 열고, 닫기는 이후에도 안내를 숨긴다. 저장에 실패하면 안내를 되살리고 상태 줄로 알린다 |

노출 지점과 주소 안내 방식의 근거는 DECISIONS 3-4에 있다.

> **제약**: 매니페스트의 단축키는 **제안일 뿐 보장이 아니다.** 다른 프로그램이 이미 쓰는 조합이면 등록되지 않고, 확장이 그 조합을 빼앗을 수도 없다. 따라서 "단축키가 동작하지 않는다"는 정상 범위의 상태이며, 제품은 이를 **감지해 안내하는 것까지만** 할 수 있다. 근거와 대안 검토는 DECISIONS 3-3에 있다.

**완료 조건**

| 상황 | 기대 |
| --- | --- |
| 팝업이 열렸다 | 저장된 `userOrder` 순서대로 카드가 렌더링된다 |
| `userOrder`가 없다 | 기본 목록 10개가 이름 가나다순으로 표시된다 (§3-4) |
| 표시할 항목이 없다 | 빈 상태 메시지를 보여준다 |

## 2-1-2 바로가기 이동

> 학생으로서, 목록에서 서비스를 눌러 바로 이동하고 싶다. 여러 개를 한꺼번에 열어두고 싶을 때도 있다.

세 가지 입력을 구분해서 처리한다.

| 입력 | 새 탭 | 팝업 |
| --- | --- | --- |
| 일반 클릭 | **활성 상태**로 연다 | 닫는다 |
| `Ctrl`/`Cmd` + 클릭 | **배경**으로 연다 | **유지한다** |
| 휠(가운데) 클릭 | **배경**으로 연다 | **유지한다** |

`Ctrl`/`Cmd` 클릭과 휠 클릭에서 팝업이 유지되는 것이 핵심이다. 학기 초처럼 여러 서비스를 연달아 열어야 할 때 팝업을 다시 열지 않아도 된다.

카드는 `<a href>`로 만들되 클릭 기본 동작은 막고 확장 API로 탭을 연다 (MUST). 팝업 안에서 링크가 그대로 열리면 팝업 화면 자체가 이동해버리기 때문이다.

**완료 조건**

| 상황 | 기대 |
| --- | --- |
| 세 가지 입력 | 위 표대로 동작한다 |
| 서비스 아이콘 로딩 실패 | 확장 기본 아이콘(`icons/icon48.png`)으로 대체되어 깨진 이미지가 보이지 않는다 |
| 같은 id가 중복 저장됨 | 카드는 한 번만 렌더링된다 |

## 2-1-3 검색

> 학생으로서, 목록을 눈으로 훑지 않고 이름을 입력해 찾고 싶다.

| 규칙 | 내용 |
| --- | --- |
| 대상 | 서비스 **이름, id, 카테고리** 세 가지 |
| 비교 방식 | 검색어와 대상 모두 소문자화(`ko-KR`)하고 공백 제거. "e campus"와 "ecampus"가 같다 |
| 범위 | `userOrder`가 아니라 `MASTER_SITE_LIST` **전체**. 담아두지 않은 서비스도 찾을 수 있어야 한다 |
| `/` 키 | 검색창으로 포커스 이동. 입력 요소 안이거나 조합 키가 눌린 상태면 동작하지 않는다 |
| `Enter` | 첫 번째 결과를 **현재 탭**에서 연다. 한글 조합 중(`isComposing`)에는 동작하지 않는다 (MUST) |

결과 정렬 우선순위는 다음과 같다 (MUST). 같은 점수 안에서는 `MASTER_SITE_LIST` 정의 순서를 유지한다.

| 점수 | 조건 |
| --- | --- |
| 0 | 이름이 검색어로 시작 |
| 1 | 이름에 검색어 포함 |
| 2 | id가 검색어로 시작 |
| 3 | id에 검색어 포함 |
| 4 | 카테고리에 검색어 포함 |

**완료 조건**

| 상황 | 기대 |
| --- | --- |
| 일치하는 결과가 없다 | 빈 상태 메시지를 보여준다 |
| 검색 입력을 빠르게 연타한다 | 이전 렌더 결과가 뒤늦게 덮어쓰지 않는다 |

## 2-1-4 숫자 단축키

> 학생으로서, 자주 쓰는 앞쪽 바로가기는 키보드만으로 열고 싶다.

| 규칙 | 내용 |
| --- | --- |
| 동작 | `1`~`9` 키로 화면에 보이는 순서대로 n번째 카드를 연다 |
| 동작하지 않는 조건 (MUST) | 입력 요소에 포커스가 있거나, `Ctrl`/`Alt`/`Cmd`가 함께 눌렸거나, 키가 눌린 채 반복 중일 때. 검색어에 숫자를 입력할 수 없게 되면 안 된다 |
| 열리는 방식 | 카드를 클릭한 것과 같은 경로를 타므로 §2-1-2의 일반 클릭과 같다 |

## 2-1-5 내 바로가기 구성

> 학생으로서, 내 전공과 학년에 맞는 서비스만 팝업에 두고 원하는 순서로 정렬하고 싶다.

설정 페이지는 두 열로 구성된다. 왼쪽은 담을 수 있는 전체 서비스를 카테고리별로 나눠 보여주고, 오른쪽은 내 바로가기다. 카테고리는 §3-2가 정한 여덟 개이며, 화면의 영역 순서도 그 목록 순서를 따른다.

**담기와 정렬**

| 조작 | 결과 |
| --- | --- |
| 왼쪽 목록 표시 | 이름 기준 한국어 정렬(`localeCompare("ko-KR")`) |
| 이미 담은 서비스 | 왼쪽에서 사라진다. 같은 항목이 양쪽에 동시에 보이지 않는다 |
| 오른쪽으로 드래그 | 담긴다 |
| 왼쪽으로 드래그 | 원래 카테고리 자리로 되돌아간다 |
| 오른쪽 안에서 드래그 | 순서가 바뀐다. 이 순서가 팝업 표시 순서다 |
| 드래그 중 스크롤 영역 가장자리 40px 안 | 자동으로 스크롤한다 (MUST). 이 보조가 없으면 학과 69개 목록에서 상단으로 항목을 옮길 수 없다 |
| 항목 끝의 링크 클릭 | 그 서비스를 **새 탭에서** 연다. 이름만 보고 담을지 정하지 않아도 된다. 양쪽 목록에 같은 형태로 붙는다 |
| 링크에서 시작한 드래그 | **취소한다** (MUST). 링크를 끌었을 뿐인데 항목이 딸려가면 안 된다 |

**좁혀 보기**

설정 페이지에도 검색창이 있고 `/` 단축키가 동작한다. 검색창 아래 카테고리 필터는 목록이 길어 검색만으로는 좁히기 어려운 경우를 위한 보조 수단이다.

| 규칙 | 내용 |
| --- | --- |
| 아무 칩도 고르지 않음 | **전체를 표시한다.** 전부 끄는 것과 필터를 걸지 않은 것이 같은 상태다. 별도 "전체" 버튼을 두지 않는다 |
| 필터 + 검색어 | **AND**로 걸린다 (MUST). 필터로 뺀 카테고리는 검색어가 일치해도 나오지 않는다 |
| 필터 상태 저장 | 하지 않는다. 페이지를 다시 열면 전체 표시로 돌아온다 |
| 결과가 없는 카테고리 | 그룹을 숨긴다. 전체 결과가 0건이면 빈 상태 문구 |
| 영향 범위 | **왼쪽 목록의 표시에만** (MUST). 오른쪽 '내 바로가기'는 영향을 받지 않는다 — 저장 순서를 오른쪽에서 읽으므로, 왼쪽에서 숨겨진 항목 때문에 저장 데이터가 바뀌어서는 안 된다 |

**완료 조건**

| 상황 | 기대 |
| --- | --- |
| 드래그만 했다 | **저장되지 않는다.** 저장 버튼을 눌러야 저장된다 |
| 검색어·필터가 걸린 상태로 저장했다 | 저장되는 순서가 필터를 걸지 않았을 때와 같다 |
| 저장 성공 / 실패 | 각각 알림을 띄운다. 실패를 조용히 넘기지 않는다 (MUST) |
| 새로고침하거나 팝업을 다시 열었다 | 그 순서가 유지된다 |

## 2-1-6 버전 확인과 문의

> 학생으로서, 내가 쓰는 버전이 최신인지 알고 싶고, 불편한 점을 개발자에게 알리고 싶다.

| 규칙 | 내용 |
| --- | --- |
| 현재 버전 | 팝업 헤더에 `v{version}` 형태로 표시 |
| 업데이트 안내 | 최신 릴리스보다 낮으면 링크를 함께 보여준다 |
| 링크가 가는 곳 | 사용자의 브라우저에 맞는 스토어 (Whale / Firefox / 그 외 Chrome). 스토어로 설치하지 않은 개발 모드는 GitHub 릴리스 |
| 조회 실패 | **팝업 사용을 막지 않는다** (MUST). 안내가 보이지 않을 뿐 바로가기는 그대로 열린다. 조회 주기와 캐싱은 §5-2가 정한다 |
| 문의하기 | 팝업과 설정 페이지 하단. GitHub 계정 없이 의견을 보낼 수 있다. 답변받을 이메일은 선택 입력 |

**완료 조건**

| 상황 | 기대 |
| --- | --- |
| 문의 내용이 비어 있다 | 전송하지 않고 입력을 요구한다 |
| 이메일을 입력했는데 `@`가 없다 | 전송하지 않고 확인을 요구한다 |
| 전송 중 | 버튼을 비활성화하고, 성공·실패 결과를 문구로 알린다 |

## 2-1-7 홈페이지에서 변경 이력 보기

> 학생으로서, 설치하기 전이나 업데이트된 뒤에 무엇이 바뀌었는지 홈페이지에서 보고 싶다.

| 규칙 | 내용 |
| --- | --- |
| 위치 | 홈페이지 하단 **업데이트** 섹션. nav와 푸터에서 갈 수 있다 |
| 출처 | GitHub Releases에서 받아 그린다. 릴리스를 내면 홈페이지가 저절로 따라오므로, 사용자가 보는 이력과 실제 릴리스가 어긋나지 않는다 |
| `### Internal` | **보이지 않는다** (MUST). 내부 정리 기록은 사용자가 겪는 변화가 아니다 |
| 펼침 | 최신 릴리스만 펼쳐져 있고 나머지는 제목 줄로 접힌다. 변경 이력이 소개 흐름보다 길어지지 않게 한다 |

**완료 조건**

| 상황 | 기대 |
| --- | --- |
| 목록을 받지 못했다 | **섹션이 통째로 보이지 않는다** (MUST). 빈 상자를 남기지 않는다. GitHub 릴리스 링크가 대체 경로다 |
| 릴리스 본문에 마크업이 들어 있다 | 글자로 보인다. 본문은 외부 API 응답이다 |
| 목록을 받지 못해도 | 홈페이지의 나머지 부분은 그대로 동작한다 |

설계 근거는 DECISIONS 5-3에 있다.
