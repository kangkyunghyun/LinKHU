# 4-3. 테마

시스템·라이트·다크 세 모드를 어떻게 정하고, 어떻게 저장하고, 어떤 값으로 그리는지를 고정한다. **확장과 랜딩이 같은 세 모드를 쓰되, 저장소가 달라 서로 동기화되지 않는다.**

```text
§4-3-1   테마 모드               시스템·라이트·다크 세 가지
§4-3-2   저장                    즉시 반영과 실패 시 되돌리기
§4-3-3   선택 UI와 반영 범위     어디에 두고 무엇까지 바뀌나
§4-3-4   구현 방식과 토큰 계약   표식과 값 스왑
§4-3-5   대비 기준               테마별 최소 대비
§4-3-6   랜딩 다크 팔레트        랜딩이 따르는 값
```

## 4-3-1 테마 모드

테마 모드는 세 단계다.

| 값 | 동작 |
| --- | --- |
| `system` | 운영체제·브라우저의 `prefers-color-scheme`를 따른다 |
| `light` | 항상 라이트 |
| `dark` | 항상 다크 |

- 기본값은 `system`이다. 사용자가 아무것도 고르지 않았으면 시스템 설정을 따른다.
- 명시적 `light`·`dark` 선택은 시스템 설정보다 **우선한다**.
- `system`을 선택한 상태에서 시스템 테마가 바뀌면, 열려 있는 화면에 즉시 반영한다. `prefers-color-scheme` 미디어 쿼리 변경을 구독한다.

## 4-3-2 저장

| 항목 | 확장 | 랜딩 |
| --- | --- | --- |
| 저장소 | `chrome.storage.local` | 브라우저의 도메인별 영구 저장소 |
| 키 | `themeMode` | `themeMode` |
| 유효값 | `"system"` \| `"light"` \| `"dark"` | 같다 |
| 기본값 | `"system"` | `"system"` |
| 읽기 | 비동기 | 동기 |

**두 저장소는 서로를 보지 못한다.** 랜딩은 확장 저장소를 읽을 수 없고, 확장은 웹페이지 저장소를 읽지 않는다. 같은 기기에서 확장은 다크, 홈페이지는 라이트일 수 있다. **이것은 결함이 아니라 랜딩이 확장의 부속물이 아닌 별개 문서라는 사실의 결과다.**

- 저장에는 기존 `storage` 권한을 재사용한다. **새 권한을 추가하지 않는다**. 권한 추가는 세 스토어 전체의 재심사 사유다.
- 값이 없거나, 문자열이 아니거나, 유효값 목록에 없으면 `system`으로 폴백한다. 폴백 시 저장된 잘못된 값을 지우거나 덮어쓰지 않아도 된다 — 읽기 시점 폴백으로 충분하다.
- 테마 저장은 즉시 반영형이다. 내 바로가기 순서와 달리 별도 저장 버튼을 두지 않는다. 되돌리기 비용이 낮고 결과를 즉시 눈으로 확인하는 설정이기 때문이다.

**저장 실패 시 동작**

저장 실패는 `chrome.runtime.lastError`로 확인하고 다음과 같이 처리한다.

- **적용된 테마를 되돌린다**. 저장에 실패했는데 화면만 새 테마로 남아 있으면, 다음 실행에서 조용히 이전 테마로 돌아간다. 사용자는 자기 설정이 무시당했다고 느낀다.
- **선택 UI의 표시 상태도 함께 되돌린다**. 화면과 컨트롤이 어긋나면 안 된다.
- 실패를 사용자에게 알린다. 조용히 되돌리면 왜 바뀌지 않는지 알 수 없다. **알림 경로는 화면마다 있어야 한다** — 토글만 있는 팝업에서도 실패가 보여야 한다.
- 되돌릴 기준값은 **마지막으로 저장이 확인된 모드**다. 저장 성공 콜백과 초기 읽기 성공에서만 이 값을 갱신한다.

**랜딩도 같은 규칙을 따른다.** 저장이 동기라 실패를 예외로 확인한다는 점만 다르고, 되돌리기와 알림은 같다.

> **정정**: 이전 스펙은 되돌릴 기준을 "적용 직전의 유효한 모드"로 규정했고, 그 문장이 실제 결함을 유도했다. 이 설정은 낙관적으로 먼저 적용하고 나중에 저장하므로, "적용 직전의 모드"는 저장된 적 없는 중간값일 수 있다.
>
> 재현: 저장소가 `system`인 상태에서 토글로 `dark`를 요청하고(A, 적용 직전 = `system`) 곧바로 `light`를 요청하면(B, 적용 직전 = `dark`), 둘 다 실패했을 때 A는 낡은 요청이라 폐기되고 B가 자기 기준인 `dark`로 되돌린다. **저장소는 `system`인데 화면은 `dark`가 된다.** 다시 열면 `system`으로 돌아가므로 사용자에게는 설정이 무시된 것처럼 보인다.
>
> "적용 직전"은 **화면 상태**의 이력이고 "저장이 확인된"은 **저장소 상태**의 이력이다. 롤백의 목적은 화면을 저장소와 일치시키는 것이므로 기준은 후자여야 한다.

## 4-3-3 선택 UI와 반영 범위

**테마 컨트롤은 순환 토글 하나다**. 팝업과 설정 페이지가 **같은 컨트롤을 쓴다.** 화면마다 다른 컨트롤을 두지 않는다.

| 화면 | 두는 것 |
| --- | --- |
| 팝업 | 헤더의 순환 토글 하나 |
| 설정 페이지 | 헤더의 순환 토글 하나 |
| 랜딩 | 헤더의 순환 토글 하나 |

- **누르면 `system` → `light` → `dark` → `system` 순으로 순환한다**. 세 모드를 모두 거치므로 별도의 3단계 선택 없이도 `system`에 접근할 수 있다.
- **`system`도 저장 가능한 선택이다**. 순환이 `system`에 도달하면 그 값을 저장한다. 저장소를 비우는 것이 아니다.
- **저장 경로는 하나다**. 순환은 다음 모드를 계산하는 방식만 다를 뿐, 저장·롤백·경쟁 가드·문서 간 동기는 모두 같은 경로를 지난다.
- 선택 결과는 **팝업과 설정 페이지 모두**에 반영한다. 설정에서 바꾸고 팝업을 열면 이미 적용되어 있어야 한다.
- **랜딩도 같은 순환 토글을 둔다**. 다만 확장 저장소를 읽을 수 없어 자기 저장소에 따로 보관한다. 확장에서 고른 모드와 랜딩에서 고른 모드는 서로 옮겨가지 않는다.

**동시에 열려 있을 때**

설정 페이지는 탭으로 열리므로 팝업과 **동시에 떠 있을 수 있다.** 각 문서가 초기화 때 한 번만 저장소를 읽으면, 한쪽에서 바꾼 값이 다른 쪽에 반영되지 않아 두 화면이 갈라진다.

- **저장소 변경을 구독해 열려 있는 모든 문서를 갱신한다**. 테마·토글 아이콘·레이블이 모두 따라온다.
- 받은 값은 **정규화한 뒤** 적용한다. 다른 문서가 쓴 값도 손상돼 있을 수 있다.
- **진행 중인 자기 요청이 있으면 외부 값으로 덮지 않는다**. 그 요청의 결과가 최종이다. 덮으면 사용자가 방금 고른 값이 되돌아간다.

**표시 상태 갱신 시점**

한쪽을 바꾸면 다른 쪽 표시가 **즉시** 갱신되어야 한다. 저장은 비동기이므로 저장 완료를 기다리면 그사이 두 컨트롤이 어긋난다.

- **낙관적으로 적용하는 시점에 구독자에게 알린다**. 저장 콜백을 기다리지 않는다.
- 저장에 실패해 되돌리면 **다시 알린다**. 표시가 되돌아간 값과 맞아야 한다.

**팝업 토글의 제약**

- 헤더 영역에 **아이콘 버튼 하나**로 둔다. 레이블 텍스트나 추가 컨트롤을 붙이지 않는다.
- 검색창과 바로가기 격자의 크기·간격을 바꾸지 않는다. 레이아웃 변경은 헤더에 한정한다.

**아이콘과 접근성**

- 아이콘은 **현재 모드**를 보여준다. `system`은 모니터, `light`는 해, `dark`는 달.

| 모드 | 아이콘 |
| --- | --- |
| `system` | monitor |
| `light` | sun |
| `dark` | moon |

- **순환 토글은 다음 모드가 버튼에 드러나지 않는다.** 다음 장치로 보완한다.
  - `aria-label`과 `title`에 **현재 모드와 다음 모드를 함께** 담는다. 예: `테마: 시스템 설정. 누르면 라이트`
  - 모드가 바뀌면 레이블과 `title`을 갱신한다.
  - 바뀐 결과를 `role="status"` 라이브 영역으로 알린다.
- 아이콘만 있는 버튼이므로 **스크린 리더가 읽을 텍스트를 반드시 제공한다.**
- **`aria-pressed`를 쓰지 않는다.** 눌림/안 눌림 두 상태를 뜻하는데 실제 모드는 세 가지라 의미가 어긋난다.
- 키보드 포커스 표시가 보여야 한다.

**초기 적용 시점**

"깜빡임이 없어야 한다"는 눈으로 판정할 수 없으므로 측정 가능한 조건으로 대신한다.

- **테마를 나타내는 표식(속성 또는 클래스)이 첫 페인트 전에 문서 루트에 적용되어 있어야 한다**. 즉 테마를 결정하는 코드가 본문 렌더링을 유발하는 스타일시트·마크업보다 먼저 실행되어야 한다.
- 검증 방법: 첫 페인트 시점의 문서 루트에 테마 표식이 있는지 확인한다. `DOMContentLoaded` 이후에 표식이 붙는 구조는 이 조건을 만족하지 않는다.
- 저장소 읽기는 비동기이므로, 저장된 모드를 읽기 전에도 **시스템 설정 기준으로 먼저 칠한다**. 저장 값이 도착하면 그때 보정한다. 기본값이 `system`이므로 대부분의 경우 보정 자체가 필요 없다.
- 이 조건을 만족하면 남는 전환은 `system` 이외를 고른 사용자에 한정되며, 그 경우에도 표식 교체 한 번으로 끝난다.

## 4-3-4 구현 방식과 토큰 계약

- 다크 테마는 **토큰 값 스왑만으로** 구현한다. 확장은 `src/theme.css`, 랜딩은 자기 스타일시트가 같은 방식을 쓴다.
- **어느 테마로 그릴지는 문서 루트의 표식이 정한다.** 확장과 랜딩 모두 `prefers-color-scheme` 미디어 쿼리로 다크를 표현하지 않는다 — 미디어 쿼리는 시스템 설정만 보므로 사용자가 고른 모드를 반영할 수 없다. 시스템 설정은 `system` 모드를 해석할 때만 읽는다.
- **표식이 없으면 라이트로 그린다.** 표식은 스크립트가 붙이므로 스크립트가 실행되지 않으면 라이트가 된다. 랜딩은 서비스 목록·검색·변경 이력이 모두 스크립트로 그려지므로 같은 전제를 따른다.
- 레이아웃, 크기, 간격, 컴포넌트 구조, DOM 구조를 바꾸지 않는다. 다크 테마 때문에 카드 배치나 화면 구성이 달라지면 안 된다.
- 서비스 아이콘 이미지는 반전하거나 필터를 걸지 않는다. 아이콘 도안이 제각각이라 일괄 반전은 결과를 예측할 수 없다. (고유 이미지 파일은 167개다. 서비스마다 전용 도안을 쓰는 것이 기본이지만, 6-2 데이터의 아이콘 공유 규칙에 따라 두 서비스가 한 파일을 가리킬 수도 있어 두 수가 항상 같지는 않다.)

**선행 작업: 색상 토큰 승격**

값 스왑만으로 다크 테마를 만들려면 **화면의 모든 색이 토큰을 거쳐야 한다.** 현재 브랜드 레드만 토큰화되어 있고 표면·텍스트·테두리 색은 하드코딩되어 있다. 다음 작업을 먼저 한다.

- `popup.css`의 `:root`에 있는 색 변수를 `theme.css`로 옮긴다.
- `options.css`에 하드코딩된 색을 토큰 참조로 바꾼다.
- **HTML 인라인 스타일의 색도 대상이다**. `popup.html`의 버전 표시 텍스트 색처럼 CSS 파일 밖에 있는 값이 남으면 다크에서 그 부분만 라이트로 남는다.
- 이 승격으로 토큰 규칙의 "중성 회색은 토큰화 대상이 아니다" 예외가 종료된다.

**토큰 계약**

아래가 다크 테마 구현이 만족해야 할 토큰 전체다. 이름과 값을 이대로 정의한다. 표에 없는 색을 새로 하드코딩하지 않는다.

*주색 계열*

**주색은 역할에 따라 두 토큰으로 나뉜다**. `--color-primary`는 텍스트·강조 전용, `--color-primary-fill`은 채움 배경 전용이다. 하나로 겸용하면 다크에서 채도를 잃는다.

| 토큰 | 라이트 | 다크 | 쓰이는 곳 |
| --- | --- | --- | --- |
| `--color-primary` | `#a40f16` | `#ff4d52` | **텍스트·강조 전용.** 로고, 강조 텍스트, 입력 포커스 테두리, 드래그 중 항목 테두리 |
| `--color-primary-fill` | `#a40f16` | `#c4121b` | **채움 배경 전용.** 기본 버튼, 배지, 브랜드 패널 배경 |
| `--color-primary-fill-strong` | `#790b11` | `#d7141e` | 채움의 hover 상태 |
| `--color-primary-strong` | `#790b11` | `#ff7175` | 강조 **텍스트·테두리**의 눌린·hover 상태 |
| `--color-primary-soft` | `#fdeeef` | `#2a1214` | 단축키 안내 박스 배경, 드래그 중 항목 배경 |
| `--color-primary-border` | `#f4bfc3` | `#5c1d20` | 안내 박스 테두리, 카드 hover 테두리 (장식) |
| `--color-primary-ring` | `rgba(164, 15, 22, 0.12)` | `rgba(255, 77, 82, 0.28)` | 입력 요소 focus ring |
| `--color-primary-shadow` | `rgba(164, 15, 22, 0.15)` | `rgba(0, 0, 0, 0.45)` | 카드 hover 그림자 |
| `--color-on-primary` | `#ffffff` | `#ffffff` | `--color-primary-fill` 위의 텍스트 |

hover 상태도 같은 이유로 갈린다. 다크에서 `--color-primary-strong`(`#ff7175`)을 채움에 쓰면 흰 글자가 2.67:1로 미달한다. **채움의 hover에는 `--color-primary-fill-strong`을 쓴다**.

라이트에서는 두 주색이 같은 값이다. 밝은 배경에서는 텍스트로도 채움으로도 `#a40f16`이 그대로 통하기 때문이다. 갈라지는 것은 다크에서다.

다크의 `--color-primary-shadow`가 색 계열을 벗어나는 것은 의도다. 어두운 배경에서는 붉은 그림자가 번짐으로 보이고 깊이를 만들지 못한다.

**`--color-on-primary`는 두 테마 모두 흰색이다**. `--color-primary-fill`이 양쪽 테마에서 모두 짙은 빨강이므로 글자색을 뒤집을 이유가 없다. 채움 위의 텍스트에는 반드시 이 토큰을 쓴다.

> 이전 스펙은 "다크에서는 어두운 글자를 쓴다"고 규정했다. 그때는 주색 하나가 채움까지 겸해서 다크 채움이 밝은 분홍(`#e08589`)이었고, 흰 글자가 2.66:1로 미달했기 때문이다. 채움 토큰이 분리되면서 그 전제가 사라졌으므로 **이 규칙은 폐기한다.** 다크에서 어두운 글자를 쓰지 않는다.

*중성 계열*

| 토큰 | 라이트 | 다크 | 쓰이는 곳 |
| --- | --- | --- | --- |
| `--color-surface` | `#f8f9fa` | `#0a0a0a` | 화면 바탕 |
| `--color-surface-raised` | `#ffffff` | `#161616` | 카드, 설정 컨테이너, 목록 항목 |
| `--color-surface-sunken` | `#f1f3f5` | `#101010` | 설정 페이지 열 배경, 빈 드롭 영역 |
| `--color-field` | `#ffffff` | `#1c1c1c` | 검색·문의 입력 요소 배경 |
| `--color-text` | `#333333` | `#f4f4f5` | 본문, 항목 이름 |
| `--color-text-muted` | `#666666` | `#a1a1aa` | 보조 설명, 빈 상태 문구, 푸터 링크, 드래그 손잡이 |
| `--color-border` | `#dddddd` | `#27272a` | 장식용 구분선, 카드 기본 테두리, 푸터 구분자 |
| `--color-border-strong` | `#8a8a8a` | `#71717a` | 정보를 전달하는 테두리 (빈 드롭 영역 점선, 스크롤바 손잡이) |
| `--color-shadow` | `rgba(0, 0, 0, 0.05)` | `rgba(0, 0, 0, 0.45)` | 카드·컨테이너 기본 그림자 |

*기능색*

| 토큰 | 라이트 | 다크 | 쓰이는 곳 |
| --- | --- | --- | --- |
| `--color-notice` | `#a8321f` | `#ffab91` | 새 버전 안내 링크 |

브랜드와 구분되는 주의 환기용 색이다. 승격 전에 쓰이던 `#ff6b6b`은 **다크 테마와 무관하게 라이트에서 이미 2.63:1로 기준 미달**이었다. 토큰화하면서 두 테마 모두 기준을 넘도록 값을 바꿨다.

**토큰으로 올릴 때는 값을 그대로 옮기지 않고 대비 기준을 먼저 만족시킨다.** 보조 텍스트는 `#666666`을 쓴다 — 더 밝은 회색은 4.5:1을 넘지 못한다.

`--color-primary-strong`은 라이트에서 주색보다 **어둡고** 다크에서는 **밝다**. 두 테마에서 모두 눌린 상태를 더 강하게 보이게 한다.

## 4-3-5 대비 기준

대비 요구는 요소의 성격에 따라 두 단계다.

| 대상 | 기준 |
| --- | --- |
| 일반 텍스트 | **4.5:1 이상** |
| 정보를 전달하는 비텍스트 요소 — 포커스 표시, 상태를 나타내는 테두리, 컨트롤 경계 | **3:1 이상** |
| 순수 장식 — 구분선, 카드 기본 테두리, 그림자 | 기준 없음 |

포커스 표시는 **키보드 사용자가 현재 위치를 알 수 있는 유일한 단서**이므로 장식으로 분류하지 않는다.

**실측값** (WCAG 2.1 상대 휘도 기준)

```text
[텍스트 — 4.5:1 기준]
라이트  본문   #333333  on raised  #ffffff   12.63 : 1
라이트  본문   #333333  on sunken  #f1f3f5   11.36 : 1
라이트  muted  #666666  on raised  #ffffff    5.74 : 1
라이트  muted  #666666  on surface #f8f9fa    5.45 : 1
라이트  muted  #666666  on sunken  #f1f3f5    5.16 : 1
라이트  강조   #a40f16  on raised  #ffffff    7.90 : 1
라이트  강조   #a40f16  on soft    #fdeeef    7.02 : 1

다크    본문   #f4f4f5  on surface #0a0a0a   18.01 : 1
다크    본문   #f4f4f5  on sunken  #101010   17.31 : 1
다크    본문   #f4f4f5  on raised  #161616   16.46 : 1
다크    본문   #f4f4f5  on field   #1c1c1c   15.50 : 1
다크    본문   #f4f4f5  on soft    #2a1214   15.99 : 1
다크    muted  #a1a1aa  on surface #0a0a0a    7.72 : 1
다크    muted  #a1a1aa  on raised  #161616    7.06 : 1
다크    강조   #ff4d52  on surface #0a0a0a    6.07 : 1
다크    강조   #ff4d52  on raised  #161616    5.55 : 1
다크    강조   #ff4d52  on soft    #2a1214    5.38 : 1
다크    strong #ff7175  on raised  #161616    6.78 : 1

[채움 배경 위 텍스트 — 4.5:1 기준]
라이트  on-primary #ffffff on fill   #a40f16    7.90 : 1
라이트  on-primary #ffffff on strong #790b11   11.24 : 1
다크    on-primary #ffffff on fill   #c4121b    6.09 : 1
다크    on-primary #ffffff on fill-hover #d7141e  5.24 : 1

[비텍스트 정보 요소 — 3:1 기준]
라이트  포커스 테두리   #a40f16 on field  #ffffff   7.90 : 1
라이트  border-strong #8a8a8a on raised #ffffff   3.45 : 1
라이트  border-strong #8a8a8a on sunken #f1f3f5   3.10 : 1
다크    포커스 테두리   #ff4d52 on field  #1c1c1c   5.22 : 1
다크    border-strong #71717a on raised #161616   3.74 : 1
다크    border-strong #71717a on sunken #101010   3.94 : 1
다크    채움 경계      #c4121b on surface #0a0a0a   3.25 : 1
```

**장식으로 분류해 기준을 적용하지 않는 것**

- `--color-border` — 카드 윤곽과 구분선. 정보를 전달하지 않는다.
- `--color-primary-border` — 안내 박스 테두리와 카드 hover 테두리. **상태를 전달하는 것은 함께 바뀌는 배경(`--color-primary-soft`)과 텍스트이지 이 테두리가 아니므로 순수 장식으로 분류한다** (다크 기준 1.42:1).
- `--color-primary-shadow`, `--color-shadow` — 그림자.

**여유가 가장 적은 조합**

라이트의 `border-strong` on `sunken`(3.10:1)과 다크의 채움 경계 on `surface`(3.25:1)다. 이 둘은 기준선에 가까우므로 **관련 토큰을 조정할 때 반드시 재측정한다**.

- 팔레트를 조정하면 위 조합을 다시 측정하고 결과를 PR 본문과 이 표에 남긴다. 기준 미달 조합이 하나라도 있으면 병합하지 않는다.

## 4-3-6 랜딩 다크 팔레트

랜딩도 세 모드를 모두 지원한다. 다크 값은 **문서 루트의 다크 표식 아래 한 블록**에 모은다.

**브랜드 색은 확장과 같은 값을 쓴다**. `--color-primary`, `-strong`, `-soft`, `--color-on-primary` 네 토큰이 토큰 규칙의 동기 대상이다.

**표면과 연출은 랜딩 고유로 유지한다**. 다음은 확장과 값이 달라도 된다.

| 유지하는 것 | 이유 |
| --- | --- |
| `--color-background`, `--color-surface`, `--color-surface-muted`, `--color-foreground`, `--color-muted`, `--color-border` | 홍보 표면의 배경 성격이 도구 화면과 다르다. **단 값은 중성이어야 한다** |
| `--color-focus` (파랑) | 랜딩에만 있는 역할이다 |
| 그라디언트, 글로우, 히어로 연출 | 확장 우선 원칙에 따라 랜딩 고유 표현이다 |

**채움은 모두 `--color-primary-fill`을 쓴다**. 버튼·결과 마크 같은 작은 컨트롤과 `.feature-card-accent`·`.cta-card` 같은 큰 브랜드 패널이 같은 토큰을 공유한다.

**크기와 무관하게 같은 채움 토큰을 쓴다.** `--color-primary-fill`이 두 테마 모두 짙은 빨강이므로 큰 패널에도 그대로 쓸 수 있고, 다크 전용 오버라이드가 필요 없다.

**배경이 테마와 무관하게 고정된 자리는 전용 토큰을 쓴다**. 랜딩에는 두 곳이 있다. 여기에 `--color-on-primary`나 `--color-primary`를 쓰면 테마에 따라 값이 뒤집혀 대비가 깨진다.

| 토큰 | 값 | 배경 | 쓰이는 곳 |
| --- | --- | --- | --- |
| `--color-on-primary-muted` | `#f7dee0` | 브랜드 패널 `--color-primary-fill` | feature 번호·본문, CTA 본문 |
| `--color-flow-accent` | `#ff4d52` | flow 섹션 `#1d1d1d` | 섹션 kicker, 단계 번호 |

`--color-flow-accent`는 다크 주색과 같은 값을 쓴다 — flow 섹션이 항상 어두우므로 "어두운 배경 위 브랜드 색"이라는 같은 문제를 푼다. 이 토큰은 다크 변형이 없다.

`--color-on-primary-muted`는 채움 배경 위에 올라가므로 **두 테마의 채움 값 모두에 대해 4.5:1을 만족해야 한다**.

**실측값** (WCAG 2.1 상대 휘도 기준)

```text
[다크 텍스트 — 4.5:1 기준]
foreground #f4f4f5 on background   #0a0a0a   18.01 : 1
foreground #f4f4f5 on surface      #161616   16.46 : 1
foreground #f4f4f5 on surface-muted #1c1c1c  15.50 : 1
muted      #a1a1aa on background   #0a0a0a    7.72 : 1
muted      #a1a1aa on surface      #161616    7.06 : 1
primary    #ff4d52 on background   #0a0a0a    6.07 : 1
primary    #ff4d52 on surface      #161616    5.55 : 1
primary    #ff4d52 on soft         #2a1214    5.38 : 1
strong     #ff7175 on surface      #161616    6.78 : 1
focus      #73a7ff on background   #0a0a0a    8.20 : 1

[채움 배경 위 텍스트 — 4.5:1 기준]
on-primary       #ffffff on fill(라이트) #a40f16   7.90 : 1
on-primary       #ffffff on fill(다크)   #c4121b   6.09 : 1
on-primary-muted #f7dee0 on fill(라이트) #a40f16   6.20 : 1
on-primary-muted #f7dee0 on fill(다크)   #c4121b   4.78 : 1
flow-accent      #ff4d52 on flow 섹션    #1d1d1d   5.17 : 1
스킵 링크         #0a0a0a on foreground  #f4f4f5  18.01 : 1

[정보성 비텍스트 — 3:1 기준]
검색 데모 테두리 #ff4d52 on surface #161616   5.55 : 1
```

`--color-border`(`#27272a`)는 카드 윤곽을 잡는 장식이라 대비 기준의 대상이 아니다.

**테마에 따라 뒤집히는 색 위에 고정 색 텍스트를 올리지 않는다.** 키보드 스킵 링크가 그 예다 — 배경이 `--color-foreground`이므로 글자는 `--color-background`로 두어 두 테마에서 함께 반전되게 한다.
