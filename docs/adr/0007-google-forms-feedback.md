# ADR 0007: 문의 채널로 Google Forms 선택

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 작성일 | 2026-07-30 |
| 이슈 | - |
| 출처 | 옛 `spec/3-3-DESIGN-DECISIONS.md` §3-3-7 (2026-09-13 분리) |

**배경**

사용자 의견을 받을 경로가 필요했다. GitHub 이슈만으로는 계정이 없는 학생을 놓친다.

결정을 지배한 제약은 하나다. **확장 프로그램은 소스가 공개된다.** 스토어 패키지는 누구나 열어볼 수 있고 저장소도 공개다. 따라서 **어떤 비밀 키도 확장 안에 숨길 수 없다.**

**대안**

1. 자체 백엔드 API — 서버 운영 비용과 인증 키 보관 문제
2. 서드파티 폼 SaaS의 API 키 방식 — 키가 노출되면 폼이 오남용된다
3. Google Forms `formResponse` 직접 POST — 지금 구성

**결정**

3번을 택했다. Google Forms의 응답 제출 주소로 백그라운드 POST를 보낸다. 이 주소와 필드 id는 **공개돼도 안전한 값**이다. 노출되어도 남이 할 수 있는 일은 폼에 응답을 넣는 것뿐이고, 그건 원래 누구나 할 수 있다.

수신은 응답 시트와 이메일 알림으로 처리한다. 팝업·설정·랜딩 세 경로의 문의가 폼 하나로 모인다.

답변용 이메일은 Forms의 **내장 "이메일 수집" 기능을 쓰지 않고 선택 단답형 질문으로 받는다.** 내장 기능은 로그인을 강제해 익명 백그라운드 전송이 깨지기 때문이다. 이메일 질문 id를 비워두면 입력란 자체가 숨겨지므로, 이메일을 받지 않는 구성으로도 운영할 수 있다.

**영향**

- 서버가 없다. 운영 비용이 0이고 개인정보를 직접 보관하지 않는다.
- 확장에 비밀값을 두지 않는다는 원칙이 유지된다. 새 외부 연동을 추가할 때도 같은 기준을 적용한다 (MUST) — **비밀 키가 필요한 방식은 채택할 수 없다.**
- 대가로 전송 성공을 확인할 수 없다. CORS 제약 때문에 응답을 읽지 못하므로 "네트워크 오류 없음 = 성공"으로 간주한다. 이 한계에서 파생되는 검증 절차가 [5-TESTING](../spec/5-TESTING.md)에 있다.
- 확장과 랜딩이 같은 폼·같은 필드를 쓰는지는 테스트로 고정한다.
