# ADR 0013: 릴리스 무결성 장치

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 작성일 | 2026-07-30 |
| 이슈 | - |
| 출처 | 옛 `spec/3-3-DESIGN-DECISIONS.md` §3-3-13 (2026-09-13 분리) |

**배경**

릴리스는 사람이 여러 단계를 순서대로 밟는 작업이다. 버전을 올리고, 노트를 쓰고, 머지하고, 태그를 민다. 어느 하나를 빠뜨리면 **잘못된 산출물이 스토어로 나간다.** 배포된 뒤에는 되돌리기 어렵다.

**대안**

1. 체크리스트 문서로 사람이 확인
2. 자동 검증으로 막는다 — 채택 (문서와 병행)

**결정**

2번을 택했다. 릴리스 경로에 세 가지 장치를 뒀다.

| 장치 | 막는 실수 |
| --- | --- |
| 태그와 매니페스트 버전 대조 | 버전을 올리지 않고 태그만 미는 것 |
| 릴리스 노트 존재 확인 | 노트 없이 릴리스가 나가는 것 |
| 재현 가능한 패키징 | 같은 커밋에서 다른 ZIP이 나오는 것 |

패키징은 파일 타임스탬프를 고정값으로 기록한다. 체크아웃 시각과 무관하게 **같은 소스에서 항상 같은 바이트의 ZIP이 나온다.** 스토어에 올린 파일이 저장소의 어느 커밋에서 나왔는지 해시로 대조할 수 있다.

**영향**

- 릴리스 실수가 배포 전에 워크플로에서 막힌다.
- 재현 가능성은 테스트로 고정되어 있다. 패키징 스크립트를 고칠 때 이 성질을 깨뜨리면 테스트가 실패한다 ([5-TESTING](../spec/5-TESTING.md)).
- 대가로 ZIP의 파일 시각이 1980년으로 보인다. 스토어 심사와 동작에 영향이 없어 감수한다.
