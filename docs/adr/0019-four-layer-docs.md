# ADR 0019: 문서를 requirements·adr·design·spec 4계층으로 나누고 옛 문서는 고치지 않는다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 작성일 | 2026-09-13 |
| 이슈 | [#198](https://github.com/kangkyunghyun/LinKHU/issues/198) |
| 요구사항 | [../requirements/198-four-layer-docs.md](../requirements/198-four-layer-docs.md) |

**배경**

결정 기록이 `spec/3-3-DESIGN-DECISIONS.md` 한 파일에 18건 쌓여 있었고, 후속 변경이 생기면 옛 항목을 제자리에서 고쳤다(3-3-16의 후속 변경 표시, 3-3-18에 #196 덧붙임). 그러면 "그때 왜 그렇게 정했는지"가 git log를 뒤져야만 나온다. 요구사항은 GitHub 이슈에만 있어 에이전트가 매번 네트워크로 읽어와야 했고, 이슈 댓글에서 이뤄진 결정은 더 찾기 어려웠다.

여러 기능을 병행할 때 필요한 것은 "현재 어떻게 동작하는가"와 "그때 왜 그렇게 정했는가"를 저장소 안에서 나란히 읽는 것이다.

**대안**

1. 현행 유지 + 3-3 불변 규칙만 추가 — 폴더를 늘리지 않고 규칙 두 줄로 끝난다. 그러나 요구사항이 여전히 GitHub에만 있다.
2. `requirements/`만 최상위에 추가 — 요구사항은 해결되지만 결정 기록은 여전히 한 파일이라 "고치지 않는다"를 지키기 어렵다.
3. `docs/` 아래 requirements·adr·design·spec 4계층 — 채택.

**결정**

3번. `docs/`를 문서 루트로 삼고 네 폴더를 둔다. 앞의 셋은 그 시점의 기록이라 구현이 끝나면 고치지 않고, 이후 변경은 새 문서로 남긴다. 현재 동작은 `spec/`만이 설명하며 코드와 함께 갱신한다.

이를 위해 GitHub Pages 랜딩을 `docs/`에서 `landing/`으로 뺐다. `docs/`가 통째로 Pages 아티팩트였고 `docs/**` 변경마다 재배포됐기 때문에, 문서 폴더로 쓰려면 배포물과 분리해야 했다.

Design은 **자명하지 않을 때만** 쓴다. 매 이슈마다 쓰면 PR 본문과 같은 내용을 두 번 쓰게 된다. 요구사항도 완료 조건이 둘 이상이거나 여러 문서가 움직일 때 쓰고, 한 줄짜리 변경은 이슈 본문으로 끝낸다.

**영향**

- 작업 시작 순서가 "요구사항 파일 → 이슈 → 브랜치"로 바뀐다. 요구사항 파일이 원본이고 이슈는 사본이다.
- ADR은 `NNNN-slug.md` 한 건 한 파일이다. 결정을 뒤집을 때는 새 ADR을 쓰고 옛 ADR의 상태만 바꾼다.
- 스펙 문서는 결과만 쓰고 ADR을 링크한다. 이 원칙은 이전부터 있었고 위치만 바뀌었다.
- 동기화할 문서가 늘어난다. 이 비용을 줄이려고 requirements와 design은 "필요할 때만"으로 문턱을 뒀다. 문턱이 잘 지켜지지 않아 문서가 형식적으로 쌓이면 이 결정을 재검토한다.
- 옛 ADR 본문의 `docs/` 경로는 당시 랜딩 폴더를 뜻한다. 본문을 고치지 않는다는 규칙을 이 마이그레이션에도 적용했고, 색인이 한 줄로 안내한다.
