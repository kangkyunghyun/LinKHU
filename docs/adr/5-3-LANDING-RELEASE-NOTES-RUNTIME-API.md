## 5-3-1 배경

릴리스 노트가 저장소와 GitHub Releases에만 있었다. 홈페이지로 온 학생은 무엇이 언제 바뀌었는지 볼 곳이 없고, 그 역할을 커뮤니티 홍보글이 떠맡아 **처음 보는 사람에게 변경 이력부터 들이미는** 상태였다.

## 5-3-2 대안

1. **빌드 시점 생성** — 릴리스 때 `release-notes/*.md`를 읽어 `landing/assets/releases.json`을 만든다
2. **런타임 fetch** — 브라우저가 GitHub Releases API를 부른다 — 채택
3. 손으로 랜딩에 옮겨 적는다 — 릴리스마다 사람이 한 번 더 해야 하므로 검토에서 제외

## 5-3-3 결정

2번을 택했다. **릴리스를 내면 홈페이지가 저절로 따라온다.** 1번은 산출물이 하나 늘고, 릴리스마다 재생성·검증이 필요하며, 생성을 빠뜨리면 홈페이지만 옛 내용으로 남는다. 이미 `validate:landing-data`가 같은 종류의 어긋남을 막으려고 존재하는데 그 대상을 하나 더 늘리는 셈이다.

**이것이 랜딩이 외부 API를 부르는 첫 사례다.** 지금까지 랜딩의 `fetch`는 정적 자산(`assets/services.json`)뿐이었고, GitHub API를 부르는 것은 확장의 `src/version.js`뿐이었다. 그래서 아래 네 가지를 함께 정했다.

## 5-3-4 `### Internal`을 거른다 (MUST)

릴리스 노트의 `### Internal`은 저장소 기록이지 사용자에게 보일 것이 아니다. 그대로 뿌리면 "토큰으로 통합", "폭 가드 추가"가 학생에게 보인다. Firefox 배포에서 이미 한 번 새어 나갔다([#171](https://github.com/kangkyunghyun/LinKHU/issues/171)).

거르는 규칙은 `scripts/publish-firefox.js`와 `landing/landing.js`에 **두 벌로 있다.** Node 스크립트와 브라우저라 파일을 공유할 수 없기 때문이다. 검색 랭킹이 같은 이유로 두 벌인 것과 같다([3-1](../spec/3-1-DESIGN-SOFTWARE-ARCHITECTURE.md)). **주석으로 서로를 가리키는 데서 그치지 않고, 실제 `release-notes/*.md` 전부에 두 구현을 돌려 결과가 같은지 테스트로 고정한다** (MUST). 갈라지면 `npm test`가 실패한다.

## 5-3-5 마크다운 파서를 넣지 않는다 (MUST)

ADR 1-1의 의존성 없음이 이유다. 릴리스 노트가 쓰는 문법은 **`### 제목`, `- 불릿`, `` `코드` `` 셋뿐**이므로 그 범위만 다루는 렌더러를 직접 쓴다. 범위 밖 문법(표, 링크, 굵게)이 들어오면 **글자 그대로 보인다** — 깨지지 않고 마크업 기호가 노출될 뿐이다. 릴리스 노트에 새 문법을 쓰기 시작하면 이 렌더러를 함께 고친다 (MUST).

## 5-3-6 본문은 신뢰 경계 밖이다 (MUST)

`body`는 GitHub API 응답이다. 우리가 쓴 글이지만 우리 저장소 밖을 거쳐 오므로 **`innerHTML`로 붙이지 않는다.** `createElement`와 `textContent`로만 조립해, 본문에 마크업이 들어와도 글자로 보이게 한다. 테스트가 `innerHTML` 대입 자체를 막는 가짜 DOM으로 이 성질을 고정한다.

## 5-3-7 실패하면 섹션을 감춘다 (MUST)

GitHub이 응답하지 않거나 rate limit(비인증 60회/시간, 방문자 IP 기준)에 걸릴 수 있다. **빈 상자를 남기지 않는다** — 로딩 중인지 내용이 없는 것인지 구분되지 않는다. 섹션 전체를 `hidden`으로 두고, 푸터의 GitHub Releases 링크가 대체 경로가 된다. 소개 흐름은 이 섹션이 없어도 성립한다.

## 5-3-8 영향

- **캐시는 `sessionStorage`에 탭 세션 단위로 둔다.** 확장의 `version.js`가 쓰는 12시간 TTL을 옮기지 않았다. 개인 방문자는 시간당 60회를 넘길 일이 없지만 **학내망은 NAT로 IP를 공유하므로 한도가 집단으로 소진될 수 있다.** 세션 캐시는 그 배수의 주범인 새로고침을 없애면서, TTL 관리 없이도 하루 지난 내용을 보여줄 일이 없다. 저장소 접근이 막힌 환경(시크릿 모드 등)에서는 예외를 삼키고 매번 받는다 — 캐시는 있으면 좋은 것이지 없으면 안 되는 것이 아니다.
- **최근 다섯 개만 그리고, 그중 최신 하나만 펼친다.** 나머지는 `<details>`의 제목 줄로 접힌다. 여닫기를 네이티브 요소에 맡겨 JS 토글이 없다. 처음에는 전부 그렸는데, 접어도 열여덟 줄이라 소개 흐름을 끊었다. **잘린 나머지는 섹션 아래 "GitHub에서 전체 릴리스 보기"가 받으므로 볼 수 없게 되지는 않는다.** 개수 상한은 `tests/landing-releases.test.js`가 고정한다 — 상한이 없으면 릴리스가 쌓이면서 조용히 되돌아간다.
- 변경 이력을 홈페이지가 맡으므로 **커뮤니티 홍보글은 소개에 집중한다.** 그 글에서 `(vX.Y.Z 업데이트)` 목록을 걷어냈고(이슈 [#192](https://github.com/kangkyunghyun/LinKHU/issues/192)), 릴리스 문구 스킬도 **버전 목록은 스토어 글에만 둔다**로 바꿨다. 커뮤니티 글을 읽는 사람은 이전 버전을 모른다. 이어서 스토어 문법(제품명 제목, 대괄호 기능 목록, 단축키 나열, 리뷰·스타 요청)도 걷어내고 독자의 불편에서 시작하는 게시글로 다시 썼다(이슈 [#196](https://github.com/kangkyunghyun/LinKHU/issues/196)). 게시판에서 스토어 문법은 광고로 읽혀 넘겨진다.
- 랜딩이 외부 API에 의존하기 시작했다. **이후 외부 호출을 추가할 때도 위 네 가지(거르기·파서 없음·신뢰 경계·실패 폴백)를 같은 기준으로 적용한다** (MUST).
